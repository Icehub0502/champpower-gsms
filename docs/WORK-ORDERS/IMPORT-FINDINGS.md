## 0. ผมแจ้งผิดไปก่อนหน้านี้ ขอแก้

ผมบอกว่า **"สต๊อกในระบบเก่าว่างเปล่า อะไหล่ 447 รายการมีของแค่ 9 รายการ 15 ชิ้น"**
อันนั้นผมอ่านจาก dump ในเครื่อง ซึ่งเป็น **ข้อมูล dev ไม่ใช่ production** ของจริงคือ:

| | รายการ | มีของ | รวมชิ้น |
|---|---|---|---|
| `racks` (แร็ค) | 126 | 84 | 236 |
| `wing_arms` (ปีกนก) | 386 | 235 | 799 |
| **รวม** | **512** | **319** | **1,035** |

สต๊อกใน production **ไม่ว่าง** มีของอยู่ 1,035 ชิ้นใน 319 รายการ
คำแนะนำก่อนหน้าของผมตั้งอยู่บนข้อมูลผิด — คุณตัดสินใจเรื่องไม่นำเข้าสต๊อกโดยได้ข้อมูลที่ไม่ถูกจากผม
ถ้าอยากทบทวนการตัดสินใจนั้นใหม่ ตอนนี้มีข้อมูลจริงแล้ว

> หมายเหตุประกอบการตัดสินใจ: ตัวเลขนี้เป็น counter ที่ถูกบวกลบมาเรื่อย ๆ ไม่มี ledger รองรับ
> (ตาราง `stock_ledger` ไม่เคยถูก deploy ขึ้น production) จึงไม่มีทางตรวจย้อนได้ว่ามันตรงกับของจริงบนชั้นแค่ไหน
> "มีเลข" กับ "เลขถูก" คนละเรื่องกัน — แต่นี่เป็นเรื่องที่คุณตัดสิน ไม่ใช่ผม

## 2. schema บน production ต่างจากสำเนาในเครื่อง

production มี **27 ตาราง** สำเนาในเครื่องมี **39** — 12 ตารางนี้ **ไม่เคยขึ้น production เลย**:

```
parts, part_codes, part_fitments          ← การรวมอะไหล่เป็นตารางเดียว
stock_ledger, stock_counts, stock_count_items  ← โมดูลสต๊อก
suppliers                                  ← รายชื่อร้านอะไหล่
prod_racks, prod_wing_arms, prod_transactions,
rack_fitments, wing_arm_fitments
```

ผลที่ตามมา:
- อะไหล่ใน production ยังแยกเป็น `racks` + `wing_arms` **ไม่มีตาราง `parts` รวม** → สคริปต์นำเข้าต้องอ่านสองตารางแล้วรวมเอง
- **ไม่มีรายชื่อร้านอะไหล่ (suppliers) ใน production เลย** → เริ่มจากศูนย์ ต้องคีย์ใหม่
- โมดูลสต๊อกที่เขียนไว้ ไม่เคยถูกใช้จริงบนของจริง

## 4. เรื่องด่วนที่สุด — ค่าหลอกจะทำลายกฎจับคู่ที่เพิ่งสั่งไป

ผมสั่งให้ resolver ของ arrive/check-in จับคู่ลูกค้าด้วย **เบอร์โทร** และจับคู่รถด้วย **ทะเบียน**
ข้อมูลจริงบอกว่ากฎนั้นจะพังทันที:

**เบอร์โทร**
```
0999999999   ใช้ซ้ำ 8 ราย   ← ค่าหลอกที่พนักงานพิมพ์ตอนลูกค้าไม่ให้เบอร์
0993333333   ค่าหลอก
0000000000   ค่าหลอก
```
อีก 8 เบอร์ที่ซ้ำ 2 ราย (น่าจะคนเดียวกันคีย์ซ้ำ — อันนี้ควรรวม)

**ทะเบียน** — ซ้ำ 9 กลุ่ม เกินมา 12 แถว
```
1กอ2222  x4      1กก1111  x3     ← ข้อมูลทดสอบชัดเจน
ญส6798 x2   2กก5233 x2   กท1325 x2
2ฒษ4181 x2  ฌย3722 x2   กต9558 x2   ฎก1513 x2
```

> **ถ้าปล่อยไว้: ลูกค้า 8 รายที่ไม่เกี่ยวกันเลยจะถูกยุบเป็นคนเดียว**
> เพราะทุกคนใช้เบอร์ `099-999-9999` เหมือนกัน ประวัติซ่อมของทั้ง 8 คนจะกองรวมกัน
> นี่คือหายนะแบบเดียวกับ `vehicle_owner_mismatch` แต่เข้ามาทางประตูเบอร์โทร

### กฎที่ต้องเพิ่มใน WO-003 (ด่วน — resolver กำลังถูกเขียนอยู่ตอนนี้)

1. มีตาราง **ค่าที่ห้ามใช้เป็นกุญแจจับคู่** (placeholder blocklist) ตั้งค่าได้ต่อร้าน
   ค่าตั้งต้น: เบอร์ที่เป็นเลขเดียวกันซ้ำ ๆ ทั้งเบอร์ (`0999999999` `0000000000` `0993333333`)
   ~~ทะเบียนแบบ `1กก1111` `1กอ2222`~~ — **ยกเลิก (Ice ตัดสิน 29–30 ก.ย. 2026)**: ทะเบียนเลขซ้ำคือทะเบียนจริงที่ลูกค้าจ่ายเงินซื้อ
   ทะเบียนจึงไม่มีกฎ pattern ถูกบล็อกได้ทางเดียวคือแถวใน `match_blocklist` ของร้านนั้น (commit `bca173d`)
   ส่วนรถ `1กอ2222` ×4 และ `1กก1111` ×3 ในข้อมูลเดิมเป็น**แถวทดสอบ → ไม่นำเข้าเลย** (ดู WO-004 §3)
2. เบอร์หรือทะเบียนที่อยู่ใน blocklist → **สร้างลูกค้า/รถใหม่เสมอ ห้ามจับคู่กับของเดิม**
   (ยังเก็บค่าไว้ในระเบียนได้ แค่ห้ามใช้เป็นกุญแจ)
3. กฎอัตโนมัติเสริม: ถ้าเบอร์หนึ่งถูกใช้เกิน 3 ราย ระบบเตือนผู้ดูแล และหยุดใช้เบอร์นั้นจับคู่
4. สคริปต์นำเข้าใช้ blocklist ชุดเดียวกัน **ห้ามเขียนกฎแยกอีกชุด**
