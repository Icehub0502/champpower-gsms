# คำตัดสิน 7 ต.ค. — รับความเสี่ยง 3 ข้อ และหน่วยประกัน

---

## 1. หน่วยประกัน — **วัน (`days`) ไม่ใช่เดือน**

ผมไปอ่าน schema จริงก่อนตอบ คำถามนี้ถูกตอบไปแล้วในโค้ด:

| | |
|---|---|
| `warranties.days integer` | migration **0010** — หน่วยคือ **วัน** |
| `document_lines.warranty_term_id` · `warranty_days` · `warranty_max_km` | **มีอยู่แล้วตั้งแต่ 0010** |
| 0021 เพิ่มแค่ | `warranty_name` + FK ที่ปลอดภัยต่อสาขา `(shop_id, warranty_term_id)` + CHECK |

**ทีมทำถูกแล้ว** — แผน v2 เคยเขียนว่าจะเก็บเป็น "จำนวนเดือนรวม" แต่ตอนลงมือกลับใช้ `warranty_days` ที่มีอยู่
ซึ่งถูกต้องกว่าแผน **อย่าเอาเดือนกลับมา** ระบบหน่วยเดียวมีค่ามากกว่าความแม่นระดับวัน

### การแปลงตอนนำเข้า (WO-004)

```
days = warranty_year × 365 + warranty_month × 30
```

ข้อมูลจริงทั้ง **596 แถว** ที่มีประกัน เป็น **1 ปีถ้วนทั้งหมด** (ลูกหมาก 514 · แร็ค 73 · โช๊ค 9)
→ สูตรนี้แม่น 100% กับข้อมูลที่มีจริง ส่วนทางเดือนแทบไม่ถูกใช้

*(ข้อเสียที่รู้อยู่: 365 วันจากวันที่ 1 มี.ค. ในปีอธิกสุรทิน จะคลาดไป 1 วัน — ยอมรับได้
เพราะ `expires_at` ถูกคำนวณครั้งเดียวแล้วตรึงไว้ ไม่ขยับอีก และไม่มีอู่ไหนปฏิเสธเคลมเพราะเกิน 1 วัน)*

## 2. ความเสี่ยงที่เหลือ 3 ข้อ — **รับทั้งหมด** พร้อมของที่ต้องตามเก็บ

### 2.1 ราคาแรกที่ advisor ตั้ง ค้างไว้โดยไม่มีคนตรวจ — **รับ**

ทางเลือกคือตั้งคิวให้ผู้จัดการอนุมัติราคาใหม่ทุกตัว ซึ่งในสองสัปดาห์แรกจะเป็นหลายร้อยรายการ
และจะไปขวางการเปิดใบเสนอราคา — **ยาแรงกว่าโรค**

มีอยู่แล้ว: endpoint แก้ราคา (manager) · audit `catalog_price_set` ทุกครั้ง

**ของที่ต้องตามเก็บ — ใส่เป็นรายการชื่อชัดใน P3.1b:**
> **"หน้าจอราคาที่เพิ่งตั้ง 7 วันล่าสุด"** — ผู้จัดการกวาดตาดูได้ในหน้าเดียว

ไม่ใช่ "ไว้ค่อยทำ" แบบลอย ๆ — เพราะ audit ที่ไม่มีใครเปิดดู เท่ากับไม่มี

### 2.2 ส่วนลดไม่มีเพดาน — **รับ แต่กำหนดเส้นไว้แล้วสำหรับ P3.2**

เหตุผลที่รับได้ตอนนี้: **ตรวจจับได้เร็ว** ยอดส่วนลดโผล่ในสรุปยอดรายวันที่เจ้าของร้านดูทุกวัน
บิลที่ถูกลดจนเหลือศูนย์จะเห็นภายในวันเดียว ไม่ใช่ความเสี่ยงแบบ "ไม่มีใครรู้เป็นเดือน"
และยอดถูก clamp ไม่ให้ติดลบอยู่แล้ว + audit ครบ

**ตัดสินไว้เลยสำหรับ P3.2 (ตอนทำใบเสร็จ จะแตะส่วนลดอยู่แล้ว ไม่ต้องมาถกใหม่):**

| ส่วนลด | ใคร |
|---|---|
| ≤ 40% ของยอดรวม | advisor |
| > 40% | **manager ขึ้นไป** + บังคับเหตุผล |

เส้น 40% มาจากข้อมูลจริง: ส่วนลดที่ใช้จริงเฉลี่ย **3.7%** สูงสุดที่เคยมี **28.6%**
→ 40% อยู่เหนือทุกเคสจริงอย่างสบาย แต่ต่ำกว่าการล้างบิลมาก

### 2.3 ไม่มีลายเซ็นลูกค้าบนจอ — **รับ** (ผมเป็นคนตัดเอง)

ตัดจากข้อมูลจริง: ใบเสร็จ 358 ใบมีลายเซ็น 46 · ใบเสนอราคา 482 ใบมีลายเซ็น **1**
พนักงานไม่เคยใช้ฟีเจอร์นี้อยู่แล้ว

**ตัวควบคุมจริงคือกระดาษ A4 ที่ลูกค้าเซ็น** ซึ่งเชื่อถือได้กว่าลายเซ็นบนจอที่ถูกใช้ 13%

> **ช่องว่างที่ต้องรู้:** การพิมพ์ A4 มาพร้อม P3.2 (~24 ต.ค.)
> ระหว่างนี้ ใบเสนอราคาจากระบบใหม่ยัง**พิมพ์ไม่ได้** — พนักงานต้องใช้วิธีเดิมไปก่อน
> ไม่ใช่ข้อบกพร่อง แต่ต้องบอกพนักงานให้ชัดตอนเริ่มใช้ ไม่ใช่ให้เขาไปงงหน้าเคาน์เตอร์
