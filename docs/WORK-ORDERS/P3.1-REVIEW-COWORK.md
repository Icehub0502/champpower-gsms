# ผลตรวจแผน P3.1 — **ยังไม่อนุมัติ** ให้แก้ 3 ข้อแล้วส่งกลับ

1 ต.ค. 2026 · ตรวจโดย Cowork เทียบกับ dump production จริง (16 ก.ย. 2026)

---

## สรุปก่อน

แผนนี้**คุณภาพดีจริง** — ไปอ่านต้นแบบเองไม่ใช่อ่านสรุป, จับได้ว่า WO-005 ของผมเขียนผิดเรื่อง
"Parts Editor", ใช้ schema เดิมแทนสร้างใหม่, รายการความเสี่ยงซื่อสัตย์, แบ่งงานตาม §14 ถูกต้อง
**ส่วนที่เขียนไว้ไม่ต้องรื้อ** — ที่ขาดคือ 3 เรื่องที่จะเจอได้ต่อเมื่อไปดู*เนื้อหา*ของใบเสนอราคาจริง
ไม่ใช่แค่ดูโครงตาราง

---

## 0. ข้อที่ **ผมผิด เขาถูก** — ต้องบันทึกไว้

ผมเคยบอก Ice ว่า *"ตารางราคา 71,558 แถว คือของที่มีค่าที่สุด ถ้าคีย์ใหม่คือเดือนนึงหายไปเลย"*

ผมตรวจ dump จริงซ้ำแล้ว:

| | |
|---|---|
| `quote_part_prices` ทั้งหมด | **71,558 แถว** |
| มีราคา > 0 | **1 แถว** (Ford Laser แร็ค OEM 5,500) |
| `needs_price = 1` | **71,556 แถว** |

**เป็นตารางเปล่า ไม่ใช่สมบัติ** คำแนะนำเดิมของผมเรื่องลำดับความสำคัญของการนำเข้าข้อมูลผิด
ต้องแก้ทั้งใน `IMPORT-FINDINGS.md` และ `WO-004`

---

## 1. แต่ทีมก็พลาดเหมือนกัน — **ราคาจริงมีอยู่ คนละตาราง**

แผนสรุปว่า *"ราคากลางจะว่างเปล่าในวันแรก"* — **ไม่จริง** ของจริงอยู่ที่นี่:

| ตาราง | แถว | มีราคา |
|---|---|---|
| `products` | 1,403 | **1,374 (97.9%)** |
| `service_items` | 265 | มี `set_price` สำหรับชุด |

ตัวอย่างจริงจาก `products`: `RTCH5201 · แร็คใหม่ OEM CHEVROLET… · 4,400` — **มีราคาจริงทั้งหมด 1,374 รายการ**

ก่อนเขียน 0020 ต้องไปดู `products` และ `service_items` ก่อน ไม่ใช่สรุปว่าไม่มีราคาเลย

## 2. ช่องว่างที่ 1 — **ไม่มีแนวคิด "ชุด/แพ็กเกจ" ทั้งที่เป็นของที่ขายดีที่สุด**

ผมนับบรรทัดใบเสนอราคาจริงทั้ง **2,423 บรรทัด** จาก 482 ใบ:

```
148  ชุดโปรช่วงล่าง          ← อันดับ 1 ของทั้งร้าน
127  ค่าแรง
112  - ลูกหมากคันชักนอก L+R
 95  - ประกอบติดตั้ง รวมตั้งศูนย์
 92  - ปีกนกล่าง L+R
 92  - ลูกหมากปีกนกล่าง L+R
 89  แร็ค OEM
 89  - ยางรัดกันโคลง L+R
 85  - ลูกหมากกันโคลง L+R
 83  ส่วนลด
```

**บรรทัดที่ขึ้นต้นด้วย `- ` คือรายการย่อยในชุด ราคา 0** และ **974 จาก 2,423 บรรทัด (40%) มีราคาเป็น 0**
ทั้งหมดคือรายการย่อยของชุด

และกลไกนี้มีอยู่ในฐานข้อมูลเดิมแล้วจริง ๆ:
- `service_items.is_set` + `set_price`
- `service_item_components` (`component_name`, `default_qty`, `sort_order`)

**ถ้าระบบใหม่ไม่มีชุด พนักงานต้องพิมพ์รายการย่อย 8 บรรทัดด้วยมือทุกครั้งที่ขายชุด
ซึ่งเป็น 40% ของบรรทัดทั้งหมดที่ร้านพิมพ์** งานจะช้ากว่าระบบเก่า แล้วเขาจะไม่ใช้

**ต้องเพิ่ม:** เลือกชุด 1 ครั้ง → ระบบกาง component ออกเป็นบรรทัดย่อยอัตโนมัติ ราคาอยู่ที่บรรทัดแม่
แก้/ลบบรรทัดย่อยได้ ยอดรวมต้องคิดจากบรรทัดแม่เท่านั้น ห้ามบวกซ้ำ

## 3. ช่องว่างที่ 2 — **ตารางราคาคีย์ผิดแกน**

แผนออกแบบ `part_prices` คีย์ `(shop_id, brand_key, model_key, part_key)` — คือรูปทรงของ
`quote_part_prices` ซึ่งเป็น**ตารางที่ไม่มีใครกรอก**

แต่ของที่ร้านใช้จริงคือ `service_items` ซึ่งคีย์คนละแกน:

```
category (แร็คพวงมาลัย / ช่วงล่างหน้า / ...) → product_name (แร็ค OEM / ปีกนกล่าง L+R / ...)
```

**ไม่มียี่ห้อ ไม่มีรุ่นรถอยู่ในแกนนี้เลย** พนักงานเลือกจาก "หมวด → ชื่อรายการ" ไม่ใช่ "ยี่ห้อ → รุ่น"

> ตารางที่คนไม่เคยกรอกตลอด 3 เดือนที่ใช้งานจริง บอกเราว่ามันไม่เข้ากับวิธีทำงานของเขา
> การสร้างตารางใหม่ด้วยรูปทรงเดิมเป๊ะ ๆ แล้วหวังว่ารอบนี้จะมีคนกรอก — **ไม่สมเหตุสมผล**

**ต้องตัดสินก่อนเขียน 0020:** แกนหลักคือ `category → item` (ตามที่ร้านใช้) และราคาต่อรุ่นรถ
เป็นชั้น*ทางเลือก*ที่ทับลงไปเมื่อมีเท่านั้น — ไม่ใช่สลับกัน

---

## 4. ช่องว่างที่ 3 — **ไม่มีการรับประกันบนบรรทัด**

`quotation_items` ของจริงมี `warranty_name`, `warranty_year`, `warranty_month`, `warranty_km`
และ `service_items.warranty_id` เป็นต้นทาง (แร็ค OEM = ประกัน 1 ปี / แร็คมือสอง = อีกแบบ)

แผน P3.1 **ไม่พูดถึงการรับประกันเลยสักคำ**

นี่คือข้อมูลที่ต้อง snapshot ลงบรรทัดตอนเสนอราคา เพราะเงื่อนไขประกันเปลี่ยนได้ แต่ของที่ขายไปแล้ว
ต้องคงเงื่อนไข ณ วันขาย — และระบบใหม่มีตาราง `warranties` กับหน้าจอ `WarrantyPage` รออยู่แล้ว
**ถ้าบรรทัดใบเสนอราคาไม่เก็บประกัน โมดูลประกันจะไม่มีต้นทางข้อมูลตลอดไป**

## 5. ข้อเล็กที่ควรแก้ด้วย

| # | เรื่อง |
|---|---|
| 5.1 | **แก้ราคากลางที่ตั้งผิดไม่ได้** — มี `POST /price-book/entries` (เขียนครั้งแรก) แต่ไม่มีทางแก้ ถ้าพนักงานพิมพ์ 1,842 แทน 18,420 ราคานั้นจะติดถาวร ต้องมีหน้าจอ/endpoint แก้ไข เฉพาะ manager ขึ้นไป + audit |
| 5.2 | **กด "ยืนยันผลลูกค้า" ผิดแล้วถอยไม่ได้** แผนบอกให้ออก revision ใหม่เสมอ — แต่เลขเอกสารจองตอน `issued` ไม่ใช่ `signed` ดังนั้นถอย `signed→issued` ไม่ได้ทำให้เลขเสีย **ควรมีปุ่มถอยแบบเดียวกับ "ย้อน ส่งแล้ว" ที่เพิ่งทำไป** เงื่อนไข: วันเดียวกัน + งานยังไม่เลยสถานะ "อนุมัติ" + เข้า audit · บังคับออก revision ทุกครั้งที่กดผิด จะได้ revision ขยะเต็มระบบ ซึ่งแย่กว่าการถอยที่บันทึกไว้ |
| 5.3 | **`vehicle_offered_items` ไม่ได้ต่อสาย** แผนระบุว่าตารางนี้มีอยู่แล้ว แต่ไม่บอกว่าเขียนเมื่อไหร่ ถ้าปฏิเสธด้วยเหตุผล `next_time` ต้องเขียนลงตารางนี้ เพื่อให้ครั้งหน้าเสนอซ้ำได้ — ไม่ทำตอนนี้จะไม่มีใครกลับมาทำ |
| 5.4 | **ส่วนลด** แผนกำหนดให้เป็นช่องระดับเอกสาร แต่ของจริง `ส่วนลด` ถูกพิมพ์เป็น**บรรทัด 83 ครั้ง** — ตัดสินใจระดับเอกสารใช้ได้ แต่**ต้องพิมพ์ออกมาเป็นบรรทัดบนเอกสาร** ไม่ใช่ซ่อนอยู่ในยอดรวม ลูกค้าต้องเห็นว่าลดให้เท่าไหร่ |
| 5.5 | **`products.product_id` ไม่เคยถูกใช้** — ใบเสนอราคาจริง 2,423 บรรทัด ผูกกับ `products` **0 บรรทัด (0%)** พนักงานพิมพ์ชื่อเองทุกครั้ง นี่เป็นหลักฐานอีกชิ้นว่าแคตตาล็อกที่ผูกไม่ได้ จะไม่ถูกใช้ ระบบใหม่ต้องทำให้การ*เลือก*เร็วกว่าการ*พิมพ์* ไม่งั้นผลเดิม |
| 5.6 | ชื่อสถานะ `signed` ใช้แทน "ลูกค้ายืนยันผล" ทั้งที่ไม่มีลายเซ็นแล้ว (เราตัดออกไป) — ยอมรับเหตุผลเรื่องไม่อยากแก้ CHECK + partial index พร้อมกัน **แต่ต้องเขียนคอมเมนต์กำกับในไฟล์ migration** ว่าทำไมชื่อไม่ตรงความหมาย |
| 5.7 | ความเสี่ยงข้อ 3 (ยังไม่จองสต๊อกตอนอนุมัติ) แผนบอกจะ "บันทึกไว้ใน commit message" — **ไม่พอ** commit message คือที่ที่ของหาย ให้ใส่เป็นรายการในขอบเขต WO-006 สต๊อกโดยตรง |

## 6. สิ่งที่อนุมัติแล้ว ไม่ต้องแก้

- การใช้ schema เดิม (`documents`, `document_lines`, `allocate_document_number`, revision chain) — ถูกต้อง
- จุด freeze `issued → ล็อกบรรทัดเหลือแค่ช่องตัดสินใจ → signed → ล็อกหมด` บังคับด้วย trigger ไม่ใช่ซ่อนปุ่ม — ถูกต้อง
- 0022 เป็นไฟล์เสี่ยงสุด ต้องมีเทส integration คุม superseded/void — ถูกต้อง
- แผนวัด index ด้วย `EXPLAIN (ANALYZE, BUFFERS)` ในฐานะ `gsms_app` ใต้ RLS — ถูกต้อง และละเอียดกว่าที่ผมสั่ง
- การแบ่งงาน/ผู้รีวิวตาม §14 และ commit แยก 3 ก้อน — ถูกต้อง
- `GET work-order` ไม่มีราคา — ถูกต้อง
- ไม่ยกบั๊กต้นแบบมา (float, DELETE+INSERT, ปุ่มที่ไม่ถูกบันทึก) — จับได้ดี

## 7. ต้องทำอะไรต่อ

**ยังไม่เขียนโค้ด** กลับไปแก้แผนให้ครอบคลุม 3 ข้อใหญ่ + 7 ข้อเล็ก แล้วส่งกลับมาตรวจอีกรอบ

ก่อนแก้ ให้ไปอ่านของจริงเพิ่ม 3 ตาราง ที่รอบแรกยังไม่ได้ดู:
```
service_items (265)  ·  service_item_components (45)  ·  products (1,403)
```
และดู **เนื้อหา** ของ `quotation_items` 2,423 บรรทัด ไม่ใช่แค่โครงตาราง —
วิธีที่ร้านขายจริงอยู่ในข้อมูล ไม่ได้อยู่ในชื่อคอลัมน์
