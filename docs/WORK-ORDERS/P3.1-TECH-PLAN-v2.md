## 1. ข้อเท็จจริงจากข้อมูล production (dump 16 ก.ย. 2026)

### 1.1 ราคาขาย — **ไม่มีตารางราคาขายที่ใช้งานจริงเลย**

ข้อนี้แก้ทั้งฉบับแรกของทีม ("ราคาว่างเปล่า") และ `P3.1-REVIEW-COWORK.md` §1 ("ราคาจริงอยู่ใน `products`")

| ตาราง | แถว | ข้อเท็จจริง |
|---|---|---|
| `quote_part_prices` | 71,558 | มีราคา > 0 แค่ **1 แถว** — เป็นโครงเปล่า |
| `products` | 1,403 | มี `price` 97.9% แต่**เป็นต้นทุน ไม่ใช่ราคาขาย** — อยู่หน้า `/product-costs` จำกัดสิทธิ์ `requireRole("office")` และโค้ดต้นแบบเขียนไว้ว่าตารางนี้ "isn't kept in sync with what's actually sold" จึงตั้งใจไม่ใช้ตอนเสนอราคา |
| `service_items` | 265 | ชื่อ + หมวด + `is_set` + `warranty_id` · ไม่มีคอลัมน์ราคาขาย ยกเว้น `set_price` ของชุด (กรอกแค่ 1 จาก 7 ชุด) |
| `quotation_items` | 2,423 | พนักงาน**พิมพ์ราคาขายเองทุกบรรทัด** · ผูก `product_id` **0%** |

ผลต่อแผน:
- `products.price` **ไม่ใช้ในใบเสนอราคา ไม่นำเข้าในรอบนี้** และ advisor ต้องไม่เห็นเด็ดขาด (CLAUDE.md §12.2) — เป็นของ WO-006 (สต๊อก/ฝั่งซื้อ)
- ราคาขายเข้าระบบได้ทางเดียว คือ**ราคาแรกที่พนักงานพิมพ์ กลายเป็นราคากลาง** (คำตัดสินของ Ice) — วันแรกพนักงานพิมพ์ราคาเองเหมือนที่ทำอยู่ทุกวัน ไม่แย่กว่าระบบเก่า แล้วระบบจะดีขึ้นเรื่อย ๆ
- `service_items.set_price` ที่มีอยู่ (ถ้ามี) นำเข้าเป็น `base_price` ของชุดนั้นได้ เพราะเป็นราคาขาย

### 1.2 ชุด/แพ็กเกจ

- "ชุดโปรช่วงล่าง" ขายบ่อยที่สุดอันดับ 1 ของร้าน (148 ครั้ง)
- **974 / 2,423 บรรทัด (40%) ราคา 0** ทั้งหมดเป็นบรรทัดย่อยของชุด
- ต้นแบบเก็บชุดเป็น**แถวแบน ไม่มีอะไรผูกกัน**: แถวหัว (ราคาเต็ม) ตามด้วยแถว "- …" ราคา 0 ไม่มี parent_id ไม่มี marker
- 154 ชุด · บรรทัดย่อยเฉลี่ย 6.43 · 138 จาก 154 ชุดมีบรรทัดย่อย 6 บรรทัดพอดี
- ชุดอ้างอิง **"ชุดโปรช่วงล่าง"** = หัวชุด + ปีกนกล่าง L+R · ลูกหมากปีกนกล่าง L+R · ลูกหมากกันโคลง L+R · ลูกหมากคันชักนอก L+R · ยางรัดกันโคลง L+R · ประกอบติดตั้งรวมตั้งศูนย์
- **บั๊กเดิม ใบ #186:** โช้คสองยี่ห้อเป็นตัวเลือกให้ลูกค้าเทียบ (Showa 15,500 / Formula 12,000) แต่ถูกบวกเข้ายอดรวมทั้งคู่ — ปุ่ม "ปิดการใช้งานบรรทัด" ของต้นแบบไม่เคยถูกบันทึกจริง

### 1.3 การรับประกัน

- ใช้จริงแค่ 3 แบบ: "ลูกหมาก 1 ปี 100000 Km" (514) · "แร็ค 1 ปี 100000 Km" (73) · "รับประกันโช๊ค 1 ปี" (9)
- ต้นแบบคัดลอกประกันเป็นข้อความใน 4 จุดของโค้ด แต่ละจุดทำไม่เหมือนกัน และ **2 จุดทำประกันหายเฉย ๆ** (แผง A และตอน promote draft)

### 1.4 ส่วนลด

- 108 บรรทัด (ชื่อ "ส่วนลด" 83 + ชื่ออื่น 25) · เป็นจำนวนเงินทั้งหมด ไม่มีเปอร์เซ็นต์ · ไม่ผูกกับบรรทัดที่ลดให้
- เฉลี่ย 3.7% ของยอดรวม · สูงสุด 28.6%

### 1.5 บั๊กต้นแบบที่ห้ามยกมา

- เงินเป็น string และคำนวณด้วย float
- แก้ใบ = DELETE + INSERT บรรทัดทั้งหมด → id เปลี่ยนทุกครั้ง ประวัติหาย
- ปุ่มปิดบรรทัด (👁/🚫) ไม่ถูกบันทึก
- เหตุผลปฏิเสธมีแค่ระดับทั้งใบ

## 3. ข้อใหญ่ 1 — ชุด/แพ็กเกจ

### 3.1 ต้นทางในต้นแบบที่นำมาใช้
- `service_items.is_set` → `catalog_items.is_set`
- `service_items.set_price` → `catalog_items.base_price` ของชุด (ถ้ามี)
- `service_item_components (component_name, default_qty, sort_order)` → `catalog_set_components`

### 3.2 โครงสร้างในระบบใหม่
- `catalog_set_components (shop_id, set_item_id, component_item_id NULL, component_name, default_qty, sort_order)`
  - `component_item_id` ผูกกับรายการในแคตตาล็อกเมื่อจับคู่ได้ · ถ้าไม่ได้ใช้ `component_name` (ต้นแบบเก็บเป็นชื่อ)
  - ประกันของชิ้นย่อยมาจาก `component_item_id.warranty_id` ถ้ามี (§5)
- `document_lines.parent_line_id` → ชี้ไปบรรทัดแม่ใน**เอกสารเดียวกันเท่านั้น** บังคับด้วย FK + trigger

### 3.3 พฤติกรรม
1. พนักงานเลือกชุดจากช่องค้นหา (§7) → **server กางบรรทัดย่อยให้** ตาม `sort_order` ไม่ใช่ให้หน้าจอกางเอง
2. บรรทัดแม่มีราคาชุด (ราคาที่ดึงได้ตาม §4.3 หรือที่พนักงานพิมพ์) · บรรทัดย่อย `unit_price = 0`
3. **ยอดรวมคิดจากบรรทัดที่ไม่มี parent เท่านั้น** — ฟังก์ชันเดียวใน `packages/domain` ใช้ทั้งจอ ทั้งเอกสาร ทั้ง API · บรรทัดย่อยไม่ถูกนับ แม้ราคาไม่ใช่ 0
4. ตอนเป็นร่าง แก้หรือลบบรรทัดย่อยได้ · ลบบรรทัดแม่ = ลบทั้งชุด
5. **ลูกค้าตัดสินที่บรรทัดแม่** (D10) บรรทัดย่อยตามบรรทัดแม่เสมอ — API ไม่รับการตัดสินที่บรรทัดย่อย
6. ใบสั่งงานช่าง: ชุดที่อนุมัติแสดงทั้งบรรทัดแม่และบรรทัดย่อย (ช่างต้องเห็นว่าต้องทำอะไรบ้าง) ไม่มีราคา
7. **ปิดบั๊ก #186:** ตัวเลือกเทียบสองยี่ห้อคือสองบรรทัดแยกกัน ลูกค้าอนุมัติบรรทัดหนึ่ง และปฏิเสธอีกบรรทัดด้วยเหตุผล `chose_alternative` → ยอดที่อนุมัตินับแค่บรรทัดเดียว และมีเทสยืนยัน

## 4. ข้อใหญ่ 2 — แกนตารางราคา `category → item`

### 4.1 ตาราง (migration 0020)

| ตาราง | คอลัมน์หลัก | หน้าที่ |
|---|---|---|
| `catalog_items` | shop_id · category · name · `name_key` · line_type (part/labor/fee) · unit · default_qty · warranty_id · is_set · `base_price numeric(12,2) NULL` · is_active · legacy_source / legacy_id · created_by | รายการที่ร้านขาย แกนหลักคือหมวด → ชื่อ เหมือน `service_items` |
| `catalog_set_components` | ดู §3.2 | ชุดกางเป็นอะไร |
| `catalog_model_prices` | shop_id · item_id · brand_key · model_key · `price numeric(12,2) NOT NULL CHECK (price >= 0)` · set_by · set_at | **ชั้นเสริม** ราคาของรายการนั้นสำหรับรุ่นรถหนึ่ง ทับ base_price |

- `base_price` เป็น NULL ได้ = ยังไม่มีราคา (ไม่ใช่ 0 — ราคา 0 คือแจกฟรีที่ตั้งใจ)
- unique `(shop_id, category, name_key)` สำหรับรายการ · `(shop_id, item_id, brand_key, model_key)` สำหรับราคาต่อรุ่น · partial unique `(shop_id, legacy_source, legacy_id)` สำหรับการนำเข้า
- `price_key(text)` — ฟังก์ชัน normalise ตัวเดียว (ตัดช่องว่าง ตัวพิมพ์เล็กใหญ่ ขีด) ใช้กับยี่ห้อ รุ่น และชื่อรายการ ทั้งใน SQL และ domain ต้องให้ผลตรงกัน
- ทุกตารางเรียก `apply_tenant_rls` · แคตตาล็อกแยกต่อสาขา (WO-005 §5.3)
- index: ตัดสินจาก `EXPLAIN (ANALYZE, BUFFERS)` ในฐานะ `gsms_app` ใต้ RLS (`SET LOCAL app.current_shop_id`) บนข้อมูลจำลองขนาดของจริง — ประมาณ 300 รายการ · 154 ชุดแบบของจริง · ราคาต่อรุ่น 536 คู่ยี่ห้อ/รุ่น × รายการที่ขายบ่อย × 2 สาขา · ใส่ query ที่ใช้จริงและแผนที่ได้ไว้ในหัวไฟล์ migration (CLAUDE.md §11)

### 4.2 ข้อมูลตั้งต้น (ผ่าน WO-004 ไม่ใช่ในรอบนี้)
- `service_items` 265 แถว → `catalog_items` (หมวด · ชื่อ · ประเภท · ประกัน · is_set · set_price) — **ไม่มีราคารายชิ้น** เพราะต้นทางไม่มี
- `service_item_components` 45 แถว → `catalog_set_components`
- **ไม่นำเข้า** `quote_part_prices` (โครงเปล่า) และ `products.price` (ต้นทุน)
- ต้องแจ้งแก้ `IMPORT-FINDINGS.md` และ `WO-004` ตาม `P3.1-REVIEW-COWORK.md` §0 — เอกสารของ Cowork ทีมไม่แก้เอง
- dev / เทส ใช้ข้อมูลจำลอง

### 4.3 ลำดับการดึงราคา (ฟังก์ชันเดียวใน domain)
```
ราคาของรุ่นรถคันนี้ (catalog_model_prices ของยี่ห้อ/รุ่นของงานนี้)
  → base_price ของรายการ
    → ว่าง = พนักงานพิมพ์เอง
```
- ยี่ห้อ/รุ่นมาจาก**รถของงานนี้** ไม่ให้เลือกแยกอีกรอบเหมือน modal B ของต้นแบบ
- รถที่ไม่มียี่ห้อหรือรุ่น → ข้ามชั้นรุ่นไปใช้ base_price

### 4.4 การเขียนราคา — สอง endpoint แยกกันชัดเจน
| endpoint | ทำอะไร | ใคร | เงื่อนไข |
|---|---|---|---|

## 5. ข้อใหญ่ 3 — การรับประกันบนบรรทัด

### 5.1 ต้นทาง
`catalog_items.warranty_id` (มาจาก `service_items.warranty_id`) → ตาราง `warranties` ที่มีอยู่แล้วในระบบใหม่ (รอหน้าจอ `WarrantyPage`)

### 5.2 คอลัมน์บนบรรทัด (migration 0021)
`warranty_id` · `warranty_name` · `warranty_months` · `warranty_km` — ทั้งหมด nullable
- ต้นแบบเก็บเป็นปี + เดือน → ระบบใหม่เก็บเป็นจำนวนเดือนรวม (1 ปี = 12) แปลงตอนนำเข้า

### 5.3 กติกา
1. **มีฟังก์ชันเดียวที่ใส่ประกันลงบรรทัด** (`warrantySnapshotOf(item)` ใน domain ส่วน service ฝั่ง API เรียกใช้) — **ทุกเส้นทางที่สร้างบรรทัดต้องผ่านฟังก์ชันนี้:** เพิ่มรายการ · กางชุด (บรรทัดย่อยได้ประกันของตัวเอง) · เพิ่มจาก "เคยเสนอไว้" · คัดลอกตอนออก rev ใหม่ · บรรทัดพิมพ์อิสระ (ไม่มีประกัน เว้นแต่พนักงานเลือก)
2. snapshot **ณ วันเสนอราคา** — แก้เงื่อนไขประกันในตาราง `warranties` ภายหลัง บรรทัดที่ออกไปแล้วต้องไม่เปลี่ยน
3. ตอนเป็นร่าง พนักงานเปลี่ยนประกันของบรรทัดได้ (เลือกจากตาราง `warranties`) · หลังออกใบแล้วล็อกตาม 0022
4. **เทส:** ทุกเส้นทางในข้อ 1 ได้ประกันครบ · แก้ `warranties` แล้วบรรทัดเดิมไม่เปลี่ยน

## 6. วงจรชีวิตใบเสนอราคา และจุด freeze (แทนลายเซ็น)

```
draft    ไม่มีเลข · แก้ได้ทุกอย่าง
  │  ออกใบ  → จองเลข IV{YY}{MM}{DD}{SEQ:3} ด้วย allocate_document_number เดิม
issued   เนื้อหาบรรทัดถูกล็อก · บันทึกการตัดสินใจทีละบรรทัดได้ (อนุมัติ / ปฏิเสธ + เหตุผล)
         เปลี่ยนใจได้จนกว่าจะกดยืนยัน · แก้ส่วนลดได้ในจังหวะยืนยัน (D11)
  │  "ยืนยันผลลูกค้า"  ← ต้องตัดสินครบทุกบรรทัดแม่ก่อน
signed   FREEZE ทุกช่อง · งาน → "อนุมัติ" ถ้าอนุมัติ ≥ 1 (D4) · ถ้าปฏิเสธหมด งานค้างที่ "เสนอราคา" (D5)
  │  ถอยการยืนยัน (§8.2)  → issued  (วันเดียวกัน · งานยังเป็น "อนุมัติ" · เหตุผล · audit)
  │  ลูกค้าขอเพิ่ม/แก้  → ออก rev ใหม่ (D6) อ้างใบเดิม · ใบเดิม → superseded · คัดลอกผลการตัดสิน (D7)
superseded / void   แตะไม่ได้เลย
```

- **ชื่อสถานะ `signed` คงไว้** แม้จะไม่มีลายเซ็นแล้ว เพราะถ้าเปลี่ยนชื่อต้องแก้ CHECK และ partial index พร้อมกัน → เขียนคอมเมนต์อธิบายในไฟล์ 0022 (§8.6)
- **การเปลี่ยนพฤติกรรมเดิม:** ถอยงาน "อนุมัติ → เสนอราคา" จะได้ 409 เมื่อใบเสนอราคาเป็น `signed` (CLAUDE.md §5 ข้อ 5) → ต้องถอยการยืนยัน (§8.2) หรือออก rev ใหม่แทน
- สถานะงานเปลี่ยนใน transaction เดียวกับการยืนยัน/ถอยการยืนยัน

## 7. หน้าจอ — "เลือก" ต้องเร็วกว่า "พิมพ์" (§8.5)

ยก layout / ลำดับช่อง / ปุ่มจากแผง A (D14) แล้วสร้างส่วนต่อไปนี้ใหม่:

  1. ชุด (`is_set`)
  2. รายการที่ร้านขายบ่อย — นับจากบรรทัดใบเสนอราคาจริงของสาขา
  3. "เคยเสนอไว้" ของรถคันนี้ (§8.3)
- ใช้คีย์บอร์ดได้ล้วน: ลูกศรเลือก · Enter = เพิ่ม · ราคาขึ้นทันทีตาม §4.3
- พิมพ์ชื่อที่ไม่มีในแคตตาล็อกได้เสมอ → มีช่องติ๊ก "เพิ่มเข้าแคตตาล็อก" **ติ๊กไว้ให้แล้ว** (D12) พร้อมเลือกหมวดได้
- ราคาว่าง → ช่องราคาเด่นขึ้นมาให้พิมพ์ · พิมพ์แล้วบันทึกเป็นราคากลางของรุ่นนี้ (D8) พร้อมบอกพนักงานว่า "บันทึกเป็นราคากลางของ {รุ่น} แล้ว"
- แสดง**สองยอดเสมอ**: ยอดเสนอทั้งหมด และยอดที่อนุมัติ (CLAUDE.md §5.1 ข้อ 3) และบรรทัด "ส่วนลด" (§8.4)
- บรรทัดที่ปฏิเสธ**ยังอยู่บนจอและบนเอกสาร** พร้อมเหตุผล
- route ใหม่ `/jobs/:id/quote` เปิดจากการ์ดใน `/today` (หน้า JobDetailPage เดิมไม่ได้ route และจะไม่ฟื้น)
- เกตก่อนใช้งานจริง: ux-advocate **จับเวลา "ใส่ชุดโปรช่วงล่าง 1 ชุด"** เทียบกับระบบเก่า · ตรวจด้วยตาที่ 390 / 820 / 1180 / 1440px · หมุนจอ 820↔1180 ระหว่างกรอกค้างอยู่ ข้อมูลต้องไม่หาย

## 9. Migration

ทุกไฟล์มีหัว WHAT / WHY / ROLLBACK / LOCKS · ผ่าน migration-safety ได้ GO/NO-GO ก่อนรัน · แนบผล `verify-rls.sql` · ห้ามแก้ไฟล์ที่รันไปแล้ว

### 0020_catalog.sql
- `price_key()` · `catalog_items` · `catalog_set_components` · `catalog_model_prices` (§4.1) · `apply_tenant_rls` ทุกตาราง
- เงิน `numeric(12,2)` · `CHECK (price >= 0)`
- rollback: DROP 3 ตาราง + ฟังก์ชัน (ยังไม่มีข้อมูลจริงในวันที่ deploy — export ก่อนถ้ามี)

### 0021_quote_lines.sql
- `document_lines` เพิ่มคอลัมน์: `parent_line_id` (FK ไปเอกสารเดียวกัน) · `catalog_item_id` · `list_price` · `price_source` · `price_ref_id` · `decided_by` · `warranty_id` · `warranty_name` · `warranty_months` · `warranty_km` — ทั้งหมด nullable · ADD COLUMN แบบไม่มี default จึงแก้แค่ catalog ล็อกตารางชั่วครู่
- `decline_reason` เพิ่มค่า `chose_alternative` (D13) — แก้ CHECK เดิมแบบ `NOT VALID` แล้วค่อย `VALIDATE`
- rollback: DROP คอลัมน์ (export ก่อน) · คืน CHECK เดิม (ถ้ามีแถวที่ใช้ `chose_alternative` แล้ว ต้องตัดสินก่อน rollback)

### 0022_quote_freeze.sql — **ไฟล์ที่เสี่ยงที่สุด**
- `documents_are_immutable()`:
  - draft → แก้ได้
  - issued → แก้ได้เฉพาะ `approved_total` · `discount` · และคอลัมน์ของการเปลี่ยน issued → signed
  - signed → ได้เฉพาะ signed → issued (คอลัมน์สถานะ) และ → superseded
  - superseded / void → แตะไม่ได้
  - **คงทุกกิ่งเดิมของ 0011 ไว้** (ทางออกไป void/superseded โดย type/number/grand_total ไม่เปลี่ยน · ห้ามแก้เอกสาร superseded/void) — ต้องแนบ diff เทียบ 0011 ทีละกิ่ง
- `document_lines_are_immutable()` (ใหม่ · UPDATE / DELETE / INSERT):
  - parent draft → ได้หมด
  - parent issued → แก้ได้เฉพาะ `approval_status` · `decided_at` · `decided_by` · `decline_reason` · `decline_note`
  - parent signed / superseded / void → ไม่ได้เลย
  - ห้ามย้ายบรรทัดไปเอกสารอื่น · `parent_line_id` ห้ามเปลี่ยนหลังร่าง
- `RAISE … USING ERRCODE = 'GS002'` (ลงทะเบียนแล้วใน CLAUDE.md §9.1) · API map ด้วย `err.code` เท่านั้น → 409
- คอมเมนต์เรื่องชื่อ `signed` (§8.6)
- rollback: คืนฟังก์ชันของ 0011 ตามต้นฉบับ + DROP trigger/ฟังก์ชันใหม่
- **ช่องโหว่ที่ปิดไปด้วย:** วันนี้บรรทัดของเอกสารที่ออกเลขแล้วยังแก้ได้
