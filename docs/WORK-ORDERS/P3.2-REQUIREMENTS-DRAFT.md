# P3.2 — Requirements (DRAFT รอ Ice รีวิว)

16 ต.ค. 2026 · product-analyst · สถานะ: **ร่าง ยังไม่ผ่านการอนุมัติ — ห้ามเริ่มออกแบบ/เขียนโค้ดจนกว่า Ice ตอบคำถามในหัวข้อ 9**
ขอบเขตเอกสารนี้: นิยามปัญหาและเงื่อนไขความสำเร็จ ไม่ใช่การออกแบบ ไม่เลือกเทคโนโลยี (ที่เขียนว่า "ให้ architect ตัดสิน" คือการส่งต่า ไม่ใช่ข้อสรุป)

---

## 0. สรุปหนึ่งหน้า

**ปัญหาที่แก้จริง ๆ:** ตอนนี้ระบบใหม่ทำได้ถึง "ลูกค้ายืนยันผลใบเสนอราคา" แล้วจบ — ยังเก็บเงินไม่ได้ ออกใบเสร็จไม่ได้ พิมพ์ไม่ได้ ทำให้ร้าน **ใช้เป็นระบบหลักไม่ได้** (เป้า ~24 ต.ค.) และมีสองเรื่องที่ DECISION ผูกไว้กับ P3.2 โดยตรง: (1) กระดาษ A4 ที่ลูกค้าเซ็นคือตัวควบคุมแทนลายเซ็นบนจอ (DECISION-2026-10-07 §2.3) (2) เพดานส่วนลด 40% (DECISION-2026-10-07 §2.2)

**ผลลัพธ์ที่ต้องได้เมื่อจบ P3.2:** พนักงานหน้าร้านเปิดงานที่ลูกค้าอนุมัติแล้ว → พิมพ์ใบสั่งงานให้ช่าง → งานเสร็จ ติ๊กทีละบรรทัดว่าทำจริงไหม → ระบบคิดยอดที่ต้องเก็บ → รับเงิน (ช่องทาง/ยอดรับ/เงินทอน) → ปิดบิลและออกใบเสร็จใน transaction เดียว → พิมพ์ A4 สองชุด → เจ้าของเปิด "สรุปรายวัน" เห็นเงินเข้า กับยอดขาย เป็นสองตัวเลขแยกกัน และนับเงินสดในลิ้นชักเทียบได้

**ข้อค้นพบสำคัญ 6 ข้อ (รายละเอียดหัวข้อ 7):**
1. `fulfilled_qty` เขียนบนบรรทัดของใบเสนอราคาที่ confirm แล้วไม่ได้ — trigger 0022 ล็อกบรรทัดไว้หมด ที่เก็บการติ๊กต้องเป็นเอกสารใบเสร็จ (draft) ของตัวเอง
2. "ห้ามจ่ายขาด" ชนกับ "ยังไม่มีมัดจำจนกว่า P3.3" — งานที่ลูกค้าวางมัดจำไว้แล้วจะปิดบิลไม่ได้ในช่วงนี้
3. ส่วนลดที่ตกลงไว้ตอน confirm แล้วถูกยกมาเงียบ ๆ เป็นช่องหลบเพดาน 40% (advisor ไม่ต้องแก้อะไรเลยก็ปิดบิลลด 60% ได้) ถ้าเพดานคุมเฉพาะ "ตอนแก้"
4. `delivered` กับ `ใบเสร็จ` ใครมาก่อนกัน ยังไม่เคยตัดสิน — กระทบ warranty (0010 สร้างประกันตอน `delivered` จากบรรทัดที่ fulfilled) และกระทบ flow รับรถ→ส่งรถ ที่ร้านใช้ทุกวัน
5. ต้นแบบ **ไม่ได้ใช้ Puppeteer** (ใช้ React template + `window.print()`) ขัดกับ WO-005/PLAYBOOK ที่บอกให้ "ยก Puppeteer มา" และ `afterprint` บอกไม่ได้ว่าพิมพ์จริงหรือกดยกเลิก — กระทบ "พิมพ์ครั้งที่ N"
6. การพิมพ์ **ใบเสนอราคา** ไม่อยู่ในรายการที่สั่งมา แต่ DECISION-2026-10-07 §2.3 และ DECISION-2026-10-15 §2 ผูกไว้กับ P3.2 — ต้องอยู่ในขอบเขต (หัวข้อ 4)

## 3. พจนานุกรม — คำที่ต้องใช้ตรงกันทุกที่ (pin แล้ว รอ Ice ยืนยัน)

> ทุกคำที่ติด ⚠ มีข้อขัดแย้งในเอกสารต้นทาง ดูหัวข้อ 7

| คำ | นิยามที่ใช้ใน P3.2 | ห้ามใช้ปนกับ |
|---|---|---|
| **ใบสั่งงาน / ใบแจ้งซ่อม** ⚠ | มุมมองอ่านอย่างเดียวของ "บรรทัดที่ approved" สำหรับช่าง ไม่มีราคา. ในเอกสารต่าง ๆ ถูกเรียกทั้ง "ใบสั่งงาน" (PLAYBOOK) "ใบแจ้งซ่อม" (CLAUDE.md §5, series `WO`) "ใบงาน" (WO-005 §2 แต่หมายถึงเลขงาน `JB-`) → ใน P3.2 ใช้ **"ใบสั่งงาน" = เอกสารพิมพ์นี้** และ **"เลขงาน" = `jobs.job_number` (`JB-…`)** | "ใบงาน" |
| **ใบเสร็จ (receipt)** | เอกสารชนิด `receipt` ที่ออกเลข `REC` แล้ว เป็น snapshot ของ: บรรทัดที่ทำจริง + ส่วนลดสุดท้าย + ยอดสุทธิ + (ในใบเดียวกัน) การรับเงิน. **ไม่ใช่ใบกำกับภาษี** | ใบกำกับภาษี, ใบรับเงินมัดจำ |
| **ปิดบิล (close bill)** | การกระทำเดียวที่ทำ 3 อย่างใน transaction เดียว: บันทึกการรับเงิน + ออกเลขและ issue ใบเสร็จ + บันทึกบรรทัดที่ทำจริง/คืนของที่ไม่ได้ทำ. สำเร็จทั้งหมดหรือไม่สำเร็จเลย | "ส่งรถ" (`delivered` เป็นสถานะงาน ไม่ใช่การปิดบิล), "ปิดงาน" |
| **บิล** | ภาษาพนักงาน = ใบเสร็จที่ออก/ที่กำลังจะออก ของงานหนึ่งงาน. ในระบบไม่มีเอนทิตี "บิล" แยก — ห้ามสร้างสถานะ "บิลเปิด" ที่ไม่มีใบเสร็จ (CLAUDE.md §5.3 ข้อ 6) | "ใบเสนอราคา" ที่ต้นแบบเรียก `quotation` แล้ว convert เป็น receipt |
| **ยอดเสนอ** | `offered_total` / `grand_total` ของ**ใบเสนอราคา** (ค้างไว้ไม่ขยับ) | ยอดที่ลูกค้าจ่าย |
| **ยอดที่ตกลง** | `approved_total` ของใบเสนอราคา ณ ตอน confirm ( = Σ บรรทัดที่ approved − ส่วนลดที่ตกลง) | ยอดที่ลูกค้าจ่ายจริง (อาจต่างถ้ามีบรรทัดไม่ได้ทำ) |
| **ยอดที่ลูกค้าต้องจ่าย (amount due)** ⚠ | บน**ใบเสร็จ**: `Σ(ราคาบรรทัดที่ทำจริง) − ส่วนลดสุดท้าย`. P3.3 จะมี "หักมัดจำ" เพิ่มจึงต้องแยก: **ยอดบิล (bill total)** = ก่อนหักมัดจำ; **ยอดคงเหลือชำระ (balance due)** = ยอดบิล − มัดจำที่หัก. ใน P3.2 ไม่มีมัดจำ → สองตัวเท่ากัน แต่ต้องแยกชื่อใน API/จอ/พิมพ์ตั้งแต่ตอนนี้. ใน schema ใบเสร็จ `grand_total` ควรแปลว่า **ยอดบิล** (แต่ในใบเสนอราคา `grand_total` แปลว่ายอดเสนอ — ชื่อคอลัมน์เดียวความหมายต่างตามชนิดเอกสาร = กับดัก ให้ architect ตัดสินว่าจะจัดการอย่างไร) | `grand_total` ของใบเสนอราคา |
| **ทำจริง (fulfilled)** ⚠ | ต่อบรรทัดที่ approved: ค่า `fulfilled_qty` ที่พนักงาน**เลือกเอง** ในช่วง `0 ≤ fulfilled_qty ≤ qty ที่อนุมัติ`. ทำครบ = เท่า qty, ทำบางส่วน = ระหว่าง, ไม่ได้ทำ = 0. **ไม่มีค่าเริ่มต้นที่ติ๊กไว้ให้** (§5.1 ข้อ 7 "ห้ามข้ามขั้น"). ราคาบรรทัดบนใบเสร็จ = `unit_price × fulfilled_qty` ปัดต่อบรรทัด. เกิน qty ที่อนุมัติ = ไม่ได้ (ต้องออกใบเสนอราคา rev ใหม่ §5.1 ข้อ 8). ชุด (set): ดูคำถาม B5 | "อนุมัติ" (approved = ลูกค้าตกลง; fulfilled = ร้านทำ) |
| **ส่วนลดที่เสนอ** | `offered_discount` บนใบเสนอราคา (ค้างไว้) | |
| **ส่วนลดที่ตกลง** | `documents.discount` ของใบเสนอราคาหลัง confirm (อาจถูกกรอกใหม่ตอน confirm ตาม DECISION-2026-10-15 §1) | |
| **ส่วนลดใบเสร็จ (receipt discount)** ⚠ | ส่วนลดสุดท้ายที่พิมพ์บนใบเสร็จ. **เป็นค่าของใบเสร็จเอง** ไม่ใช่การแก้ใบเสนอราคา. เริ่มต้นจาก "ส่วนลดที่ตกลง" ได้เฉพาะกรณีที่ยอดทำจริง = ยอดที่อนุมัติ (ดู AC-C2) แต่ไม่ว่าจะมาจากไหน **เพดาน 40% วัดที่ค่าสุดท้ายนี้** | "ส่วนลดที่ตกลง" |
| **ฐานของ 40%** ⚠ | `ส่วนลดใบเสร็จ ÷ ยอดรวมก่อนลดของบรรทัดที่ทำจริง` (รวมทุก `line_type` — ของ ค่าแรง ค่าบริการ) เทียบด้วยสตางค์จำนวนเต็ม: `ส่วนลด×100 ≤ 40×ฐาน` = advisor ได้ (พอดี 40.00% ผ่าน). "ยอดรวม" ใน DECISION-2026-10-07 ไม่ได้ระบุว่าก่อนหรือหลังลด → เลือก **ก่อนลด** เพราะหลังลดทำให้ 40% ของฐานเปลี่ยนตามส่วนลดเอง. ถ้า Ice หมายถึงฐานแบบอื่น ให้แก้ที่นี่ที่เดียว | |
| **วันที่ (รายวัน)** ⚠ | วันตามปฏิทิน **Asia/Bangkok** (`business_date`). **เงินเข้า** ใช้วันของ `payments.received_at`; **ยอดขาย** ใช้วันที่**ปิดบิล** = วันของ `documents.issued_at` ของใบเสร็จ. ไม่ใช่วัน `delivered`, ไม่ใช่ `receipt_date` ที่พนักงานแก้ได้แบบต้นแบบ (ใน P3.2 **ไม่มีช่องให้เลือกวันย้อนหลัง** — ดู A-3). WO-005 §4 เขียนว่ายอดขาย "นับจากวันที่ปิดงาน" ซึ่งอาจตีความเป็น `delivered`; CLAUDE.md §5.4 ข้อ 9 เขียน "วันที่ปิดบิล" → ใช้ตามหลัง | |
| **เงินเข้าวันนี้** | Σ (`amount − change_given`) ของ `payments` ที่ `received_at` ตกวันนั้น, **ไม่รวมแถว `deposit_offset`** (เงินก้อนนั้นนับไปแล้วตอนรับมัดจำ) และไม่รวมของใบเสร็จที่ void ตามหัวข้อ A-5 | ยอดขาย |
| **ยอดขายวันนี้** | Σ ยอดบิล (bill total) ของใบเสร็จสถานะ `issued` ที่ปิดบิลวันนั้น ไม่รวม void ไม่รวมงานเคลม (ไม่มีใบเสร็จอยู่แล้ว) ไม่รวมเงินริบมัดจำ (P3.3 แยกประเภท) | เงินเข้า |
| **พิมพ์ครั้งที่ N** | N = จำนวนครั้งที่ระบบ**สร้างผลพิมพ์** (print action) ของเอกสารนั้น นับรวมครั้งนี้. หนึ่ง action ที่ออก 2 ชุด (ลูกค้า/ร้าน) = 1 ครั้ง ทั้งสองชุดแสดง N เดียวกัน. เลขบนกระดาษต้องเท่ากับจำนวนแถวในประวัติ ณ ตอนนั้น | |

## 4. ขอบเขต

### อยู่ใน P3.2
1. **ใบสั่งงาน** พิมพ์ A4 (ไม่มีราคา, ช่างเห็นได้)
2. **ใบเสนอราคา พิมพ์ A4** — *ไม่อยู่ในรายการที่สั่งมา แต่ต้องมี:* DECISION-2026-10-07 §2.3 ระบุว่า "การพิมพ์ A4 มาพร้อม P3.2" เป็นตัวควบคุมแทนลายเซ็นบนจอ และ DECISION-2026-10-15 §2 ผูก "พิมพ์ครั้งที่ N" กับกรณีถอยการยืนยันหลังพิมพ์ ซึ่งเกิดกับใบเสนอราคา ไม่ใช่ใบเสร็จ. **ถ้า Ice ตั้งใจตัด ต้องบอก** ไม่งั้นช่องว่างที่ DECISION-2026-10-07 เขียนไว้ ("ใบเสนอราคาจากระบบใหม่ยังพิมพ์ไม่ได้") จะไม่ปิด

## 5. User stories และ Acceptance Criteria

> รูปแบบ Given/When/Then. ตัวเลขทั้งหมดเป็นบาท, คำนวณที่ชั้น domain เป็นสตางค์จำนวนเต็ม (§4 ข้อ 2). ทุก AC ต้องเทสผ่าน **API ตรง** ด้วย (ไม่ใช่แค่ปุ่มที่ซ่อน) และทุกกลุ่มต้องมีเทส 2 ร้าน (§8 ข้อ 6, §13)

### A. ใบสั่งงาน (พิมพ์ อ่านอย่างเดียว)

**Story A1:** As a `technician`, I want to hold a printed sheet of exactly what I must do on this car, so that I do not do (or order parts for) anything the customer declined.
**Story A2:** As an `advisor`, I want to print the work order the moment the quotation is confirmed, so that the shop floor starts without waiting for me to copy anything.

- **AC-A1** Given ใบเสนอราคายืนยันผลแล้ว มี 4 บรรทัดระดับบน (อนุมัติ 2, ปฏิเสธ 2) / When พิมพ์ใบสั่งงาน / Then กระดาษมี **2 บรรทัดเท่านั้น**, ไม่มีบรรทัดที่ปฏิเสธ, **ไม่มีตัวเลขเงินใด ๆ** (ไม่มีราคา ส่วนลด ยอดรวม) และ API response ก็ไม่มีฟิลด์เงิน (ไม่ใช่แค่ซ่อนตอนพิมพ์)
- **AC-A2** Given ใบเสนอราคายังไม่ยืนยัน / When ขอใบสั่งงาน / Then 409 `quotation_not_confirmed`; ไม่มีใบ → 409 `quotation_missing`; ปฏิเสธทุกบรรทัด → 200 รายการว่าง และปุ่มพิมพ์แสดง "ไม่มีรายการที่ต้องทำ" (พฤติกรรม P3.1 คงเดิม ห้ามพัง)
- **AC-A3** Given ลูกค้าอนุมัติเพิ่มระหว่างซ่อม (ใบเสนอราคา rev 2 ยืนยันแล้ว) / When พิมพ์ใบสั่งงานอีกครั้ง / Then เห็นบรรทัดของ rev 2, ประวัติการพิมพ์ระบุว่าพิมพ์จาก rev ไหน, และคำเตือนพิมพ์ซ้ำ (AC-G5) ขึ้น เพราะเนื้อหาเปลี่ยน
- **AC-A4** ใบสั่งงานมีเลขงาน (`JB-…`) ชื่อ/ทะเบียนรถ ยี่ห้อ/รุ่น ชื่อบรรทัด จำนวน หน่วย ชื่อประกัน. บรรทัดที่ `shortfall` (รออะไหล่ — มีเมื่อ WO-006 พร้อม) ต้องขึ้น "รออะไหล่" (§6 ข้อ 6) — ถ้า WO-006 ยังไม่มา ยกเว้นได้ ให้บันทึกเป็นเงื่อนไขของเกต
- **AC-A5** ใบสั่งงาน**ไม่ออกเลขเอกสาร `WO`** และไม่ใช้ลำดับเลข (assumption A-4) — พิมพ์กี่ครั้งก็ไม่กินเลข
- **AC-A6** สิทธิ์: ดูตาราง 5-J

### B. ติ๊กทำจริงทีละบรรทัด (`fulfilled_qty`)

**Story B1:** As an `advisor`, I want to confirm line by line what was really done before billing, so that the customer is charged only for work done and unused parts return to stock.

- **AC-B1** Given งานสถานะที่ออกใบเสร็จได้ (ดูคำถาม B1) และใบเสนอราคาที่ยืนยันแล้ว / When เปิดหน้าปิดบิล / Then แสดง**ทุกบรรทัดระดับบนที่ `approved`** (และไม่แสดง declined ในรายการติ๊ก) ทุกบรรทัดอยู่สถานะ "ยังไม่ระบุ" และปุ่ม "ออกใบเสร็จ" **กดไม่ได้**จนกว่าทุกบรรทัดจะถูกเลือก (ทำครบ / ทำบางส่วน+จำนวน / ไม่ได้ทำ)
- **AC-B2** Given ยังมีบรรทัดไม่ระบุ / When ยิง API ปิดบิลตรง ๆ / Then 409 `fulfillment_incomplete` พร้อมรายการบรรทัดที่ขาด (ไม่ใช่ซ่อนปุ่มอย่างเดียว)
- **AC-B3** Given บรรทัด qty 4 / When เลือกทำบางส่วน = 3 / Then ราคาบรรทัด = `unit_price × 3` (ปัดต่อบรรทัด), ส่วนที่เหลือ 1 ถูกคืนจอง (AC-H1); fulfilled_qty = 5 หรือ −1 หรือไม่ใช่ตัวเลข → 400 พร้อม field error (ด่านหน้า CHECK, §4.y)
- **AC-B4** บรรทัดที่ไม่ได้ทำ (0) → ไม่คิดเงิน, **ยังคงอยู่บนใบเสร็จเป็นบรรทัด "อนุมัติแต่ไม่ได้ทำ — ไม่คิดเงิน"** (assumption A-6; เหตุผล: เหมือนเหตุผลที่ declined ต้องไม่ถูกซ่อน — ตรวจสอบย้อนหลังได้ทั้งสองฝ่าย) และต้องไม่ถูกส่งไปสร้างประกันใน 0010
- **AC-B5** ทุกการเลือกบันทึก `fulfilled_by` / `fulfilled_at` (คอลัมน์มีแล้วใน 0010)
- **AC-B6** ทางลัด "ทำครบทุกบรรทัด": ถ้ามี (assumption A-7) ต้องเป็นการกดของพนักงานที่ **เขียนค่าชัดเจนลงทุกบรรทัด** ไม่ใช่ค่า default; ไม่มีปุ่มนี้ได้ถ้า Ice ไม่ต้องการ
- **AC-B7** ผลการติ๊กต้อง**ไม่แก้บรรทัดของใบเสนอราคาที่ยืนยันแล้ว** (trigger 0022 จะปฏิเสธอยู่แล้ว — เป็นข้อจำกัดที่ตั้งใจ ดู C1). ผลการติ๊กต้อง**คงอยู่ข้ามการรีเฟรช/หมุนจอ/สลับคน** (พนักงานติ๊กครึ่งหนึ่งแล้วไปทำอย่างอื่นได้) จนกว่าจะปิดบิล
- **AC-B8** ถ้ามีการออกใบเสนอราคา rev ใหม่ที่ยืนยันแล้วหลังเริ่มติ๊ก → การติ๊กเดิมต้องไม่ถูกนำไปคิดเงินเงียบ ๆ กับบรรทัดผิดชุด: ต้องแจ้งเตือนและให้ติ๊กใหม่สำหรับบรรทัดที่เปลี่ยน (ผูกด้วย `source_line_id`)
- **AC-B9** ใบเสนอราคาล่าสุดมี rev ที่ยัง**ไม่ยืนยัน** (ลูกค้ากำลังตัดสินงานเพิ่ม) → ปิดบิลไม่ได้ 409 `revision_pending` (assumption A-9) ไม่งั้นงานเพิ่มจะหลุดจากบิล

### C. ยอดใบเสร็จและส่วนลด

**Story C1:** As an `advisor`, I want the system to show exactly what the customer owes for what was actually done, so that I never type a total by hand.
**Story C2:** As an `owner`, I want any discount above 40% to need a manager and a written reason, so that a bill cannot be quietly zeroed (DECISION-2026-10-07 §2.2).

- **AC-C1 (invariant)** Given ทุกบรรทัดที่ approved ถูกเลือก "ทำครบ" และส่วนลดใบเสร็จ = ส่วนลดที่ตกลง / Then ยอดบิลบนใบเสร็จ **เท่ากับ `approved_total` ของใบเสนอราคาเป๊ะ** ทุกกรณีรวมชุดที่ตัดบางชิ้น (`approved_amount`). ใบเสร็จอ่านจาก `approved_total`/ข้อมูลที่ตกลง **ห้ามอ่าน `grand_total` ของใบเสนอราคา** (นั่นคือยอดเสนอ)
- **AC-C2 (ส่วนลดตกลงที่ยกมา)** ตัวอย่าง: อนุมัติ A 3,000 + B 2,000 = 5,000, ส่วนลดที่ตกลง 500 (10%).
  - ทำครบทั้งคู่ → ช่องส่วนลดใบเสร็จขึ้นค่า 500 (ให้อ่านและคงไว้ได้ พร้อมข้อความ "ส่วนลดที่ตกลงไว้")
  - B ไม่ได้ทำ → ฐาน 3,000, ส่วนลดที่ตกลง 500 (16.7%) → ช่องส่วนลด **ว่าง ไม่เติมค่าให้** และ**ออกใบเสร็จไม่ได้จนกว่าพนักงานกรอกเอง** (ขยายหลักเดียวกับ DECISION-2026-10-15 §1; แสดง "ส่วนลดที่ตกลงไว้ 500 บนฐาน 5,000 · ฐานตอนนี้ 3,000" เป็นข้อมูลอ้างอิง). กรอก 0 ได้
  - ส่วนลดใบเสร็จ > ฐาน → 400 `discount_exceeds_subtotal` (ไม่ใช่ปล่อยให้ clamp เป็นบิล 0 เงียบ ๆ)
- **AC-C3 (เพดาน 40% — ค่าสุดท้ายเสมอ)** ฐาน 3,000: ส่วนลด 1,200.00 (40.00%) → `advisor` ทำได้; 1,200.01 → ต้อง `manager` ขึ้นไป + เหตุผลบังคับ (ข้อความอิสระ ไม่ใช่ dropdown อย่างเดียว); 1,300 → เช่นกัน
- **AC-C4 (กันช่องหลบ)** Given ส่วนลดที่ตกลงตอน confirm = 60% ของฐาน และทำครบทุกบรรทัด (พนักงานไม่แตะช่องส่วนลดเลย) / When `advisor` ปิดบิล / Then **ปิดไม่ได้** 403 `discount_requires_manager` — เพดานตรวจที่ค่าสุดท้ายบนใบเสร็จ ไม่ว่าใครตั้งหรือตั้งตอนไหน. (นี่คือเหตุที่ต้องตอบคำถาม B4: ควรมีเพดานเดียวกันที่ตอน confirm ใบเสนอราคาด้วยหรือไม่)
- **AC-C5** การอนุมัติโดย `manager`+ บันทึก audit: ใคร ส่วนลดเท่าไหร่ ฐานเท่าไหร่ เปอร์เซ็นต์ เหตุผล เวลา. ส่วนลดใบเสร็จทุกครั้ง (แม้ ≤ 40%) ที่**ต่างจากส่วนลดที่ตกลง** ต้องมีเหตุผลสั้น ๆ บันทึกไว้ด้วย (assumption A-10) เพื่อให้สรุปรายวันอธิบายได้
- **AC-C6** ยอดบิล = 0 (ทุกบรรทัดไม่ได้ทำ หรือส่วนลด = ฐาน) → ไม่ออกใบเสร็จ 409 `nothing_to_bill` (assumption A-11; `payments.amount > 0` ก็บังคับอยู่แล้ว). งานจบอย่างไรเมื่อไม่มีอะไรเก็บเงิน → ดู G5
- **AC-C7** ปัดเศษ: ปัดต่อบรรทัดแล้วรวม วิธีเดียวกันทั้งจอ/พิมพ์/สรุป (§4 ข้อ 3) ผ่านฟังก์ชันใน `packages/domain` + `.test.ts` คู่กัน. ตัวเลขที่พิมพ์ = ตัวเลขที่ snapshot ตอน issue ไม่คำนวณใหม่ (§4 ข้อ 4)
- **AC-C8** บรรทัด `labor`/`fee` ถูกนับในฐานและในยอดบิลเหมือน `part` (ร้านคิดแยกแต่ลดรวม). การแยกฐาน VAT (ของ vs ค่าแรง) เป็นเรื่องห้อง VAT — ใน P3.2 เก็บ**ส่วนลดระดับเอกสาร**เท่านั้น ไม่กระจายลงบรรทัด (ดูกลุ่มคำถามบัญชี)

### D. รับเงิน (payment entry)

**Story D1:** As an `advisor`, I want to record how the customer paid and how much they handed over, so that the system tells me the change and the drawer balances.

- **AC-D1** ช่องทาง: ปุ่มเลือก (ไม่ใช่ dropdown ที่มีค่าเริ่มต้นเงียบ) ค่าที่ใช้ได้ใน P3.2 ตามผลคำถาม B3. **ห้ามมีค่า default** ที่ทำให้กดผ่านได้โดยไม่ได้เลือก (ต้นแบบมี "ไม่ระบุ" และให้เติมทีหลัง — ต้องไม่ย้ายพฤติกรรมนี้มา)
- **AC-D2 จ่ายพอดี** Given ยอดคงเหลือ 7,500 / When transfer 7,500 / Then ปิดได้, ไม่มีเงินทอน
- **AC-D3 เงินสดเกิน (ทอน)** Given 7,500 / When cash 8,000 / Then แสดงเงินทอน 500.00 ก่อนยืนยัน, บันทึกแถว payment `amount = 8000`, `change_given = 500` (**ไม่ใช่** บันทึก 7,500) — ผลสุทธิ = `amount − change_given` = 7,500
- **AC-D4 จ่ายขาด** Given 7,500 / When cash 7,000 / Then บล็อก 409 `payment_short` พร้อม `short: "500.00"` ข้อความ "ขาดอีก ฿500.00"; ไม่มีใบเสร็จ ไม่มีแถว payment ค้าง (ทั้ง transaction rollback)
- **AC-D5 เกินที่ไม่ใช่เงินสด** transfer/card ที่ยอดรับ > ยอดคงเหลือ → 409 `payment_over_noncash` (ทอนได้เฉพาะเงินสด) — ให้ Ice ยืนยัน (assumption A-12)
- **AC-D6 หลายช่องทางในบิลเดียว** Given 7,500 / When transfer 5,000 + cash 3,000 / Then สองแถว, เงินทอน 500 ผูกกับแถวเงินสด, ผลรวมสุทธิ 7,500 ปิดได้. เงินทอนต้อง ≤ ยอดเงินสดที่รับ และเกิดได้เฉพาะเมื่อ Σ amount > ยอดคงเหลือ
- **AC-D7 นิยาม paid_total** ⚠ §5.3 เขียน `paid_total = SUM(payments.amount)` แต่ถ้า amount เก็บยอดรับจริงก่อนทอน การเทียบกับ grand_total จะเกินเมื่อมีทอน → ต้องใช้ **`SUM(amount − change_given)`** เทียบยอดคงเหลือ. เทสยืนยัน D3 และ D6
- **AC-D8** ยอดรับ ≤ 0, ไม่ใช่ตัวเลข, ทศนิยมเกิน 2 ตำแหน่ง → 400 field error (ไม่ใช่ CHECK `amount > 0` ระเบิดเป็น 500)
- **AC-D9** ไม่มีการแก้/ลบแถว `payments` ทุกกรณี (append-only; API ไม่มี PUT/DELETE; ยิงตรงต้องถูกปฏิเสธ)
- **AC-D10** บัตรเครดิต "บวก 3%" แบบต้นแบบ (ยอดรับแก้ได้): **ใน P3.2 ไม่มี** — ยอดต้องเท่ายอดคงเหลือ. ถ้าร้านเก็บค่าธรรมเนียมบัตรจริง → คำถาม B3 (ต้องเป็นบรรทัด `fee` ที่ลูกค้าเห็นและอนุมัติ ไม่ใช่การแก้ยอดรับ)

### E. ปิดบิล + ออกใบเสร็จใน transaction เดียว

**Story E1:** As an `owner`, I want it to be impossible to have a closed bill without a receipt or a receipt without payment, so that the books and the paper always agree.

- **AC-E1 ทั้งก้อนหรือไม่เลย** Given ขั้นตอนปิดบิลทำงาน / When ขั้นใดล้มเหลว (ออกเลขไม่ได้ `GS001`, payment ผิด, สต๊อก unreserve ล้ม, เครือข่ายหลุดกลางทาง) / Then ไม่มีเลขใบเสร็จถูกใช้ ไม่มีแถว payment ไม่มี `fulfilled_*` ถูกบันทึก ไม่มี stock move. หลังสำเร็จ: ใบเสร็จ `issued` + payments + (ถ้า WO-006 พร้อม) unreserve อยู่ครบ
- **AC-E2 เลขที่** เลขใบเสร็จมาจาก `allocate_document_number()` ใน transaction เดียวกับที่ issue (§5 ข้อ 3). ยิง 20 คำขอปิดบิลพร้อมกันคนละงาน → เลขไม่ซ้ำไม่ข้าม (เทส invariant ข้อ 4 ของ §13 สำหรับชุด REC). ล้มเหลวหลังขอเลข → เลขต้องไม่หาย (ไม่เกิด gap)
- **AC-E3 Idempotent** กดปิดบิลซ้ำ / retry / สองเครื่องพร้อมกันกับงานเดียวกัน → ได้ใบเสร็จ**ใบเดียว** ครั้งที่สองได้ผลเดิมกลับ (หรือ 409 `already_billed` พร้อมเลขใบเสร็จเดิม) ไม่เกิดแถว payment ซ้ำ ไม่เกิด `unreserve` ซ้ำ. ปุ่มปิดบิลปิดการใช้งานระหว่างรอ (§10)
- **AC-E4 ลำดับล็อก** `jobs → documents → document_lines → สต๊อก` ตาม §4.x; อ่านเอกสารก่อนล็อกเพื่อหา `job_id` เท่านั้น แล้วอ่านซ้ำหลังล็อก ห้ามตัดสินยอด/สถานะจากค่าที่อ่านก่อนล็อก (ตัวอย่างอันตราย: ใครสักคนถอยการยืนยัน/ออก rev ใหม่ระหว่างที่อีกคนกดปิดบิล)
- **AC-E5 Gate ที่ backend** ใบเสนอราคายังไม่ confirm → 409; งานเป็น `warranty_claim` → 409 `claim_no_receipt`; งานสถานะที่ยังไม่ถึงจุดออกใบเสร็จ → 409; สิทธิ์: เฉพาะ `owner/manager/assistant_manager/advisor`
- **AC-E6 ไม่มีทางออกใบเสร็จโดยไม่ผ่านขั้นติ๊ก** ยิง API ตรงด้วย body ที่มีแค่ยอดเงิน → 400/409 (ยอดบนใบเสร็จคำนวณฝั่ง server จากบรรทัด ไม่รับยอดจาก client)
- **AC-E7 Snapshot** ใบเสร็จเก็บบรรทัดที่ทำจริง (ชื่อ ยี่ห้อ ราคา จำนวน ประกัน) + ส่วนลด + ยอด + ชื่อ/เบอร์ลูกค้า + ทะเบียนรถ ณ ตอนออก ไม่ join สดตอนพิมพ์ (§5 กติกา 1). แก้ชื่อลูกค้าทีหลัง ใบเสร็จเก่าต้องไม่เปลี่ยน
- **AC-E8 หลังปิดบิล** ใบเสร็จแก้ไม่ได้ (ยิง UPDATE ตรงต้องชน `GS002`); สถานะงาน `delivered → ready` ต้องถูกปฏิเสธ 409 เมื่อมีใบเสร็จที่ไม่ void (WO-005 §8 — ค้างมาจาก /today, ต้องทำใน P3.2)
- **AC-E9 สถานะงาน** เมื่อปิดบิล งานได้ substate `paid` (ชำระแล้ว, มีใน 0016) — แต่การปิดบิล **ไม่เลื่อนสถานะงานเป็น `delivered` อัตโนมัติ** (assumption A-5; ผูกกับคำถาม B1)
- **AC-E10** `vat_mode = 'none'` บนใบเสร็จทุกใบใน P3.2 และไม่มี UI/endpoint ให้เปลี่ยน; ใบเสร็จไม่มีคำว่า "ใบกำกับภาษี" ที่ใดเลย

### F. สรุปรายวัน (เงินเข้า ≠ ยอดขาย) และนับเงินสดลิ้นชัก

**Story F1:** As an `owner`, I want two separate daily numbers, so that a deposit received on the 3rd and billed on the 8th never distorts either day.
**Story F2:** As a `manager`, I want to count the cash drawer and see the variance against what the system says should be there.

- **AC-F1 สองแผงแยกกัน** หน้าสรุปรายวันแสดง **"เงินเข้า"** และ **"ยอดขาย"** เป็นสองแผงคนละหัวข้อ ป้ายบอกช่วงเวลา (วัน, Asia/Bangkok) และตัวหาร (จำนวนบิล / จำนวนรายการจ่าย) (§5.7 ข้อ 10). **ห้ามมีตัวเลข "รวม" ที่ทำให้สองตัวนี้เท่ากัน** และห้ามคำนวณจากชุดข้อมูลเดียวกัน
- **AC-F2 เงินเข้า** แยกตามช่องทาง; เงินสด = Σ(amount − change_given); แสดงจำนวนครั้งที่ทอนและยอดทอนรวม
- **AC-F3 ยอดขาย** = จำนวนบิล, จำนวนลูกค้า (distinct), ยอดบิลรวม, **ยอดส่วนลดรวม**, รายการบิลที่ส่วนลด > 40% (ผ่านการอนุมัติโดยใคร), บิลที่ยอดน้อยกว่ายอดตกลง (มีบรรทัดไม่ได้ทำ) — เพราะ DECISION-2026-10-07 §2.2 รับความเสี่ยง "ส่วนลดไม่มีเพดาน" โดยอาศัยว่าเห็นในสรุปรายวันภายในวันเดียว
- **AC-F4 Fixture พิสูจน์ว่าแยกจริง** (เทส) Given payment `received_at` = 3 ก.ย. ผูกกับใบเสร็จที่ `issued_at` = 8 ก.ย. (สร้างด้วย fixture ตรงในฐานข้อมูลทดสอบ เพราะ P3.2 ปิดบิลแล้วเงินเข้าวันเดียวกันเสมอ — มัดจำจริงมาใน P3.3) / Then 3 ก.ย.: เงินเข้า = ตามแถว, ยอดขาย = 0; 8 ก.ย.: ยอดขาย = ยอดบิลเต็ม, เงินเข้า = เฉพาะแถวที่ตกวันนั้น. **เกณฑ์ผ่านข้อ 9 ของ WO-005 §6 ("สองตัวเลขต่างกันได้และต่างกันถูกต้อง") จึงพิสูจน์ครบได้เมื่อ P3.3 ลง — ใน P3.2 พิสูจน์ด้วย fixture**
- **AC-F5 ใบเสร็จ void** ไม่นับในยอดขาย; ผลต่อ "เงินเข้า" ต้องตัดสินกับ architect (G3) และแสดงเป็นบรรทัดแยก "ยกเลิกใบเสร็จ" ไม่ใช่หายเงียบ
- **AC-F6 ขอบเขตวัน** บิลปิด 23:59 และ 00:01 ตกคนละวัน; ทดสอบด้วยเขตเวลา Bangkok ไม่ใช่ UTC (UTC 17:00 = 00:00 ของวันถัดไปในไทย)
- **AC-F7 นับเงินสด** Given วันนั้นมีเงินสดเข้า (สุทธิหลังทอน) 12,500 และผู้ใช้นับได้ 12,300 / When บันทึกการนับ / Then `expected_cash = 12,500` (ระบบคำนวณ ผู้ใช้แก้ไม่ได้), `counted_cash = 12,300`, `variance = −200` ขึ้นเด่น. เหตุผล/หมายเหตุ**บังคับเมื่อ variance ≠ 0** (assumption A-13)
- **AC-F8** หนึ่งวันนับได้ครั้งเดียวต่อสาขา (`UNIQUE (shop_id, business_date)`); ความต้องการกรณีนับซ้ำ/แก้ ดูคำถาม B7. เงินสดที่เข้า**หลัง**บันทึกการนับของวันนั้นต้องขึ้นธง "รับหลังนับ ฿X" ไม่ปล่อยให้ variance เปลี่ยนเงียบ
- **AC-F9** สิทธิ์: ดู 5-J. ตัวเลขต้นทุน/กำไรไม่อยู่ในหน้านี้ (advisor เห็นได้ตามตาราง §12.1)
- **AC-F10 เตรียม P3.3** ข้อกำหนดของนิยาม (ไม่ใช่ UI): "เงินเข้า" ในอนาคตต้องรวมเงินรับมัดจำตามวันที่รับ และ**ไม่นับ**แถว `deposit_offset` ซ้ำ; ยอดขายจะไม่รวมเงินริบมัดจำ. นิยามใน P3.2 ต้องเขียนให้เพิ่มแหล่งเงินได้โดยไม่ต้องเปลี่ยนความหมายของรายงาน (ดู C7: ซอร์สเอกสารขัดกันว่ามัดจำเป็นแถวใน payments หรือตาราง deposits)

### G. พิมพ์ A4 สองชุด + ประวัติการพิมพ์

**Story G1:** As an `advisor`, I want to print two clean A4 copies in one action, so that the customer and the shop each hold the same paper.
**Story G2:** As an `owner`, I want to know how many times each paper was printed and by whom, so that two different papers with the same number can be told apart (DECISION-2026-10-15 §2).

- **AC-G1 รูปแบบ** A4 อย่างเดียว ขาวดำอ่านง่าย ไม่ใช้สีแบรนด์ ฟอนต์ไทยไม่แตก (ตัวอย่างต้องมีพยัญชนะซ้อน วรรณยุกต์ สระบน/ล่าง เช่น "ปรับตั้งศูนย์ล้อ", "ลูกหมากปีกนกล่าง") ตัดหน้าถูกแม้รายการยาวเกิน 1 หน้า (หัวตารางซ้ำ/ยอดรวมไม่ขาดข้ามหน้าแบบอ่านผิด) — เกณฑ์ผ่าน WO-005 §6 ข้อ 8
- **AC-G2 สองชุด** การพิมพ์ 1 ครั้งออก 2 ชุด: **ลูกค้า 1 / ร้านเก็บ 1** ระบุบนหน้ากระดาษว่าชุดไหน (ถ้อยคำ — A-14). ใบกำกับภาษี (นอก P3.2) ใช้ "ต้นฉบับ/สำเนา" ตาม §5.5b — ใบเสร็จไม่ใช่เอกสารภาษีจึงไม่จำเป็นต้องใช้คำนี้
- **AC-G3 ท้ายกระดาษทุกครั้ง** "พิมพ์ครั้งที่ N · วันที่ เวลา · โดย ชื่อพนักงาน" บนทุกหน้าของทุกชุด; วันที่แสดงเป็น **พ.ศ.** (DD/MM/พ.ศ. HH:mm, เขตเวลา Bangkok) ตามที่พนักงานคุ้น (ต้นแบบใช้ +543); ค่าที่จัดเก็บเป็น timestamp ปกติ
- **AC-G4 ประวัติ** ทุกครั้งที่พิมพ์เก็บแถวใหม่ (append-only ห้ามแก้ห้ามลบ): ใคร, เมื่อไหร่, ชนิดและรหัสเอกสาร, **สถานะเอกสารตอนนั้น**, revision, ยอดสำคัญที่พิมพ์ (หรือเทียบเนื้อหาได้), ลำดับ N. N บนกระดาษ = จำนวนแถวประวัติของเอกสารนั้น ณ ตอนนั้น (ถ้าบันทึกประวัติล้ม ต้องไม่ออกกระดาษที่เลข N ไม่มีในประวัติ). ใบสั่งงานที่ไม่มีเลขเอกสาร ผูกประวัติกับงาน+ชนิด
- **AC-G5 เตือนพิมพ์ซ้ำ** Given เอกสารเคยพิมพ์ N ครั้ง และ**เนื้อหาเปลี่ยนหลังพิมพ์ครั้งล่าสุด** (เช่น ถอยการยืนยันแล้วยืนยันใหม่ด้วยส่วนลดต่าง, ออก rev ใหม่) / When กดพิมพ์ / Then ก่อนพิมพ์ขึ้น "ใบนี้เคยพิมพ์ไปแล้ว N ครั้ง เนื้อหาเปลี่ยนหลังจากนั้น — เก็บใบเก่าคืนจากลูกค้า" ต้องกดรับทราบจึงพิมพ์ได้ และการรับทราบบันทึกในประวัติ. เทียบ "เนื้อหาเปลี่ยน" ด้วยข้อมูลที่บันทึกไว้ตอนพิมพ์ครั้งก่อนกับสถานะปัจจุบัน — ไม่ใช่เดาจากเวลา
- **AC-G6 พิมพ์ซ้ำเอกสารที่ไม่เปลี่ยน** (ใบเสร็จ immutable): ไม่ต้องมีคำเตือนเนื้อหาเปลี่ยน แต่ N เพิ่ม และ**หน้ากระดาษแสดงว่าเป็นการพิมพ์ซ้ำ** (assumption A-15) เพราะใบเสร็จซ้ำคือช่องโกง
- **AC-G7 ใบเสนอราคา** พิมพ์ได้ทั้ง draft/issued/signed: draft = ไม่มีเลข ต้องแสดง "ฉบับร่าง" ชัดเจน (assumption A-16); issued/signed แสดง**สองยอดเสมอ** ("ยอดเสนอทั้งหมด" และ "ยอดที่อนุมัติ") และบรรทัดที่ลูกค้าปฏิเสธต้องพิมพ์ออกมาพร้อมข้อความ "เสนอรายการนี้ไปแล้ว ลูกค้าไม่อนุมัติ" (§5.1 ข้อ 2)
- **AC-G8 ใบเสร็จ** แสดง: เลขที่, วันที่ (พ.ศ.), ลูกค้า, รถ/ทะเบียน/เลขไมล์, บรรทัดที่ทำจริง (ราคา×จำนวน), ประกันต่อบรรทัด, ส่วนลดใบเสร็จ, **ยอดบิล**, รับเงินแยกช่องทาง, **เงินทอน**, **ยอดสุทธิ**, ชื่อพนักงานที่ปิด. ไม่มีลายเซ็นบนจอ (ตัดแล้ว) มีช่องเซ็นบนกระดาษ. ห้ามมีคำว่า "ใบกำกับภาษี". ตัวเลขทั้งหมดอ่านจาก snapshot
- **AC-G9 สิทธิ์ราคา** ใบสั่งงานไม่มีเงิน; ใบเสร็จ/ใบเสนอราคาต้องไม่เปิดให้ `technician` (ไม่เห็นราคา §12.1)
- **AC-G10 สิทธิ์ข้ามสาขา** พิมพ์/เปิดประวัติของสาขาอื่นไม่ได้ (เทส 2 ร้าน). ไฟล์ผลพิมพ์ (ถ้ามี) เสิร์ฟผ่าน endpoint ที่ตรวจ JWT ไม่ใช่ `express.static` (§12)
- **AC-G11 ข้อจำกัดที่ต้องรู้** ระบบบอกไม่ได้ว่ากระดาษถูกพิมพ์ออกจริงหรือผู้ใช้กดยกเลิกที่กล่องพิมพ์ของเบราว์เซอร์ (ต้นแบบก็บอกไม่ได้ — `afterprint` ยิงทั้งสองกรณี) → ประวัติ = "ระบบสร้างผลพิมพ์ให้" ไม่ใช่ "กระดาษออกแล้ว" และยอมรับว่า N อาจนับเกินกระดาษจริง; **ไม่ยอมรับ** N ที่ถูกรายงานจาก client เองโดยเซิร์ฟเวอร์ไม่รู้ (ต้นแบบทำแบบนั้น) — วิธีทำให้ architect ตัดสิน (ดู G7)

### H. คืนของจองของบรรทัดที่ไม่ได้ทำ (stock `unreserve`)

**Story H1:** As an `owner`, I want parts reserved for work that was not done to go back to available stock automatically when the bill closes, so that stock is not silently locked forever.

> **เงื่อนไขพึ่งพา:** ยังไม่มีโค้ด reserve ใน API (หัวข้อ 1). AC นี้แบ่งสองระดับ: **H-contract** ต้องผ่านใน P3.2 เสมอ; **H-effect** ผ่านเมื่อ WO-006 merge แล้ว (จะเลื่อนเกตไปรวมกับ WO-006 ถ้า WO-006 ตามหลัง)

- **AC-H1 (contract)** ปิดบิลเรียกขั้นตอน "คืนของจอง" ครั้งเดียวต่อบรรทัดที่ approved ที่ `fulfilled_qty < qty` ภายใน transaction เดียวกับ E1 และด้วย `idempotency_key` ที่ซ้ำไม่ได้ (รูปแบบอยู่ที่ WO-006: `unreserve:…`) — ถ้าไม่มี reserve อยู่ (บรรทัดไม่มี `sku_id`, ยังไม่มีโมดูลสต๊อก, `buy_to_order` ที่ไม่ได้จอง) ต้อง**ไม่ error** และไม่สร้าง move ขยะ แต่ต้องทำให้ปิดบิลสำเร็จ
- **AC-H2 (effect)** Given บรรทัด qty 4 จองแล้ว 4, ทำจริง 3 / Then `unreserve` 1, `reserved` ลด 1, `on_hand` ไม่เปลี่ยน, `available` เพิ่ม 1. ทำจริง 0 → `unreserve` 4. ปิดบิลซ้ำ → ไม่ unreserve ซ้ำ
- **AC-H3 (effect)** `reserve` จองได้เท่าที่มี ส่วนที่ขาด = `shortfall` (ไม่ได้จองจริง) → `unreserve` ต้องคืนเฉพาะที่จองจริง ไม่ทำให้ `reserved` ติดลบ (CHECK ที่ฐานข้อมูลเป็นตาข่ายสุดท้าย ต้องมีด่านหน้าที่ domain, §4.y) และ `purchase_suggestion` ของ shortfall บรรทัดนั้นต้องถูกยกเลิก/ปิดเมื่อบรรทัดไม่ได้ทำ (ให้ architect + inventory-ledger-engineer ตัดสินรูปแบบ)
- **AC-H4 ของที่เบิก (`issue`) ไปแล้วแต่บรรทัดไม่ได้ทำ** — `unreserve` คืนไม่ได้แล้ว (จองถูกแปลงเป็น issue ตั้งแต่เบิก, WO-006 §3). ระบบต้อง**ไม่ปล่อยเงียบ**: ขึ้นเป็นรายการ "ของเบิกแล้วแต่ไม่ได้ใช้ — ต้องคืนเข้าคลัง N ชิ้น" ในรายงานกระทบยอด (§6 ข้อ 7) และไม่บล็อกการปิดบิล (assumption A-17). การบันทึก `return` เป็นงานของโมดูลสต๊อก
- **AC-H5** `fulfilled_qty` ที่มากกว่าจำนวนที่ issue จริง (ใบเสร็จคิดเงิน 4 แต่เบิกไป 3) → ไม่บล็อก แต่ขึ้นในรายงานกระทบยอด
- **AC-H6** ต้นทุน/ตัวเลขเงินของสต๊อกไม่ปรากฏใน response ที่ `advisor` เรียก (§12.2)

## 9. คำถามสำหรับ Ice

### กลุ่ม A — คำถามบัญชี 4 ข้อ (ยกจาก PLAYBOOK.md ส่วน P3.2 ตรงตัว)

> **ก่อนเริ่ม P3.2 ส่งคำถามบัญชี 4 ข้อให้ Ice ตอบรวดเดียว** (thai-tax 15 ต.ค.): ฐาน VAT เมื่อมีส่วนลดท้ายบิลบนบิลที่มีทั้งของและค่าแรง · VAT คิดหลังหักส่วนลดหรือไม่ (add_7 / include_7) · ใบกำกับแสดงส่วนลดท้ายบิลได้ไหม · กฎเศษสตางค์ตอนกระจายส่วนลด — ใบเสร็จต้องอ่าน `approved_total` ไม่ใช่ `grand_total`

แยกเป็นข้อ (ถ้อยคำเดิม):
1. ฐาน VAT เมื่อมีส่วนลดท้ายบิลบนบิลที่มีทั้งของและค่าแรง
2. VAT คิดหลังหักส่วนลดหรือไม่ (add_7 / include_7)
3. ใบกำกับแสดงส่วนลดท้ายบิลได้ไหม
4. กฎเศษสตางค์ตอนกระจายส่วนลด

*(ท้ายประโยคเดิม "— ใบเสร็จต้องอ่าน `approved_total` ไม่ใช่ `grand_total`" เป็นข้อกำหนด ไม่ใช่คำถาม: ผมรับไว้เป็น AC-C1)*

**ข้อสังเกตของผม (ไม่ใช่คำตอบ):** ทั้ง 4 ข้อเป็นเรื่องห้อง VAT ซึ่งอยู่นอกขอบเขต P3.2. ที่แตะ P3.2 จริงมีข้อเดียวคือข้อ 4 ถ้า Ice ต้องการให้ใบเสร็จเก็บ**ส่วนลดที่กระจายลงรายบรรทัด**ตั้งแต่ตอนนี้ — ผมเสนอให้ P3.2 เก็บส่วนลด**ระดับเอกสารอย่างเดียว** (AC-C8) ซึ่งไม่ปิดทางห้อง VAT (กระจายทีหลังได้จากบรรทัดและส่วนลดที่ snapshot ไว้) ดังนั้น **ทั้ง 4 ข้อไม่บล็อกการเริ่ม P3.2** ถ้า Ice ยืนยันข้อเสนอนี้ — ตอบได้ทีหลัง แต่ต้องตอบก่อนเริ่มห้อง VAT

### กลุ่ม B — คำถามใหม่ (แต่ละข้อเปลี่ยนสิ่งที่ต้องสร้าง)

**B1. ลำดับ "จ่ายเงิน / ปิดบิล" กับ "ส่งรถ (`delivered`)" และกรณีออกใบเสร็จก่อนเงินเข้า**
(ก) ร้านเก็บเงิน **ก่อน** ส่งกุญแจเสมอใช่ไหม (พร้อมส่ง → ปิดบิล → ส่งแล้ว)? ถ้าใช่ จะให้ระบบ**บังคับ**ว่างานปกติต้องมีใบเสร็จก่อนกด "ส่งแล้ว" ไหม (งานเคลมยกเว้น)? — ข้อนี้เปลี่ยน flow รับรถ→ส่งรถที่ใช้ทุกวัน และกระทบการสร้างประกัน (C6)
(ข) มีกรณีที่ต้อง **พิมพ์ใบเสร็จก่อนเงินเข้าจริง** ไหม (รอสลิปโอน/ลูกค้าโอนทีหลัง) — ต้นแบบให้พิมพ์ก่อนแล้วเติมช่องทางทีหลัง; ใหม่ไม่ให้ (ต้องมีเงินครบตอนปิดบิล)
*คำแนะนำ: (ก) ใช่และบังคับ (ข) ไม่มี → ไม่รองรับ*

**B2. มัดจำในช่วงก่อน P3.3 (~5% ของงาน):** งานที่ลูกค้าวางมัดจำไว้แล้ว จะปิดบิลในระบบใหม่ได้อย่างไร (C2)?
ก) ปิดบิลงานเหล่านั้นในระบบเก่า/ด้วยมือ จน P3.3 พร้อม  ข) ส่งส่วนหักมัดจำแบบบาง ๆ มาในรอบนี้  ค) ช่อง "มัดจำที่รับไว้นอกระบบ" (`manager`+ กรอก ต้องมีเหตุผล+อ้างอิงใบเก่า ไม่ถูกนับเป็นเงินเข้า)
*คำแนะนำ: ค) — ถ้า P3.3 ตามมาภายใน 1–2 สัปดาห์ อาจเลือก ก) แทนได้ เพราะ ค) สร้างสิ่งที่ต้องย้ายภายหลัง*

**B3. ช่องทางชำระ และค่าธรรมเนียมบัตร:**
(ก) รายงาน "เงินเข้า" ต้องแยกตาม **ประเภท** (เงินสด/โอน/บัตร) หรือแยกตาม **บัญชีที่เงินเข้า** (ออมสิน / คลิก / JPM / …) หรือทั้งสอง? ต้นแบบแยกตามบัญชี, WO-005 บอกประเภท 4 แบบ (โอน/เงินสด/บัตร/QRCode), schema มี 3 ประเภท — โอนกับ QR เป็นอันเดียวกันไหม?
(ข) ร้านเก็บค่าธรรมเนียมบัตรเครดิต (ต้นแบบมีโน้ต "+3%") จริงไหม? ถ้าจริง ต้องเป็นบรรทัด `fee` ที่เสนอและลูกค้าอนุมัติบนใบเสนอราคา ไม่ใช่แก้ยอดรับตอนปิดบิล
(ค) ตัด `credit` (§5.3) ออก ถูกไหม — ขัดกับ "ไม่มีลูกหนี้"
*คำแนะนำ: (ก) ประเภทเป็นค่าบังคับ + "บัญชีที่เงินเข้า" เป็นตัวเลือกที่ร้านตั้งเอง ถ้าตอบว่าต้องการ (ข) ถ้าไม่เก็บ ไม่ต้องทำอะไร (ค) ตัด*

**B4. เพดาน 40% — วัดอะไร ที่ไหน ใครอนุมัติ:**
(ก) วัดที่ **ส่วนลดสุดท้ายบนใบเสร็จ ÷ ยอดรวมก่อนลดของบรรทัดที่ทำจริง** (นิยามหัวข้อ 3) ไม่ว่าส่วนลดนั้นตั้งตอนเสนอ/ตอน confirm/ตอนปิดบิล — ใช่ไหม? (ถ้าวัดเฉพาะ "ตอนแก้ที่ใบเสร็จ" advisor หลบได้ AC-C4)
(ข) ควรมีเพดานเดียวกันที่ **ตอน confirm ใบเสนอราคา** ด้วยไหม? (ตอนนี้ไม่มี; กรอกส่วนลดใหม่ตอน confirm ตาม DECISION-2026-10-15 §1 ก็ไม่มีเพดาน)
(ค) "manager ขึ้นไป" รวม `assistant_manager` ไหม? และ `manager` ต้อง**ลงมือปิดบิลเอง** (login ของเขา) หรือ advisor เป็นคนปิดโดยมี manager กดอนุมัติ?
*คำแนะนำ: (ก) ใช่ (ข) ใช่ ใช้กติกาเดียวกัน (ค) รวม assistant_manager; manager เป็นคนยืนยันการปิดบิลนั้นเอง (ขั้นตอนเดียว ไม่มีสถานะ "รออนุมัติ" ค้าง)*

**B5. ชุด (set) ที่ทำไม่ครบตอนติ๊ก:** ชุดโปรช่วงล่างมีลูกหลายชิ้น ราคาชุดเดียว. ถ้าลูกค้าอนุมัติครบแต่ช่างทำจริงไม่ครบทุกชิ้น ให้ติ๊กทำจริงที่ระดับ **ชุดทั้งชุด (ทำ/ไม่ทำ)** หรือเลือกรายชิ้น (แล้วใครตั้งราคาชุดใหม่ เหมือน `approved_amount` ตอน confirm)?
*คำแนะนำ: ชุดทั้งชุดเท่านั้นใน P3.2; ชิ้นที่ไม่ได้ใช้จริงลดผ่านส่วนลดใบเสร็จพร้อมเหตุผล (ผ่านเพดาน 40%) — ลดความซับซ้อน; รายชิ้นเป็นงานภายหลังถ้าเจอบ่อย*

**B6. ใบเสร็จผิดวันแรก (เลือกช่องทางผิด กรอกยอดผิด):** ตามตาราง void = `owner` เท่านั้น. เจ้าของไม่อยู่หน้าร้านทุกวัน — ยอมรับได้ไหมที่จะแก้ได้เฉพาะตอนเจ้าของ void+ออกใหม่? หรืออยากให้ `manager` void ใบเสร็จของ**วันเดียวกัน**ได้ (ข้อยกเว้นจากตาราง §12.1)? ใน P3.2 จะมี void ใบเสร็จหรือไม่
*คำแนะนำ: มี void; เริ่มตามตาราง (owner คนเดียว) แล้วดูว่าติดขัดจริงไหมในสัปดาห์แรก — ไม่ผ่อนกฎก่อนมีข้อมูล*

**B7. นับเงินลิ้นชัก:** (ก) มีเงินทอนตั้งต้น (opening float) ทุกเช้าไหม? ถ้ามี expected = float + เงินสดสุทธิวันนั้น ซึ่งสคีมา `daily_closings` ยังไม่มีช่องนี้ (ข) ใครนับ/ปิดวัน (`advisor` ได้ไหม?) (ค) ถ้าพบว่านับผิดหรือมีบิลปิดหลังนับ ต้องแก้ได้ไหม (ตอนนี้หนึ่งวันบันทึกได้ครั้งเดียว)
*คำแนะนำ: (ก) ตามที่ร้านทำจริง (ข) manager ขึ้นไป + advisor ถ้าร้านปิดกะด้วยพนักงาน office (ค) ไม่แก้ของเดิม — บันทึกการนับใหม่เป็นแถวใหม่พร้อมเหตุผล ให้ architect ตัดสิน*

**B8. ใบกำกับภาษีช่วงที่ยังไม่มีห้อง VAT:** ตั้งแต่ ~24 ต.ค. จนห้อง VAT เสร็จ ถ้าลูกค้าขอใบกำกับ ร้านจะทำอย่างไร (ออกจากระบบเก่า / บัญชีออกมือ / ปฏิเสธ)? ระบบใหม่จะไม่มีปุ่มหรือคำถาม "เอาใบกำกับไหม" ใน P3.2 (CLAUDE.md §7.7 เลื่อน) — และต้องไม่พิมพ์อะไรบนใบเสร็จที่ดูเหมือนใบกำกับ
*คำแนะนำ: ออกนอกระบบก่อน และให้พนักงานบันทึกใน audit/โน้ตของงานว่า "ลูกค้าขอใบกำกับ" เพื่อรวบรวมไว้เติมในห้อง VAT ภายหลัง — ต้องการให้ทำช่อง flag นี้ใน P3.2 หรือไม่ (เล็กมาก)*

## 10. เกณฑ์ผ่านของ P3.2 (ย่อ — ทดสอบรันจริง ไม่ใช่อ่านโค้ด)

4. ปิดบิล 20 คำขอพร้อมกัน → เลขไม่ซ้ำไม่ข้าม; ปิดซ้ำงานเดียว → ใบเดียว (AC-E2/E3)

6. เงินทอน: amount เก็บยอดรับจริง `change_given` แยก; นับลิ้นชักใช้ยอดสุทธิ (AC-D3/D6/F7)
7. สรุปรายวัน: เงินเข้า ≠ ยอดขาย พิสูจน์ด้วย fixture; ไม่มีตัวเลขรวม (AC-F1/F4)

9. ใบสั่งงานไม่มีเงิน ไม่มีบรรทัดที่ปฏิเสธ (AC-A1)
10. `delivered → ready` ถูกปฏิเสธเมื่อมีใบเสร็จที่ไม่ void (AC-E8)
11. integration test 2 ร้านทุก endpoint ใหม่ (ร้าน A มองไม่เห็นใบเสร็จ/payments/ประวัติพิมพ์/สรุป/การนับของร้าน B)
