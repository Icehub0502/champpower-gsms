## ก. `queue_today` — ผมเขียน view นี้ผิดเอง แก้ได้

ใบสั่งงานบอก "อ่าน view เดียว" แต่ view ที่มีอยู่ใช้ไม่ได้จริง ถูกต้องตามที่รายงาน

### "คิววันนี้" หมายถึงอะไร — **รถที่ยังอยู่ในอู่ ไม่ใช่รถที่เปิดงานวันนี้**

รถที่เข้ามาเมื่อวานแล้วยังซ่อมไม่เสร็จ **ต้องอยู่บนบอร์ด** นั่นคือเหตุผลที่บอร์ดมีอยู่ —
พนักงานมองบอร์ดเพื่อรู้ว่า "ตอนนี้ในอู่มีรถกี่คัน คันไหนอยู่ตรงไหน" ไม่ใช่เพื่อรู้ว่าวันนี้รับมากี่คัน

ถ้ากรองด้วยวันที่ รถค้างข้ามคืนจะหายจากบอร์ดตอนเที่ยงคืน ซึ่งเป็นบั๊กที่เจ็บมาก

**ดังนั้น: ชื่อ `queue_today` ผิด ไม่ใช่ตรรกะผิด**

### สั่งทำ

1. **เปลี่ยนชื่อเป็น `queue_board`** ใน migration ใหม่ ชื่อเดิมจะหลอกคนอ่านไปตลอด
2. **เพิ่มคอลัมน์ที่หน้าจอต้องใช้** — `queue_no` · `brand` · `model` · `color` ·
   `thumb_file_id` · `assigned_technician_id` · `assigned_team_id` · `job_type`
   (งานเคลมต้องดูออกจากบอร์ดว่าเป็นงานเคลม)
3. **ฝั่ง job: ไม่กรองวันที่** เอาทุกคันที่ยังไม่ `carout`/`rejected` และไม่ถูกลบ
4. **ฝั่ง booking: กรองช่วงวันที่ได้** — ให้ view คืนคอลัมน์ `at` แล้ว **API เป็นคนกรอง**
   ค่าตั้งต้นของหน้าจอ: `วันนี้ ถึง +7 วัน` ไม่งั้นการจองของเดือนหน้าจะมาปนบนบอร์ด

## ข. ช่องยก — **แก้ได้จากบอร์ดด้วย ไม่ใช่แค่ตอนรับรถ**

รถย้ายช่องระหว่างวันเป็นเรื่องปกติ และคนที่รู้คือคนที่ยืนอยู่หน้างาน ไม่ใช่คนที่รับรถเมื่อเช้า
ถ้าแก้ได้เฉพาะตอนรับรถ พนักงานจะเลิกอัปเดตภายในสองวัน แล้วบอร์ดจะโกหกทันที

**สั่งทำ:** เปลี่ยนช่องยกได้จากการ์ดบนบอร์ด (modal สั้นๆ เหมือนต้นแบบทำ) และตอนรับรถ/จองคิว

**ข้อจำกัดที่ยอมรับ:** `EXCLUDE USING gist` กันจองซ้อนอยู่บน `bookings` เท่านั้น
รถที่อยู่ในอู่จริงสองคันในช่องเดียวกัน **ฐานข้อมูลไม่กัน** — ตั้งใจ เพราะของจริงมองเห็นด้วยตา
และบางทีก็จอดซ้อนกันจริงระหว่างรอ **ให้หน้าจอเตือนเฉยๆ ห้ามบล็อก**

## ค. `queue_no` — **ให้ระบบออกเลขเอง แก้ได้ และห้ามซ้ำในวันเดียวกัน**

เลขคิวคือเลขที่พนักงานตะโกนข้ามอู่ ถ้าซ้ำแล้วรถสองคันขานรับ นั่นคือความเสียหายจริง
แต่ถ้าแก้ไม่ได้เลย พนักงานจะเจอเคสที่ต้องสลับลำดับแล้วทำไม่ได้

### สั่งทำ — migration ใหม่

```
jobs.job_date   date NOT NULL     -- วันที่รับรถ ตามเวลาไทย ไม่ใช่ created_at
                                  -- (ต้นแบบคีย์ย้อนหลังได้ ต้องรองรับ)
jobs.queue_no   integer           -- เปลี่ยนจาก text
CONSTRAINT uq_queue_no UNIQUE (shop_id, job_date, queue_no)
```

- ระบบออกเลขให้เองตอนเปิดงาน = `max(queue_no) + 1` ของ (สาขา, วันนั้น) **ในทรานแซกชันเดียวกัน**
  ไม่ใช่อ่านแล้วค่อยเขียน
- **แก้ได้** ถ้าเลขที่ขอชนกับคันอื่น ฐานข้อมูลปฏิเสธ แล้วหน้าจอบอกว่า "คิว 5 มีรถคันอื่นแล้ว"
- อยากสลับเลขสองคัน = แก้ทีละคัน ผ่านเลขว่างก่อน — ยอมรับได้ เพราะเกิดไม่บ่อย
  และการกันเลขซ้ำสำคัญกว่าความสะดวกในการสลับ
- **ไม่ต้องใช้ `document_series`** เลขคิวไม่ใช่เอกสาร ไม่ต้องต่อเนื่อง ไม่ต้องห้ามข้าม

## ง. migration เพิ่ม 2 ตัว — **อนุมัติ**

สคีมาต้องตรงกับความจริง นั่นคือเหตุผลที่ migration มีอยู่ ไม่ใช่ของที่ต้องประหยัด

**รวมเป็นไฟล์เดียว `0013_queue_board.sql`** ไม่ต้องแยกสอง เพราะทั้งหมดเป็นเรื่องเดียวกัน
(บอร์ดคิวใช้งานได้จริง) และควร rollback พร้อมกัน

ในไฟล์นั้นทำให้ครบ:

1. `queue_board` view แทน `queue_today` (พร้อม `security_invoker = true` — ห้ามลืม)
2. `jobs.job_date` + `queue_no` เป็น integer + unique ต่อวัน
3. `files.kind` เพิ่มค่าที่รูปงานต้องใช้
4. **ลบ `jobs.mileage_in` ตัวเก่า** (ข้อสังเกตข้อ 3 ของคุณ) เหลือ `mileage_in_km` ตัวเดียว
   สองคอลัมน์ที่แปลว่าเหมือนกันคือบั๊กที่รอเกิด

**อย่าลืม:** ทุก migration ที่แตะ policy หรือ view ต้องรัน `packages/db/verify-rls.sql` แล้วแนบผล

## ข้อสังเกต 3 ข้อ — ตอบครบ

**1. `packages/contracts` ยังไม่มี** — ถูกต้อง `CLAUDE.md` §2 เขียนไว้ว่ามี แต่ยังไม่ได้สร้าง
**สร้างใน WO-003 นี้เลย** เริ่มจาก schema ของ queue/booking/checkin ที่ทำอยู่
ไม่ต้อง scaffold ทั้งระบบล่วงหน้า — โตตามงานจริง

**2. `bookings.job_id` ถูกลบไปแล้วใน 0011** — ถูกต้อง เอกสารล้าสมัย **แก้ `CLAUDE.md` §5.8**
แถวที่ 2 ของตารางจาก

> `bookings.job_id` ที่ตั้งค่าแล้ว **เปลี่ยนไม่ได้อีก** | trigger

เป็น

> `jobs.booking_id` ที่ตั้งค่าแล้ว **เปลี่ยนไม่ได้อีก** | trigger `trg_jobs_booking_immutable`
> (0011 ย้ายลิงก์มาไว้ข้างเดียวที่ `jobs` — ถือไว้สองข้างแล้วมันจะขัดกันเอง)

**3. `mileage_in` ซ้ำสองคอลัมน์** — จัดการใน `0013` ตามข้อ ง.4 ข้างบน
