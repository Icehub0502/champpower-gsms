# คำตัดสิน Q1 / Q2 — และการแก้ R3 ของผมเอง

1 ต.ค. 2026 · ตอบ `P3.1-TECH-PLAN-v3` §2.2

---

## Q1 — **R3 ที่ผมเขียนไว้ผิดเอง ไม่ใช่แค่ขัดกติกา**

ผมเขียน R3 ว่า *"งานเข้าสถานะปิด ต้อง void ใบที่ยัง live"* แล้วทีมมาเจอว่ามันขัดกติกา owner-only
ทีมเสนอทางออกคือทำเป็นข้อยกเว้นแยกชนิด audit

**ทั้งคู่แก้ที่อาการ ไม่ใช่ที่ต้นเหตุ** ต้นเหตุคือคำว่า "void" ซึ่งผมเลือกมาผิดตั้งแต่แรก

### ทำไมถึงผิด

ใบเสนอราคาที่ออกไปแล้วและลูกค้าไม่เอา **ไม่ใช่เอกสารที่ควรถูกยกเลิก — มันคือบันทึกว่าร้านเสนอไปแล้วลูกค้าปฏิเสธ**

และนั่นคือข้อมูลที่เจ้าของร้านขอไว้ตั้งแต่แรกว่าอยากได้ที่สุด: **"ทำไมลูกค้าถึงไม่เอา"**
ข้อมูลจริงบอกว่าใบเสนอราคาถูกปฏิเสธ **30% (147 จาก 482 ใบ)** — ถ้า void ทิ้งเงียบ ๆ ตอนปิดงาน
รายงานนั้นจะว่างเปล่าในเคสที่สำคัญที่สุด

### กฎใหม่ — แยกเป็น 3 กรณี ไม่ใช่กรณีเดียว

| สถานะใบตอนงานจบ | ทำอะไร |
|---|---|
| `signed` (ยืนยันผลแล้ว) | **ไม่แตะเลย** เป็นบันทึกที่สมบูรณ์แล้ว ลูกค้าตัดสินครบ เหตุผลอยู่ในบรรทัด |
| `issued` แต่ยังตัดสินไม่ครบ | ปิดเอกสาร **แต่ต้องเก็บเหตุผลก่อน** (ดูข้างล่าง) |
| `draft` (ยังไม่มีเลข) | ลบหรือทิ้งได้ ไม่ใช่เอกสารทางการ |

### สิ่งที่ต้องเพิ่ม — **สำคัญกว่าเรื่อง void**

**งานที่จะปิดด้วย `rejected` (ไม่อนุมัติ) ขณะที่ยังมีใบเสนอราคาที่ตัดสินไม่ครบ
→ ระบบต้องบังคับให้กรอกเหตุผลที่ลูกค้าไม่เอา ก่อนปิดงานได้**

ใช้ enum `decline_reason` ชุดเดียวกับที่มีอยู่ ไม่สร้างชุดใหม่ · เขียนลงเอกสารนั้น

> นี่คือจุดเดียวในระบบที่จะได้คำตอบว่าลูกค้าไม่เอาเพราะอะไร ถ้าปล่อยผ่านตรงนี้
> รายงานที่เจ้าของร้านจะใช้ตัดสินใจลงโฆษณา จะมีข้อมูลแค่เคสที่พนักงานขยันกรอกเท่านั้น

`carout` (ลูกค้าเอารถกลับกลางคัน) ไม่ต้องบังคับ เพราะเหตุผลมักไม่เกี่ยวกับราคา

### เรื่องสิทธิ์ — **ไม่ต้องทำข้อยกเว้น**

เมื่อ `signed` ไม่ถูกแตะ และ `issued` ถูก "ปิด" ไม่ใช่ "ยกเลิก" ความขัดแย้งก็หายไปเอง

- ใช้สถานะ `void` ได้ตามที่ schema มี **แต่ต้องมี `void_reason = 'job_closed'` และ `voided_by = NULL`** (ระบบปิด ไม่ใช่คนกด)
- audit แยกชนิด: `document_closed_by_job` ≠ `document_voided`
- **การ void ด้วยมือยังเป็นสิทธิ์ owner เท่านั้น ไม่มีข้อยกเว้น ไม่มีทางเลี่ยง** — advisor ไม่มี endpoint ไหนที่ส่งค่าแล้วทำให้เกิด void ได้ · การปิดเกิดจากการเปลี่ยนสถานะงานล้วน ๆ ซึ่งมีกติกาสิทธิ์ของตัวเองอยู่แล้ว
- ต้องมีเทส: advisor ยิง API void ตรง ๆ → 403 · advisor ปิดงาน → ใบถูกปิดโดยระบบ และ audit เป็นคนละชนิด

## Q2 — ยอดใหม่ของชุดสูงกว่ายอดเดิมได้ไหม

### **ได้ และไม่ใช่เรื่องผิดปกติ**

ราคาชุดคือราคาเหมา ถ้าตัดรายการออก ส่วนลดเหมาก็หายไปด้วย
ของที่เหลือคิดราคาเดี่ยวรวมกันอาจแพงกว่าราคาชุดเดิม — เป็นความจริงทางการค้า ไม่ใช่บั๊ก

> ชุด 20,000 (6 รายการ) · ตัดออก 1 → ที่เหลือคิดเดี่ยว ๆ รวม 22,000 — ถูกต้องและอธิบายลูกค้าได้

### แต่ "เตือนแล้วกดผ่าน" อ่อนเกินไป

คนกดผ่านคำเตือนเสมอ และ**ความผิดพลาดที่น่ากลัวที่สุดคือพิมพ์เกินหนึ่งหลัก**
20,000 → 200,000 คือการเพิ่ม 900% ซึ่งเงียบสนิทถ้าไม่มีใครดู

### กฎ 3 ชั้น

| ยอดใหม่ | ระบบทำอะไร |
|---|---|
| ต่ำกว่าที่เสนอ | ปกติ · บังคับกรอกเหตุผล (กฎเดิมของ `approved_amount`) |
| สูงกว่าที่เสนอ แต่ **ไม่เกิน 2 เท่า** | อนุญาต · บังคับกรอกเหตุผล · **หน้าจอต้องแสดงส่วนต่างเป็นตัวเลขชัด ๆ** ไม่ใช่แค่ไอคอนเตือน |
| **เกิน 2 เท่าของยอดที่เสนอ** | **บล็อก** พร้อมข้อความว่าน่าจะพิมพ์ผิด · ถ้าตั้งใจจริงต้องออก revision ใหม่ |
| ติดลบ | บล็อกเสมอ |
| 0 | อนุญาต (แถมให้ฟรี) · บังคับกรอกเหตุผล |

เหตุผลที่เลือก 2 เท่า: การเพิ่มที่สมเหตุสมผลจริงอยู่ราว +10–50% ส่วนการพิมพ์เกินหนึ่งหลักคือ +900%
เส้นที่ 2 เท่าแยกสองอย่างนี้ออกจากกันได้สะอาด โดยไม่ไปขวางเคสจริง

และเอกสารที่พิมพ์ออกมาต้องแสดง **"เสนอ X / ตกลง Y"** ของบรรทัดนั้น ลูกค้าต้องเห็นก่อนตกลง
ไม่ใช่เห็นแค่ยอดสุดท้าย

### เกณฑ์ผ่านที่ต้องเพิ่ม
- ใส่ยอดใหม่ = 10 เท่าของที่เสนอ → ถูกบล็อก
- ใส่ยอดใหม่ = 1.3 เท่า → ผ่าน แต่ต้องกรอกเหตุผล และหน้าจอโชว์ส่วนต่าง
- ใส่ยอดติดลบ → ถูกบล็อก

## สรุปสิ่งที่เปลี่ยนจากที่ทีมเสนอ

| | ทีมเสนอ | คำตัดสิน |
|---|---|---|
| ใบ `signed` ตอนงานจบ | void ด้วย (R3 เดิมของผม) | **ไม่แตะเลย** |
| ใบ `issued` ตอนงานจบ | void อัตโนมัติ เป็นข้อยกเว้นของกติกา | ปิดโดยระบบ · `voided_by = NULL` · audit คนละชนิด · **ไม่ใช่ข้อยกเว้นของสิทธิ์** |
| เหตุผลที่ลูกค้าไม่เอา | ไม่ได้พูดถึง | **บังคับกรอกก่อนปิดงานด้วย `rejected`** |
| ยอดชุดสูงกว่าเดิม | เตือนแล้วกดผ่านได้ | **เกิน 2 เท่า = บล็อก** · ไม่เกินนั้นต้องกรอกเหตุผลและโชว์ส่วนต่าง |

**R1 เคลียร์แล้ว · R2 ยังต้องทำ · R3 แทนที่ด้วยข้อ Q1 ข้างบน · R4 ตอบแล้วด้วย D10**

เมื่อแก้แผนเป็น v3 ครบตามนี้ **อนุมัติให้เริ่มเขียนโค้ดได้ทันที ไม่ต้องส่งกลับมาตรวจอีกรอบ** —
ยกเว้นเจอเรื่องที่สเปคไม่ครอบคลุม ให้ถามก่อน อย่าเดา
