# WO-002 — RLS บนตารางตัวตน (เลื่อนมาจาก WO-001 ข้อ 12)

> **สถานะ: ค้างไว้โดยตั้งใจ · ทำหลัง Release 1 ขึ้นใช้จริง · ห้ามทำก่อน**
> ปิดจาก WO-001 เมื่อ 15 ก.ย. 2026 พร้อมเหตุผลที่ตรวจสอบแล้ว ไม่ใช่การหลบงาน

## ความเสี่ยงที่ยังเปิดอยู่

`users` · `sessions` · `shops` · `shop_memberships` · `owner_groups` **ไม่มี RLS**
แปลว่า query ที่หลุดออกไปนอก `withShop()` บนตารางพวกนี้ จะคืน**ทุกสาขาของทุกกลุ่มเจ้าของ**

ครึ่งที่ปิดไปแล้ว: `client.ts` แยก type เป็น `ScopedTx` / `GroupTx` / `UnscopedTx`
ทำให้ `unscoped()` หลุดไปใช้กับที่ต้อง scope สาขาไม่ได้ **โดย compiler เป็นคนจับ**
ครึ่งที่เหลือคือ RLS ซึ่งเป็นการกันซ้อนอีกชั้นเผื่อ type ถูกข้าม

## ทำไมถึงใส่ตอนนี้ไม่ได้

ทั้ง 5 ตารางถูกอ่าน **บนเส้นทางก่อนยืนยันตัวตน** ตอนที่ยังไม่รู้ทั้ง user และ shop
จึงไม่มี session variable ให้ policy อ้างอิง — ตรวจสอบจาก `apps/api/src/routes/auth.ts` จริง

| เส้นทาง | อ่านอะไรก่อนรู้สาขา |
|---|---|
| `/login` | `SELECT FROM users WHERE lower(login_id)=$1` แล้ว `membershipsOf()` ทุกสาขา |
| `/refresh` | `SELECT FROM sessions WHERE jti=$1` ก่อนรู้ทั้ง user และ shop |
| `/me` | `membershipsOf()` ต้องคืนทุกสาขา ไม่งั้นตัวสลับสาขาว่างเปล่า |

ใส่ `apply_tenant_rls('shop_memberships')` ตอนนี้ → ทุก query ข้างบนได้ 0 แถว เพราะ
`app.current_shop_id` ยังไม่ถูกตั้ง → **ไม่มีใครล็อกอินได้เลย รวมเจ้าของ** และทางกลับเข้าไป
คือ psql เป็น superuser ถ้าเกิดวันที่ 1 พ.ย. ที่อู่เปิดทำการอยู่ นี่คือผลลัพธ์ที่แย่ที่สุดที่เป็นไปได้

GUC แบบ `user_id = current_setting('app.current_user_id')` ก็ไม่ช่วย — ตัวแปรนั้นยังไม่มี
ไม่มีใครตั้ง และตั้งบนเส้นทาง login ไม่ได้อยู่ดี เพราะ user ยังไม่ถูกระบุจนกว่าจะอ่าน `users` เสร็จ

## ดีไซน์ที่ถูกต้อง — 4 ชิ้น ทำทีเดียวพร้อมกัน

1. **`SECURITY DEFINER` function สำหรับ login lookup** คืนแค่ `id` · `password_hash` · `is_active` · `name`
   ทำให้ช่องก่อนยืนยันตัวตนที่จำเป็นจริงๆ **แคบและตรวจสอบได้** แทนที่จะเป็นตารางเปิดโล่ง
2. **GUC `app.current_user_id`** ตั้งจาก middleware ตัวเดียวกับที่ตั้ง `app.current_shop_id`
3. **policy ที่ key บน GUC นั้น** + shop-scoped read ให้ผู้จัดการดูพนักงานสาขาตัวเองได้
4. **integration test ที่ล็อกอินจาก connection pool เย็น โดยไม่มี GUC ตั้งไว้เลย** — ก่อนเปิดใช้ที่ไหนก็ตาม

ข้อ 4 คือข้อที่ห้ามข้าม ถ้าไม่มีเทสนี้ เราจะรู้ว่าพังตอนที่พนักงานล็อกอินไม่ได้

## เกณฑ์ผ่าน

- [ ] ทั้ง 4 ชิ้นเสร็จพร้อมกัน — ทำครึ่งเดียวแล้ว deploy คือทำให้ระบบล็อกอินไม่ได้
- [ ] เทสข้อ 4 ผ่านจาก pool เย็น
- [ ] เทสว่าผู้จัดการสาขา A อ่าน `shop_memberships` ของสาขา B ได้ 0 แถว
- [ ] ซ้อม rollback บนสำเนาก่อน

# ระเบิดเวลาที่ต้องปลดตอนพอร์ต `jobs.ts`

`apps/api/src/routes/jobs.ts` (โค้ดยุค MySQL ที่ยังไม่ได้พอร์ต) เรียก

```ts
emitPublic('lookup:changed', { plateKey: ... })
```

ซึ่ง **ส่งทะเบียนรถเข้าห้อง public** ตอนนี้ไม่มีผลเพราะไฟล์นี้ไม่ได้ mount ใน `app.ts` และอยู่ใน
`exclude` ของ `tsconfig.json` — เป็นโค้ดตาย

**แต่วันที่มีคนพอร์ตหน้า jobs เข้าระบบจริง** ถ้าเอา `exclude` ออกแล้วไม่แก้ TypeScript จะบล็อกให้
(signature ใหม่ไม่รับ payload แล้ว) ซึ่งปลอดภัย — **แต่ไม่มีอะไรเตือนว่ามันเคยรั่วข้อมูลแบบนี้มาก่อน**
คนแก้อาจแค่ลบพารามิเตอร์ที่สองทิ้งเพื่อให้คอมไพล์ผ่าน โดยไม่รู้ว่านั่นคือบั๊กด้านความปลอดภัย

**เมื่อพอร์ต `jobs.ts`: อ่านทุกจุดที่เรียก `emitPublic` แล้วยืนยันว่าไม่มีข้อมูลลูกค้าไหลออก
ไม่ใช่แค่ทำให้คอมไพล์ผ่าน**
