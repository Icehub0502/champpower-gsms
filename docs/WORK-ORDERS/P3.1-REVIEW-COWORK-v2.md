## สรุป

ฉบับที่ 2 ตอบครบทั้ง 3 ข้อใหญ่และ 7 ข้อเล็ก และ**ดีกว่าที่ผมขอไว้ในหลายจุด**

## 0. ทีมแก้ผมถูกอีกครั้ง — บันทึกไว้

ในผลตรวจรอบแรกผมเขียนว่า *"ราคาจริงอยู่ใน `products` 1,374 แถว (97.9%)"*

ฉบับที่ 2 แย้งว่า **`products.price` คือต้นทุน ไม่ใช่ราคาขาย** พร้อมหลักฐาน:
หน้า `/product-costs` จำกัดด้วย `requireRole("office")` และคอมเมนต์ในโค้ดต้นแบบเองเขียนว่า
ตารางนี้ *"isn't kept in sync with what's actually sold"*

**ทีมถูก ผมผิด** ผมดูแค่ว่าคอลัมน์มีตัวเลข ไม่ได้ดูว่าหน้าจอไหนใช้มันและใครเห็นได้
ถ้าผมผ่านแผนรอบแรกไป **ต้นทุนจะไหลเข้าใบเสนอราคาและ advisor จะเห็นต้นทุนร้าน** ซึ่งผิด CLAUDE.md §12.2 ตรง ๆ

นี่เป็นครั้งที่สองที่ทีมจับข้อผิดของผมได้ — กลไก "คนเขียนห้ามรีวิวตัวเอง" กำลังทำงานถูกทาง
และมันใช้กับผมด้วย ไม่ใช่แค่กับ agent

## 2. เงื่อนไข 4 ข้อ ที่ต้องแก้ก่อน

### R1 — **ต้องยืนยันว่า D1–D16 ข้อไหน Ice ตัดสินจริง** 🔴 สำคัญที่สุด

แผน §2 พาดหัวว่า *"คำตัดสินของ Ice ที่แผนนี้ยึด (ทั้งหมดเป็นคำตอบสุดท้าย)"* แต่มีอย่างน้อย 4 ข้อ
ที่ผมไม่เคยเห็นผ่านตา และไม่มีในไฟล์คำตัดสินใด ๆ ใน `docs/WORK-ORDERS/`:

| | เรื่อง | ทำไมถึงต้องให้ Ice ยืนยัน ไม่ใช่สรุปเอง |
|---|---|---|
| **D10** | ลูกค้าตัดสินทั้งชุดครั้งเดียว ตัดบางชิ้นไม่ได้ | ขัดกับพฤติกรรมจริงของร้านที่อนุมัติทีละบรรทัด และของที่ขายดีที่สุดคือชุด |
| **D11** | พนักงานแก้ส่วนลดได้ตอนกดยืนยันผล | เปิดช่องแก้ยอดเงินหลังเอกสารมีเลขแล้ว |
| **D12** | รายการที่พิมพ์เอง **ติ๊กเพิ่มเข้าแคตตาล็อกไว้ให้แล้ว** | ค่าตั้งต้นเป็น "ใช่" แปลว่าแคตตาล็อกจะโตจากทุกครั้งที่พนักงานพิมพ์ผิด |
| **D13** | เพิ่มเหตุผลปฏิเสธ `chose_alternative` | เหตุผลปฏิเสธคือข้อมูลที่เจ้าของร้านใช้ตัดสินใจลงโฆษณา |

> กฎที่วางไว้แล้วคือ **ห้าม agent แก้ `CLAUDE.md` ตามคำบอกของ agent อื่น**
> หลักการเดียวกันใช้กับคำตัดสินทางธุรกิจ: **สิ่งที่ agent สรุปเอง ห้ามเขียนว่า "Ice ตัดสินแล้ว"**
> เพราะอีกสามเดือนจะไม่มีใครแยกออกว่าอันไหนเจ้าของร้านสั่ง อันไหนเครื่องเดาให้

**ต้องทำ:** แยก §2 เป็นสองตาราง — "Ice ตัดสินแล้ว (อ้างอิงไฟล์/วันที่)" กับ "ทีมเสนอ รอ Ice ยืนยัน"
ข้อที่ยังไม่ยืนยัน **ห้ามเขียนโค้ดที่ผูกกับมัน**

### R2 — **ราคาต่อรุ่นรถห้ามคีย์ด้วยข้อความอิสระ** 🔴

แผน §4.1 ให้ `catalog_model_prices` คีย์ด้วย `brand_key` + `model_key` ที่ normalise จาก
ยี่ห้อ/รุ่นที่เขียนอยู่บนทะเบียนรถ ซึ่งเป็น**ข้อความที่พนักงานพิมพ์เอง**

ผมนับของจริง:

| | |
|---|---|
| `vehicle_models` (รายการควบคุม) | **632 แถว · 80 ยี่ห้อ · 84% มีช่วงปี** |
| ยี่ห้อที่พนักงานพิมพ์จริงใน `vehicles` | 36 แบบ |
| **ในนั้นไม่มีอยู่ในรายการควบคุมเลย** | **13 แบบ** |

ตัวที่ไม่มีในรายการ:
```
Benz · Benze · Chevloret · Havel · Porche · Nissan 4 ประตู · Toyota HiLux · ยี่ห้อ:
```

`price_key()` แก้เรื่องตัวพิมพ์เล็กใหญ่ได้ (Toyota/toyota ซ้ำ 8 กลุ่ม) **แต่แก้คำสะกดผิดไม่ได้**

> ราคาที่ตั้งไว้ใต้ `Chevloret` จะไม่มีวันถูกค้นเจอเมื่อคันต่อไปถูกคีย์ว่า `Chevrolet`
> ตารางราคาจะแตกเป็นเสี่ยง ๆ แบบเงียบ ๆ โดยไม่มีใครรู้ — และ `ยี่ห้อ:` จะกลายเป็นยี่ห้อหนึ่งในตารางราคา

**ต้องทำ:** `catalog_model_prices` คีย์ด้วย **`vehicle_model_id` (FK ไปรายการรุ่นที่ควบคุม)**
ไม่ใช่ข้อความ · ตอนรับรถต้องจับคู่รถเข้ากับรายการรุ่น (จุดเดียวกับที่จับคู่ทะเบียน/ลูกค้าอยู่แล้ว)
· รถที่จับคู่ไม่ได้ → ใช้ `base_price` ไปก่อน และขึ้นในรายการ "รุ่นที่ยังไม่จับคู่" ให้คนมาเคลียร์

*(ช่วงปีไม่ต้องเป็นคีย์ — ข้อมูลจริงมีแค่ 1 คู่ที่ยี่ห้อ+รุ่นเดียวกันมีหลายช่วงปี เพราะชื่อรุ่นระบุรุ่นย่อยอยู่แล้ว เช่น "Civic FD" · เก็บช่วงปีไว้แสดงผลพอ)*

### R3 — **ไม่มีกฎว่าใบเสนอราคาที่ยังไม่ปิด จะเป็นยังไงเมื่องานจบแบบไม่ซ่อม** 🟡

งานจบได้ 2 ทางที่ไม่ใช่การซ่อม: `ไม่อนุมัติ` และ `เอารถลง`
แต่ `uq_live_quotation_per_job` บังคับว่าหนึ่งงานมีใบ live ได้ใบเดียว

แผนไม่ได้บอกว่าถ้างานจบแล้วแต่ใบยังเป็น `issued` อยู่ จะเกิดอะไรขึ้น
→ **ใบจะค้างเป็น live ตลอดไป** นับเข้า "รอลูกค้าตัดสินใจ" ตลอดไป และไปโผล่ใน attention view

**ต้องทำ:** กำหนดกฎให้ชัด — งานเข้าสถานะปิด (`rejected` / `carout`) ต้อง `void` ใบที่ยัง live
ใน transaction เดียวกัน พร้อมเหตุผลที่โยงกับเหตุผลปิดงาน · และมีเทสคุม

### R4 — **D10 ชุดตัดสินทั้งก้อน ต้องมีทางออกที่ชัด** 🟡

ถ้าลูกค้าบอกว่า *"เอาชุด แต่ไม่เอาตั้งศูนย์"* หลังออกใบไปแล้ว ทางเดียวคือออก revision ใหม่

ทางนั้นใช้ได้ **แต่ต้องยืนยันว่ามันเร็วจริง** — ถ้าออก rev ใหม่ต้องกดหลายขั้น พนักงานจะเลี่ยงด้วยการ
ไปแก้ที่อื่นหรือจดกระดาษ ซึ่งคือการเสียทั้งระบบ

**ต้องทำ:** ใส่เป็นเกณฑ์ผ่าน — *"ลูกค้าขอตัด 1 ชิ้นออกจากชุดหลังออกใบแล้ว → ออก rev ใหม่
และกลับมาอยู่จุดเดิมได้ภายในกี่คลิก"* แล้วจับเวลาเหมือนเกตชุดใน §7
(และข้อนี้ขึ้นกับ R1 — ต้องรู้ก่อนว่า Ice ตัดสิน D10 จริงไหม)

## 4. สิ่งที่อนุมัติแล้ว ไม่ต้องแก้ ไม่ต้องถกอีก

โครงสร้างชุดด้วย `parent_line_id` · ยอดนับเฉพาะบรรทัดแม่ · แกนแคตตาล็อก `category → item` ·
ไม่นำเข้า `quote_part_prices` และ `products.price` · ฟังก์ชันประกันเดียว · snapshot ประกัน ณ วันเสนอ ·
`list_price` คู่ `unit_price` คู่ `price_source` · วงจร draft→issued→signed และ trigger 0022 ·
ถอยการยืนยันแบบมีเงื่อนไขวัน + สถานะงาน + audit · ส่วนลดระดับเอกสารแต่แสดงเป็นบรรทัด ·
การแบ่งงานและผู้รีวิวตาม §14 · commit 3 ก้อน · เกณฑ์ผ่าน 10 ข้อ

## 5. เรื่องตารางเวลา — ต้องพูดตรง ๆ

แผนระบุเองว่า **ขนาดงานใหญ่กว่าฉบับแรกราว 1.5 เท่า** และวันนี้ 1 ต.ค. ยังไม่เริ่มเขียนโค้ด

**"บิลเป็นระบบหลัก 7 ต.ค." ไม่ทันแล้ว** และ P3.1 เป็นแค่ 1 ใน 3 ส่วนของบิล
(P3.1 ใบเสนอราคา · P3.2 มัดจำ · P3.3 ใบเสร็จ+พิมพ์)

ประมาณการใหม่ที่ผมเชื่อว่าทำได้จริง:

| | เดิม | ใหม่ |
|---|---|---|
| บิลพร้อมทดสอบ | 30 ก.ย. | **~15 ต.ค.** |
| บิลเป็นระบบหลัก | 7 ต.ค. | **~24 ต.ค.** |
| สต๊อก | 10 พ.ย. | 10 พ.ย. (ยังไม่ขยับ) |

ยังอยู่ในกรอบ 1 พ.ย. แต่ไม่มีที่ว่างเหลือแล้ว — **ถ้า P3.1 ใช้เวลาเกิน 5 วัน ต้องมาคุยกันเรื่องตัดขอบเขตอีกรอบ**
