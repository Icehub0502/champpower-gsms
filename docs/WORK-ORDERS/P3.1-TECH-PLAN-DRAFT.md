## 0. คำตัดสินที่ Ice ยืนยันแล้ว (ใช้เป็นฐานของแผนนี้)

| หัวข้อ | คำตัดสิน |
|---|---|
| ประเภทบรรทัด | 3 ประเภท: `part` (อะไหล่) / `labor` (ค่าแรง) / `fee` (ค่าบริการอื่น เช่น ค่าตั้งศูนย์ ค่าขนส่ง) — ตรงกับ CLAUDE.md §5.2 |
| ราคาต่อหน่วย | เป็น 0 ได้ (แจกฟรี/รอราคา) ติดลบไม่ได้ — ส่วนลดใช้ช่อง `discount` ระดับเอกสาร ไม่ใช่บรรทัดราคาติดลบ |
| "เลื่อน" (ลูกค้าบอกไว้ครั้งหน้า) | ใช้สถานะ "ปฏิเสธ" (`declined`) + เหตุผล `next_time` ("ไว้ครั้งหน้า") ที่มีอยู่แล้วใน enum ไม่เพิ่มสถานะใหม่ |
| แก้ใบหลังลูกค้าตัดสินบางบรรทัดแล้ว | **แก้ไม่ได้เลย** ต้องออก revision ใหม่เสมอ (ตรง CLAUDE.md §5.1 ข้อ 8) |
| งานเปลี่ยนเป็น "อนุมัติ" เมื่อไหร่ | เมื่อมีบรรทัดอนุมัติ ≥1 บรรทัด **และ** ไม่เหลือบรรทัดที่ยังไม่ตัดสินใจ (ไม่ pending) |
| ราคากลางของรุ่นรถใหม่ (หรือรุ่นที่มีแต่ยังไม่ตั้งราคา) | ราคาแรกที่พนักงานพิมพ์ **เขียนเป็นราคากลางทันที** ผ่าน endpoint แยกต่างหาก ไม่ปนกับการแก้ราคาปกติ · เฉพาะ `advisor` ขึ้นไปทำได้ · ทุกครั้งเข้า audit log |
| การแก้ราคาปกติ (รุ่นที่มีราคากลางอยู่แล้ว) | ไม่เขียนย้อนกลับตารางราคากลางเด็ดขาด ผูกกับใบเสนอราคาใบนั้นเท่านั้น (WO-005 §5.2) |
| Figma node 76 "Parts Editor" | ตรงกับแผง A (หน้าจอใน `JobDetailPage.jsx` ของต้นแบบที่พนักงานใช้ประจำทุกวัน) — ยกมาเฉพาะ layout/ลำดับช่อง/ปุ่ม ส่วนการดึงราคาอัตโนมัติต้องสร้างใหม่ทั้งหมด (ต้นแบบแผงนี้ไม่มีฟีเจอร์นี้เลย) |
| ลูกค้าปฏิเสธทุกบรรทัดแล้วกดยืนยัน | งาน**ไม่เปลี่ยนสถานะอัตโนมัติ** ยังค้างที่ "เสนอราคา" ให้พนักงานกด "ไม่อนุมัติ" เองอีกที |
| ออก revision ใหม่ บรรทัดที่เคยตัดสินใจแล้วใน rev เดิม | คัดลอกผลการตัดสินใจมาด้วย ลูกค้าตัดสินใจเฉพาะบรรทัดใหม่ที่เพิ่มเข้ามา ไม่ต้องให้ตัดสินซ้ำของที่ตกลงไปแล้ว |
| ใบสั่งงานช่างรอบนี้ | แค่ endpoint อ่านบรรทัดที่อนุมัติ (read-only) ยังไม่มีเลขที่เอกสาร — ของเต็มรูปแบบรอ phase พิมพ์จริง (P3.3) |

## 1. ผลวิจัยสำคัญที่เปลี่ยนสมมติฐานเดิม

ทีมที่อ่านต้นแบบ `เดสก์ท็อป\stock-system` ตรง ๆ (ไม่ใช่แค่อ่าน WO-005 สรุป) พบ 2 เรื่องใหญ่:

1. **ไม่มีหน้าจอ "Parts Editor" เดี่ยว ๆ ตามที่ WO-005 อ้างถึง** ต้นแบบมี 3 หน้าจอแยกกัน พฤติกรรมต่างกันคนละแบบ (แผงในหน้างานที่ใช้ประจำ / modal สำนักงานที่ดึงราคาได้ / modal บิลแยกสำหรับ "ทำทีหลัง") — ยืนยันแล้วว่า Figma 76 ตรงกับแผงแรก ซึ่ง**ไม่มีการดึงราคาอัตโนมัติอยู่เดิมเลย**
2. **ตารางราคา 71,556 แถวในระบบเก่า ไม่มีแถวไหนมีราคาจริงเลยสักแถว** ตรวจ dump ล่าสุด (12 ก.ย. 2026): ทุกแถว `needs_price=1`, `price=0.00` หมด เป็นโครงเปล่าจาก seed 534 รุ่น × 134 อะไหล่มาตรฐาน ไม่เคยมีใครตั้งราคาจริงเลย → ฟีเจอร์ "เลือกรุ่น→ราคาขึ้นเอง" จะไม่มีราคาให้ขึ้นจริงในวันแรก เป็นเหตุผลที่ Ice ตัดสินให้ใช้วิธี "ราคาแรกที่พิมพ์ = ราคากลาง" เพื่อให้ตารางค่อย ๆ เต็มเองจากงานจริง

**สรุปผลกระทบ**: งานนี้ "ยกหน้าจอมาก่อน" ทำได้แค่ layout/ลำดับช่องกรอก/ปุ่ม ตามที่ WO-005 อนุญาต แต่ตรรกะเรื่องราคาอัตโนมัติและอนุมัติทีละบรรทัดต้องสร้างใหม่เกือบทั้งหมด เพราะต้นแบบไม่มีของจริงให้ยก (ใช้เวลามากกว่าที่ WO-005 ทำให้เข้าใจตอนแรก)

**ห้ามยกบั๊กของต้นแบบมาด้วย**:
- เงินเป็น string จาก DB คำนวณด้วย float ทุกที่ (ขัด CLAUDE.md §4 ตรง ๆ)
- แก้ใบเสนอราคา = DELETE+INSERT บรรทัดทั้งหมด (id เปลี่ยนทุกครั้ง, ไม่มีประวัติการแก้เลย)
- ปุ่ม "ปิดการใช้งานบรรทัด" (ใกล้เคียง per-line decline ที่สุดที่มีอยู่) ไม่ถูกบันทึกจริง หายไปตอน save
- เหตุผลปฏิเสธเป็นระดับทั้งใบเท่านั้นในต้นแบบ ไม่มี per-line เลย — ส่วนนี้ GSMS ใหม่ต้องออกแบบเพิ่มเองทั้งหมด

## 2. Schema ที่มีอยู่แล้ว — ห้ามสร้างซ้ำ

งานนี้ที่ชั้นฐานข้อมูลส่วนใหญ่คือ "ต่อสาย" ไม่ใช่ "สร้างใหม่"

| รายการ | อยู่ที่ไหน |
|---|---|
| เอกสารเป็น snapshot แยกจากงาน | `documents` (migration 0004:14) สถานะ `draft/signed/issued/superseded/void` |
| draft ไม่มีเลข | `number` เป็น NULL จนกว่าจะออก — `ck_number_when_issued` (0004:95-97) บังคับไว้แล้ว |
| จองเลขที่เอกสาร | `allocate_document_number(shop,'QUO')` (0003:154) ใช้ `FOR UPDATE` บนแถว series — รูปแบบ `IV{YY}{MM}{DD}{SEQ:3}` รันใหม่ทุกวัน ตรงกับ WO-005 §2 อยู่แล้ว |
| ใบเสนอราคา live ได้ใบเดียวต่องาน | `uq_live_quotation_per_job` partial unique index (0011:78-81) |
| Revision | `revision`, `supersedes_document_id` (0004:38-39), `source_line_id` (0004:147) — trigger อนุญาต issued/signed→superseded แล้ว (0011:89) |
| สองยอด (เสนอ/อนุมัติ) | `offered_total`, `approved_total`, `discount`, `grand_total` numeric(12,2) ครบแล้ว (0004:58-66) |
| ประเภทบรรทัด | `line_type IN ('part','labor','fee')` **มีอยู่แล้วจริง** (0004:151) · `ck_labor_no_vat` ก็มีแล้ว (0004:182) |
| Line snapshot | `name_snapshot`, `brand_snapshot`, `qty`, `unit`, `unit_price`, `line_total` ครบ (0004:156-161) |
| การตัดสินใจรายบรรทัด | `approval_status` (pending/approved/declined), `decided_at`, `decline_reason` enum ตรงกับ CLAUDE.md §5.7, `decline_note` — ครบแล้วที่ 0004:166-185 |
| เสนอบรรทัดที่ปฏิเสธซ้ำครั้งหน้า | `vehicle_offered_items` (0004:203) |
| แจ้งเตือน "รอลูกค้าตัดสินใจ" | attention view มีแขนง `quote_pending` อ่าน `status='issued'` อยู่แล้ว (0015:216-224) |

### ช่องว่างจริงมีแค่ 3 จุด

1. **ตารางราคากลาง** — ไม่มีเลย ต้องสร้างใหม่
2. **`list_price` + `decided_by` บนบรรทัด** — คอลัมน์ที่ยังไม่มี
3. **จุด freeze ใหม่** — trigger ปัจจุบันล็อกทั้งเอกสารตอน `issued` แต่ลูกค้าตัดสินใจ**หลัง**เห็นเลขแล้ว (ไม่มีลายเซ็นให้ freeze ที่จุดนั้นอีกต่อไป) และบรรทัดยังไม่เคยถูกล็อกเลยแม้แต่ตอน issued — **เป็นช่องโหว่จริงที่ต้องปิด**: ตอนนี้บรรทัดของเอกสารที่ออกเลขแล้วยังแก้ได้

## 3. วงจรชีวิตของใบเสนอราคา (จุด freeze ใหม่ แทนลายเซ็น)

```
ร่าง (draft, ไม่มีเลข แก้ได้ทุกอย่าง)
  → ออกใบ: จองเลข IV… ตอนส่งให้ลูกค้าดู (draft → issued) · เนื้อหาบรรทัดถูกล็อก
  → บันทึกการตัดสินใจทีละบรรทัด: อนุมัติ / ปฏิเสธ+เหตุผล · เปลี่ยนใจได้จนกว่าจะกดยืนยัน
  → "ยืนยันผลลูกค้า" (issued → signed) = FREEZE ทุกช่อง
      เงื่อนไข: ต้องตัดสินครบทุกบรรทัดก่อนถึงจะกดได้
      ผล: มีบรรทัดอนุมัติ ≥1 → งานเปลี่ยนเป็น "อนุมัติ" อัตโนมัติ
           ปฏิเสธทุกบรรทัด → งานค้างที่ "เสนอราคา" ให้พนักงานกด "ไม่อนุมัติ" เอง (Ice ยืนยันแล้ว)
  → ลูกค้าขอเพิ่ม/แก้ภายหลัง = ออก rev ใหม่อ้างใบเดิม · ใบเดิมกลายเป็น superseded
      บรรทัดที่ตัดสินใจไปแล้วใน rev เดิม → คัดลอกผลการตัดสินใจมาด้วย (Ice ยืนยันแล้ว)
      ลูกค้าตัดสินใจเฉพาะบรรทัดใหม่ที่เพิ่มเข้ามาเท่านั้น
```

- ฐานข้อมูลบังคับเองด้วย trigger ไม่ใช่แค่ซ่อนปุ่มที่หน้าจอ — ยิง API ตรงก็แก้ไม่ได้
- ชื่อสถานะ `signed` ใช้ของเดิมที่มีอยู่แล้ว (แทนความหมาย "เอกสารถูกเซ็น" ด้วย "ลูกค้ายืนยันผลแล้ว") ไม่เพิ่มสถานะใหม่ เพราะถ้าเพิ่มต้องแก้ CHECK + partial unique index พร้อมกันทั้งคู่ เสี่ยงพลาดจุดใดจุดหนึ่ง

### ผลกระทบข้างเคียงที่ต้องแจ้ง (เปลี่ยนพฤติกรรมเดิม)

**ถอยสถานะงาน "อนุมัติ → เสนอราคา" จะถูกบล็อก (409) เมื่อใบเสนอราคา freeze (signed) แล้ว** ต้องออก revision ใหม่แทน ตาม CLAUDE.md §5 ข้อ 5 (ห้ามถอยสถานะย้อนหลังข้ามจุดที่ออกเอกสารเลขไปแล้ว) — ตอนนี้ปุ่มนี้กดได้อยู่ หลังงานนี้จะกดไม่ได้อีกต่อไป

## 4. Migration ที่เสนอ (0020–0022)

ทุกไฟล์ต้องผ่าน migration-safety ก่อนรัน, มีแผน rollback เขียนไว้บนหัวไฟล์ตามมาตรฐานโปรเจกต์

### 0020_price_book.sql
สร้างตาราง `part_prices` ต่อสาขา:
- `id`, `shop_id`, `brand`, `model`, `part_name`
- `brand_key`, `model_key`, `part_key` — `GENERATED ALWAYS AS (price_key(x)) STORED`
- `line_type` (part/labor), `unit_price numeric(12,2) CHECK (>=0)`, `unit`, `default_qty numeric(12,2)`
- `image_path`, `legacy_source`, `legacy_id` (รอข้อมูลจาก WO-004)
- `created_by`, `created_at`, `updated_at`, `deleted_at`
- ฟังก์ชัน `price_key(text)` — IMMUTABLE SQL function เดียว (trim + collapse whitespace + lower) ให้ generated columns และ lookup query เรียกใช้ร่วมกัน (เปลี่ยนทีหลังยาก เพราะจะ rewrite ทั้งตาราง ตั้งใจให้มินิมอล)
- `UNIQUE (shop_id, brand_key, model_key, part_key)` — ใช้กันอะไหล่ซ้ำ + WO-004 upsert บนคีย์นี้ · prefix ซ้ายสุด `(shop_id, brand_key, model_key)` คือ query หลักที่ WO-005 §5.4 ต้องใช้ ไม่ต้องทำ index แยก
- Partial unique `(shop_id, legacy_source, legacy_id) WHERE legacy_id IS NOT NULL` สำหรับ WO-004 §2.2
- `CALL apply_tenant_rls('part_prices')`
- Risk: ตารางใหม่ ไม่มี lock กระทบของเดิม

**การวัด index ก่อนใช้งานจริง** (ตาม CLAUDE.md §11): โหลดข้อมูลจำลอง 536 คู่ยี่ห้อ-รุ่น × จำนวนอะไหล่ (71,558 แถว) ลง 2 สาขาในฐานทดสอบ รัน `EXPLAIN (ANALYZE, BUFFERS)` ในฐานะ `gsms_app` ภายใต้ `SET LOCAL app.current_shop_id` (ให้ RLS predicate อยู่ใน plan ด้วย) วัด 4 query หลัก: ค้นอะไหล่ตาม (brand,model) / รายการรุ่นแบบ distinct / กรองชื่ออะไหล่ในรุ่นเดียว / รายการยี่ห้อ — เกณฑ์ผ่าน: index scan และไม่กี่ ms ฝั่ง server ไม่เพิ่ม index อื่นนอกจาก unique key เว้นแต่วัดแล้วไม่ผ่าน

### 0021_quote_line_pricing.sql
เพิ่มคอลัมน์ใน `document_lines`:
- `list_price numeric(12,2) NULL` — ราคากลางจากตารางราคา ณ ตอนที่ใส่บรรทัด (override คือ `unit_price <> list_price`)
- `price_source text CHECK IN ('price_book','manual')` — แยกบรรทัดที่มาจากตารางกับพิมพ์มือ
- `price_ref_id uuid REFERENCES part_prices ON DELETE SET NULL` — ไว้ตรวจสอบย้อนหลัง (การพิมพ์ยังอ่านจาก snapshot column เหมือนเดิม)
- `decided_by uuid REFERENCES users` — บันทึกว่าใครตัดสินใจบรรทัดนี้
- `CHECK ((approval_status='pending') = (decided_at IS NULL))` — เพิ่มแบบ `NOT VALID` แล้ว `VALIDATE` (ตารางว่างตอนนี้ costs nothing)
- ทุกคอลัมน์ nullable ไม่มี default → ล็อกตารางแค่ชั่วครู่ตอน ALTER

### 0022_quote_freeze.sql — **ไฟล์ที่เสี่ยงที่สุดในสามไฟล์**
- แก้ `documents_are_immutable()`: อนุญาตเฉพาะ `issued → signed` เปลี่ยนแค่ `status`, `signed_at`, `approved_total` คงกฎเดิมของ 0011 สำหรับ void/superseded ไว้ครบ
- สร้าง trigger ใหม่ `document_lines_are_immutable()` (BEFORE INSERT/UPDATE/DELETE):
  - parent = `draft` → แก้ได้ทุกอย่าง
  - parent = `issued` → แก้ได้เฉพาะ `approval_status`, `decided_at`, `decided_by`, `decline_reason`, `decline_note` ห้าม INSERT/DELETE
  - parent = `signed`/`superseded`/`void` → แก้อะไรไม่ได้เลย
- ความเสี่ยง: ถ้าคัดลอกเงื่อนไข superseded/void จาก 0011 ไม่ครบ จะเปิดช่องแก้เอกสารที่ปิดไปแล้ว — **ต้องมีเทส integration คุม**: update ราคาบนใบที่ issued แล้ว → error, issued→superseded ยังทำงานปกติ, void ยังทำงานปกติ
- SQLSTATE ใหม่สำหรับ error นี้ (รูปแบบ `GS002` ตาม registry §9.1) — **ต้องให้ Ice/Cowork เป็นคนอนุมัติเพิ่มลง CLAUDE.md เอง** agent จะไม่แก้ไฟล์นี้เองตามกติกาเดิม

## 7. ความเสี่ยง / สิ่งที่ต้องรู้ไว้

1. ต้นแบบไม่มีระบบดึงราคาอัตโนมัติและไม่มีการอนุมัติทีละบรรทัดให้ยกมาจริง — ตรรกะต้องสร้างใหม่เกือบทั้งหมด ใช้เวลามากกว่าที่ WO-005 ทำให้เข้าใจตอนแรก
2. ราคากลางจะว่างเปล่าในวันแรกเปิดใช้งานจริง (ข้อมูลต้นทางเป็น 0 ทั้งหมด) พนักงานต้องพิมพ์ราคาเองไปก่อนในช่วงแรก แล้วราคาจะค่อย ๆ สะสมเป็นราคากลางเอง
3. ยังไม่จองสต๊อกตอนอนุมัติ (CLAUDE.md §5.1 ข้อ 6) เพราะโมดูลสต๊อกยังไม่มา — เป็นช่องว่างที่รู้อยู่แล้วตั้งแต่ต้น จะบันทึกไว้ใน commit message ชัดเจน
4. SQLSTATE `GS002` ต้องรอ Ice/Cowork อนุมัติแก้ CLAUDE.md §9.1 เอง ก่อน 0022 จะเขียนโค้ดอ้างถึงได้
