## 1. ขอบเขต

**แก้ขอบเขต 3 ต.ค. 2026 (`DECISION-2026-10-03.md` §D.2 — Cowork อนุญาตให้ทีมใส่):**
- **ตัดออกจากขอบเขต:** `quote_part_prices` (โครงเปล่า) · `products.price` (ต้นทุน)
- **ประกัน:** ต้นแบบเก็บเป็นปี + เดือนแยกกัน → แปลงตอนนำเข้า
  > **Ice ตัดสิน 7 ต.ค. (`DECISION-2026-10-07.md`): หน่วยประกัน = วัน** (schema 0010 ถูกแล้ว ห้ามเปลี่ยนเป็นเดือน)
  > สูตรแปลง: **`days = warranty_year × 365 + warranty_month × 30`** · ข้อมูลจริง 596 แถวเป็น 1 ปีถ้วนทั้งหมด สูตรนี้แม่น 100%
  > ข้อความ "จำนวนเดือนรวม" ใน §D.2 ถูกแทนที่ด้วยคำตัดสินนี้
- **ราคา 0 ต้องแยกให้ออก:** `0` ที่แปลว่า "ยังไม่มีราคา" → นำเข้าเป็น **NULL** · `0` ที่แปลว่า "แจกฟรี" → คง `0`
  ถ้าแยกไม่ออกจากข้อมูลต้นทาง ให้เป็น NULL และออกรายงานให้คนมาดู
- **ส่วนลดที่เป็นบรรทัดราคาติดลบในต้นแบบ** → ไม่นำเข้าเป็นบรรทัด แต่รวมเป็น `documents.discount`
- **เพิ่มเกณฑ์ผ่าน:** งานเก่าที่สถานะ `scheduled` ต้องถูกแปลงก่อนเขียน — migration 0017 จะ RAISE ถ้ายังเหลือ (ตัวกันนี้มีอยู่แล้ว ห้ามปิด)

### ไม่นำเข้า — ตัดสินแล้ว ห้ามเปิดประเด็นใหม่
- ประวัติรายการทั้งหมด: `jobs` 292, `quotations` 482, `receipts` 358, `transactions` 476 และตารางลูกทั้งหมด
- **จำนวนสต๊อก** (`racks.stock_qty` / `wing_arms.stock_qty` รวม 1,035 ชิ้น) — พนักงานกรอกยอดตั้งต้นเองในระบบใหม่
  แต่ **ให้ export รายชื่ออะไหล่ 319 ตัวที่ qty > 0 ออกมาเป็นไฟล์แยก** ใช้เรียงลำดับหน้าจอกรอกยอดตอนทำเฟสสต๊อก
- `suppliers` — ไม่มีใน production เลย เริ่มจากศูนย์
- `job_photos` — เก็บเป็น path ไม่ใช่รูป ตัวไฟล์อยู่บน filesystem เซิร์ฟเวอร์ ไม่เกี่ยวกับ dump

## 2. กฎเหล็ก

1. **อ่านจาก dump ที่ restore ลงเครื่องเท่านั้น ห้ามต่อเข้าเซิร์ฟเวอร์ production เด็ดขาด** ไม่ว่ากรณีใด
2. **รันซ้ำได้ (idempotent)** — สคริปต์นี้จะถูกรันอย่างน้อย 2 ครั้ง: รอบทดสอบตอนนี้ และรอบจริงจาก dump ใหม่ราว 31 ต.ค.
   รันรอบสองต้อง **update ของเดิม ไม่ใช่สร้างซ้ำ** → ทุกแถวที่นำเข้าต้องมี `legacy_source` + `legacy_id` เป็นกุญแจ
3. **เขียนผ่าน `withShop(<สมุทรปราการ>)` เท่านั้น ห้ามใช้ `unscoped`** — RLS ต้องมีผลกับการนำเข้าเหมือนกับทุก path
4. **ใช้ blocklist ชุดเดียวกับ resolver** (`packages/domain` pure function + ตาราง `match_blocklist`)
   ห้ามเขียนกฎค่าหลอกชุดที่สองในสคริปต์นี้ ถ้าต้องแก้กฎ ต้องแก้ที่เดียวแล้วมีผลทั้งสองที่
5. **เจอข้อมูลกำกวม → ออกรายงาน ห้ามเดา** สคริปต์ไม่ตัดสินใจแทนคนแม้แต่แถวเดียว

## 3. การจับคู่ซ้ำ — ออกรายงานให้คนตัดสิน

ข้อมูลจริงที่ต้องเจอแน่ ๆ:

| อาการ | จำนวน |
|---|---|
| ทะเบียนซ้ำ | 9 กลุ่ม (เกินมา 12 แถว) — รวม `1กอ2222` ×4, `1กก1111` ×3 |
| เบอร์ซ้ำ | 8 กลุ่ม + `0999999999` ที่ใช้ซ้ำ 8 ราย |
| ชื่อซ้ำ | 50 กลุ่ม |

กติกา:
- **ชื่อ ห้ามใช้เป็นกุญแจจับคู่โดยเด็ดขาด** ชื่อไทยซ้ำกันเป็นเรื่องปกติ 50 กลุ่มนี้ส่วนใหญ่คือคนละคนจริง ๆ
- **รถทดสอบ `1กอ2222` ×4 และ `1กก1111` ×3 → ไม่นำเข้าเลย** (Ice ตัดสิน 30 ก.ย. 2026 — เป็นแถวทดสอบ ไม่ใช่รถลูกค้า)
  สคริปต์ต้องข้ามแถวเหล่านี้ตามรายการ legacy_id ที่ระบุชัด ไม่ใช่ตาม pattern ของทะเบียน และต้องพิมพ์รายการที่ข้ามลงรายงานนำเข้า
  **ก่อนข้าม ให้ตรวจว่ามีงาน/บิลจริงผูกอยู่หรือไม่** ถ้ามี ให้หยุดและถามก่อน อย่าตัดสินใจเอง
- เบอร์ที่ติด blocklist → **นำเข้าเป็นระเบียนแยกทุกแถว** เก็บค่าไว้ในระเบียนได้ แต่ห้ามใช้จับคู่
  (ทะเบียนไม่มีกฎ pattern แล้ว — ดู IMPORT-FINDINGS §4)
- **ราคาจากต้นแบบ (P3.1 · 1 ต.ค. 2026):** แถวราคาที่เป็น 0 หรือ `needs_price = 1` (โครงเปล่าของ `quote_part_prices`) และ `service_items` ที่ไม่มีราคา → **นำเข้าเป็นไม่มีราคา (ไม่มีแถว / `base_price = NULL`) ห้ามนำเข้าเป็น 0** เพราะในระบบใหม่ราคา 0 แปลว่า "แจกฟรีโดยตั้งใจ" และจะไม่ถูกแทนที่ด้วยราคาแรกที่พนักงานพิมพ์ · `products.price` คือต้นทุน ไม่นำเข้าเป็นราคาขาย (ดู `P3.1-TECH-PLAN-v3.md`)
- **เงื่อนไขประกัน:** ต้นแบบเก็บเป็นปี/เดือน + กม. → ระบบใหม่ `warranty_terms` (migration 0010) เก็บเป็น **`days` + `max_km`** · แปลงตอนนำเข้า (1 ปี = 365 วัน · 1 เดือน = 30 วัน — ถ้าบัญชี/เจ้าของต้องการนับต่างจากนี้ให้ถามก่อน) และลงรายงานนำเข้าว่าแปลงอะไรไปบ้าง
- **ข้อจำกัดที่ฐานข้อมูลบังคับ (migration 0020–0022):** snapshot ประกันบนบรรทัดต้องมาเป็นชุดที่สอดคล้องกัน — มีชื่อประกันเมื่อมี `warranty_term_id` · `warranty_days` / `warranty_max_km` มีได้เฉพาะเมื่อมีชื่อ และต้องมีอย่างน้อยหนึ่งค่า ค่าเป็นบวก (`ck_lines_warranty_snapshot`) · **`unit_price` ติดลบไม่ได้** (ส่วนลดของต้นแบบที่เป็นบรรทัดราคาติดลบ ต้องแปลงไปเป็น `documents.discount` ของเอกสารนั้น) · แถวที่ไม่ผ่านให้ลงรายงานนำเข้า ห้ามแก้ค่าเอง
- **เอกสารที่นำเข้า (ถ้ามี):** ต้องสร้างเป็น `draft` → ใส่บรรทัด → แล้วค่อยเปลี่ยนสถานะเป็น `issued`/`signed` · ห้าม INSERT บรรทัดเข้าเอกสารที่ไม่ใช่ draft ตรง ๆ — trigger ของ migration 0022 จะปฏิเสธด้วย `GS002`
- **จังหวัดของรถ** ระบบใหม่รับเฉพาะชื่อทางการ 77 จังหวัด (`THAI_PROVINCES` ใน `packages/domain`) และจับคู่รถด้วย (ทะเบียน, จังหวัด)
  ข้อมูลเดิมที่พิมพ์อิสระ → แปลงด้วย `normaliseProvince` ถ้าแปลงไม่ได้ **ให้เป็น NULL** แล้วลงรายงาน ห้ามนำเข้าข้อความดิบ
  (ข้อความดิบจะถูกนับเป็น "จังหวัดอื่น" เสมอ รถคันนั้นจะไม่มีวันถูกจับคู่หรือเติมจังหวัดได้)
- เบอร์/ทะเบียนที่ซ้ำและ **ไม่** ติด blocklist → เขียนลงไฟล์ `_import/review-duplicates.csv`
  คอลัมน์: ชนิด, ค่าที่ซ้ำ, legacy_id ของทุกแถวในกลุ่ม, ชื่อ, รุ่นรถ, วันที่สร้าง
  **นำเข้าแยกทุกแถวไปก่อน** แล้วให้คนมารวมทีหลังผ่านหน้าจอรวมลูกค้า — ไม่ใช่ให้สคริปต์รวมให้

## 4. จุดที่ต้องระวังเฉพาะตาราง

### `parts` — รวมสองตารางที่มีกุญแจคนละแบบ
production ไม่มีตาราง `parts` รวม (ตัวที่รวมอยู่ในสำเนา dev ไม่เคย deploy)
- `racks` ใช้ `model_code` เป็น unique
- `wing_arms` ใช้ `sku` เป็น unique + มี `position` / `axle` / `side`

รวมแล้วรหัสอาจชนกัน → ต้องเช็คก่อนและรายงานถ้าชน ห้าม overwrite เงียบ ๆ
เก็บ `legacy_source` = `rack` | `wing_arm` และ `legacy_id` ไว้ทุกแถว

### `customers` — สองคอลัมน์ที่ห้ามทิ้ง
- `found_via` / `found_via_note` — **เจ้าของร้านอยากได้รายงานว่าลูกค้ารู้จักอู่จากช่องทางไหน เพื่อตัดสินใจลงโฆษณา** ทิ้งไม่ได้
- `line_id` — จะใช้ตอนทำบอท LINE

### ~~`quote_part_prices`~~ — **ตัดออกจากขอบเขตแล้ว (3 ต.ค.)** เป็นโครงเปล่า มีราคาแค่ 1 แถว · ไม่นำเข้า

### `service_items` + `service_item_components`
- นับยืนยันหลังนำเข้า: 265 รายการ · 45 รายการย่อยในชุด ขาดแม้แถวเดียวถือว่าไม่ผ่าน
  **แก้ไข 16 ต.ค. (DECISION-2026-10-15 §3 ทาง A, อนุมัติผ่าน coordinator):** 265 = **นำเข้า 262 + ค้างใน `_import/review-duplicates-catalog.csv` 3** (คู่ซ้ำ 17/106, 201/234, 203/204 ชน `uq_catalog_items_name`) · ส่วนประกอบ 45 ครบ · บนฐานที่มีรายการทำมือชื่อชนกันอยู่แล้ว ตัวเลขจะลดลงตามจำนวนที่ชน และต้องขึ้นในรายงาน
  การรันซ้ำ: แก้ชื่อ/หมวด/สถานะด้วยมือจะถูกคืนเป็นค่าจาก dump · **ราคาที่พนักงานตั้งไว้ไม่ถูกทับ (ตั้งใจ)** — เกณฑ์ข้อ 5.3 ให้ทดสอบด้วยการแก้ชื่อ ไม่ใช่ราคา

## 5. เกณฑ์ผ่าน

1. รันรอบแรกบนฐานเปล่า → จำนวนแถวตรงทุกตารางตามตารางข้อ 1
2. **รันซ้ำทันทีรอบที่สอง → จำนวนแถวต้องไม่เปลี่ยนเลย** (พิสูจน์ idempotent)
3. แก้ข้อมูลในฐานปลายทาง 1 แถวด้วยมือ แล้วรันซ้ำ → แถวนั้นถูก update กลับ ไม่ใช่เกิดแถวใหม่
4. `_import/review-duplicates.csv` มีครบ 9 กลุ่มทะเบียน + 8 กลุ่มเบอร์
5. ลูกค้า 8 รายที่ใช้เบอร์ `0999999999` → **ต้องเป็น 8 ระเบียนแยกกัน** ไม่ใช่ 1
6. ไฟล์รายชื่ออะไหล่ 319 ตัวที่เคยมีของ ถูก export ออกมา
7. ทุก query ที่เขียนลงฐานวิ่งผ่าน `withShop` — ตรวจด้วยการ grep หา `unscoped` ในสคริปต์ ต้องไม่เจอ
8. รันทั้งหมดโดยเชื่อมต่อฐาน MySQL local เท่านั้น — ตรวจว่าไม่มี host ของ production ในโค้ดหรือ config
9. งานเก่าที่สถานะ `scheduled` ถูกแปลงก่อนเขียน — migration 0017 จะ RAISE ถ้ายังเหลือ (ห้ามปิดตัวกันนี้)
