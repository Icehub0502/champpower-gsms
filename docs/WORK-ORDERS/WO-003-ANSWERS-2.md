## 0. จุดที่ผมคิดผิด — status ของ `job_number_series_missing`

ผมกำลังจะสั่ง `422` gsms-lead กลับไป `500` ตามกฎเดิม — **gsms-lead ถูก ผมผิด**

`422` แปลว่า "payload ของคุณใช้ไม่ได้" แต่ payload ไม่ได้ผิดเลย สิ่งที่ผิดคือสถานะฝั่งเซิร์ฟเวอร์
ที่ client แก้ไม่ได้ไม่ว่าจะส่งอะไรมา — นั่นคือนิยามของ 5xx พอดี ผมกำลังจะแลกความถูกต้องของ
semantic กับความสวยของข้อความ error ซึ่งเป็นการแลกที่ผิด ข้อความที่มีประโยชน์ทำได้ใน body
ของ 500 อยู่แล้ว ไม่ต้องเปลี่ยน status

**ใช้ 500 ตามที่ gsms-lead สั่ง** และการขุดเจอว่า "ไม่มี endpoint สร้างสาขาที่ seed series เลย
ทั้ง repo" คือการวินิจฉัยที่ถูกจุดกว่าที่ผมเสนอ — ผมเสนอให้ปะที่ error handler gsms-lead ไปแก้
ที่ต้นตอ เอาตามนั้น

## 1. ข้อ arrive/checkin — เห็นด้วย และเหลืออีก 3 ช่อง

การตีกรอบใหม่ว่า **"รถมาถึง คือการรับรถที่บังเอิญมีใบจองติดมาด้วย"** ดีกว่าคำถาม (ก)/(ข)
ที่ตั้งไว้ตอนแรก และเหตุผลที่ว่าพนักงานจะเลี่ยงขั้นตอนที่สองด้วยการเปิด walk-in ใหม่ทับ
— นั่นคือบั๊กคิวซ้ำเดิมกลับมาทางประตูหลัง — เป็นเหตุผลที่หนักกว่าเหตุผลเรื่องความสะดวกที่ผมใช้

service ตัวเดียวสำหรับ `/checkin` และ `/bookings/:id/arrive` ยืนยันตามนั้น

แต่พอรวมเป็น service เดียวแล้ว **จะเกิดคำถามที่ทั้งสองทางเดิมไม่เคยต้องตอบ** เพราะตอนนี้
path เดียวนี้สร้าง customer/vehicle ได้เอง ต้องตอบ 3 ข้อนี้ก่อนเขียน ไม่งั้นมันจะกลายเป็น
เครื่องผลิตข้อมูลซ้ำ:

### 1.1 ทะเบียนซ้ำแต่คนละเจ้าของ — **ห้ามย้ายเจ้าของเงียบ ๆ**
resolve รถด้วย `(shop_id, plate_norm)`
- ไม่เจอ → สร้างใหม่
- เจอ เจ้าของตรง → ใช้คันนั้น
- **เจอ เจ้าของไม่ตรง → 409 `vehicle_owner_mismatch`** ส่งชื่อเจ้าของเดิม + ใหม่กลับไป
  จะย้ายได้ต้องยิงซ้ำพร้อม `confirm_owner_change: true` และบันทึกลง audit

ข้อนี้สำคัญที่สุดในสามข้อ รถขายต่อ/ญาติเอามาแทน เป็นเรื่องปกติในอู่ ถ้าระบบย้ายเจ้าของอัตโนมัติ
ประวัติซ่อมของลูกค้าสองคนจะถูกเทรวมกันโดยไม่มีใครรู้ตัว และกู้คืนแทบไม่ได้ ยอมให้ 409 ขัดจังหวะ
2 วินาที ดีกว่ามาก — อันนี้ 409 ถูกต้องจริง เพราะแก้คำขอแล้วยิงใหม่ผ่านได้

### 1.2 เบอร์เดียวกันหลายราย
resolve ลูกค้าด้วย `(shop_id, phone_norm)` — เจอหลายราย → `409 customer_ambiguous`
พร้อม candidates ให้ UI เลือก แล้วยิงซ้ำด้วย `customer.id` ห้ามเดาเอาคนแรก

### 1.3 backfill กลับไปที่ booking
เมื่อ resolve ได้แล้ว เขียน `customer_id` / `vehicle_id` **กลับลง `bookings` ด้วย**
ในทรานแซกชันเดียวกับที่สร้าง job ไม่ใช่ใส่แค่ใน `jobs` — ไม่งั้นใบจองกับใบงานจะเล่าคนละเรื่อง
และรายงานที่นับจากฝั่ง booking จะเพี้ยน

> ทั้ง 3 ข้อต้องอยู่ในทรานแซกชันเดียวกับการสร้าง job ไม่มีสถานะครึ่ง ๆ กลาง ๆ

## 2. T6 — พอร์ต auth ฝั่งเว็บ: **อนุมัติ**

อยู่บนเส้นทางวิกฤตของ WO-003 ไม่ใช่งานแถม เปิดหน้าคิวในเบราว์เซอร์ไม่ได้ = ปิด WO ไม่ได้

แต่ชั้นนี้คือชั้นที่ผมเขียนพลาดมาแล้ว 15 จุดใน WO-001 จึงมีเงื่อนไขที่ไม่ยืดหยุ่น 7 ข้อ:

1. **access token อยู่ใน memory เท่านั้น** ห้าม `localStorage` / `sessionStorage` เด็ดขาด
2. **refresh token เป็น httpOnly + Secure + SameSite=Lax cookie ที่ API เป็นคนตั้ง**
   ห้ามส่งกลับมาเป็น JSON ให้ JS ถือ — ต้องแก้ฝั่ง API เล็กน้อย ยอมแก้ตอนนี้ถูกกว่าย้อนมาแก้ทีหลัง
   เพราะนี่คือเส้นแบ่งระหว่าง "โดน XSS = เสีย session 30 วัน" กับ "เสีย 15 นาที"
3. **refresh ต้อง single-flight** — 401 หลายอันพร้อมกันต้องรอ promise ก้อนเดียว
   WO-001 ใส่ refresh rotation ไว้แล้ว ถ้าไม่ทำข้อนี้ระบบจะเตะผู้ใช้ออกทันทีที่ยิงขนาน ไม่ใช่ "อาจจะ"
4. **สลับสาขาต้องล้าง cache ของ query ทั้งหมด** ไม่งั้นคิวของสาขา A จะโผล่ใต้สาขา B
   — RLS ฝั่ง DB ถูกแล้วก็ยังรั่วได้ที่ฝั่ง UI
5. **logout ต้องเรียก API เพื่อ revoke session** ไม่ใช่แค่ทิ้ง token ในเบราว์เซอร์
6. **ห้ามมี token ใน URL / query string** ไม่ว่ากรณีใด
7. route guard ต้องมีสถานะ "กำลังตรวจสอบ" ห้ามให้หน้าที่ต้องล็อกอินแวบขึ้นมาก่อนแล้วค่อยเด้งออก

**และตาม CLAUDE.md §14: ห้าม engineer คนที่เขียนเป็นคนรีวิวเอง** งานนี้ต้องผ่าน security review
จาก agent คนละตัว ก่อนนับว่าเสร็จ — เหมือน WO-001 ไม่มีข้อยกเว้นเพราะ "ฝั่งเว็บบางกว่า"

เกณฑ์ผ่านของ T6: ล็อกอินจริงในเบราว์เซอร์ เปิดหน้าคิวได้ สลับสาขาแล้วข้อมูลเปลี่ยนตาม
ทิ้งไว้เกิน 15 นาทีแล้วยังใช้งานต่อได้โดยไม่ต้องล็อกอินใหม่ และ **ตรวจด้วยตาที่ 390px**
