# คำตัดสิน — สถานะงานและป้ายบนการ์ด

22 ก.ย. 2026 · ตอบรายงาน 3 ข้อของ agent (อ่าน Figma 51–58 และ 80)
**อนุมัติให้ลง migration ได้หลังแก้ตามนี้**

---

## 1. ชื่อสถานะทั้ง 8 — **ยืนยันตามที่รายงาน ไม่แก้**

```
รับรถ → ตรวจเช็ก → เสนอราคา → อนุมัติ → กำลังซ่อม → รอตั้งศูนย์ → พร้อมส่ง → ส่งแล้ว
```

วิธีที่ใช้ยืนยัน (ตรวจ KPI ให้ยอดตรง 18 = 6+6+3+3) ถูกต้อง — นั่นคือการพิสูจน์ ไม่ใช่การเดาจากหัวคอลัมน์
ทำแบบนี้ต่อไป

---

## 2. การจับกลุ่ม 4 คอลัมน์ — **แก้ 1 จุด: `อนุมัติ` ย้ายไปคอลัมน์ 3**

| คอลัมน์ | หัวคอลัมน์ | สถานะที่ครอบ |
|---|---|---|
| 1 | รับรถ / ตรวจรับ | `รับรถ` |
| 2 | ตรวจเช็ก / รออนุมัติ | `ตรวจเช็ก` · `เสนอราคา` |
| 3 | กำลังซ่อม / ตั้งศูนย์ | **`อนุมัติ`** · `กำลังซ่อม` · `รอตั้งศูนย์` |
| 4 | พร้อมชำระ / ส่งมอบ | `พร้อมส่ง` · `ส่งแล้ว` |

### เหตุผล

คอลัมน์ 2 มี KPI กำกับว่า **"รอลูกค้าตัดสินใจ"** แต่ `อนุมัติ` แปลว่า**ลูกค้าตัดสินใจไปแล้ว**

ถ้าปล่อยไว้คอลัมน์ 2:

- KPI "รอลูกค้าตัดสินใจ" จะนับเกิน
- **พนักงานจะโทรตามลูกค้าที่ตอบตกลงไปแล้ว** — เสียเวลาทั้งสองฝ่าย และดูไม่เป็นมืออาชีพ

`อนุมัติ` ไม่ใช่สถานะที่รถนั่งรอ มันคือ*จังหวะ*ที่ผ่านไปแล้ว รถที่อนุมัติแล้วคือ**งานที่ต้องลงมือทำ**

### KPI ต้องนิยามตามตารางนี้ ไม่ใช่ตามจำนวนในดีไซน์

ตัวเลขในดีไซน์เป็นข้อมูลตัวอย่าง อาจไม่มีการ์ดสถานะ `อนุมัติ` อยู่เลย
**นับจากสถานะจริงตามตารางข้างบน** ห้าม hardcode เลขจากภาพ

---

## 3. `ส่งแล้ว` ชนกัน — **เปลี่ยนเป็น `ส่งราคาแล้ว`**

agent เจอถูกแล้วว่า `ส่งแล้ว` ในคอลัมน์ 2 (= ส่งใบเสนอราคาทาง LINE) ชนกับสถานะ 58 `ส่งแล้ว` (= ส่งรถคืนลูกค้า)

**แต่การแก้ด้วยการเก็บคนละฟิลด์ แก้แค่ปัญหาของโค้ด ไม่ได้แก้ปัญหาของคน**

บนกระดานเดียวกันจะมีการ์ดสองใบติดป้ายคำเดียวกันเป๊ะ แต่ความหมายตรงข้าม — ใบหนึ่ง "เพิ่งส่งราคา ยังไม่ทำอะไร"
อีกใบ "จบงาน รถออกจากอู่แล้ว" พนักงานกวาดตาตอนยุ่งจะอ่านผิดแน่นอน

**Ice ตัดสิน: เปลี่ยนป้ายในคอลัมน์ 2 เป็น `ส่งราคาแล้ว` ทั้งในโค้ดและใน Figma**
สถานะ 58 `ส่งแล้ว` คงเดิม

## 4. ป้ายบนการ์ด — **ไม่เอา free text**

ผมไม่เห็นด้วยกับข้อเสนอให้เก็บเป็นข้อความอิสระ เพราะป้ายพวกนี้ไม่ได้เป็นของชนิดเดียวกัน:

| ป้ายในดีไซน์ | แท้จริงคือ | เก็บไหม |
|---|---|---|
| `นัด 09:00` · `Walk-in` | มาจากใบจอง | **คำนวณ** |
| `ช่อง H2` · `ช่อง A1` | คือ `jobs.bay` ที่มีอยู่แล้ว | **มีอยู่แล้ว ห้ามเก็บซ้ำ** |
| `เหลือ 28 นาที` · `เกิน SLA 12 นาที` | คำนวณจากเวลา | **คำนวณ** |
| `รอลูกค้า` `ต้องโทร` `ส่งราคาแล้ว` `กำลังรออะไหล่` `รอตรวจ QC` `รอล้างรถ` `ชำระแล้ว` | สถานะย่อยจริง | **เก็บ เป็น enum** |

### `jobs.sub_state` — enum, nullable

```
waiting_customer  = รอลูกค้า
call_customer     = ต้องโทร
quote_sent        = ส่งราคาแล้ว
waiting_parts     = กำลังรออะไหล่
waiting_qc        = รอตรวจ QC
waiting_wash      = รอล้างรถ
paid              = ชำระแล้ว
```

**เหตุผลที่ต้องเป็น enum ไม่ใช่ free text:**

> ถ้าเป็นข้อความอิสระ จะตอบคำถามนี้ไม่ได้ตลอดไป — **"ตอนนี้มีรถกี่คันติดรออะไหล่"**
> ทั้งที่อู่สั่งอะไหล่พิเศษเป็นประจำ และเก็บมัดจำสำหรับอะไหล่สั่งพิเศษด้วย
> ของที่นับไม่ได้ คือของที่จัดการไม่ได้

คู่ `(status, sub_state)` ที่ใช้ได้ ให้ตรวจใน `packages/domain` พร้อมเทส **ไม่ต้องผูกเป็น constraint ใน DB**
(จะได้เพิ่ม/แก้ทีหลังโดยไม่ต้อง migration)

### ช่องป้ายบนการ์ด = ช่องแสดงผล เลือกตามลำดับ

```
1. มี sub_state           → โชว์ sub_state
2. ไม่มี แต่มี bay        → โชว์ "ช่อง {bay}"
3. ไม่มีทั้งคู่ + มีใบจอง  → โชว์ "นัด HH:MM"
4. ไม่มีอะไรเลย           → โชว์ "Walk-in"
```

ตัวนับเวลา/SLA เป็นคนละที่ (มุมขวาล่างของการ์ดตามดีไซน์) ไม่ใช่ช่องป้ายนี้
