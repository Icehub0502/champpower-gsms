## 0. ข่าวดี — **schema มีครบแล้ว งานนี้คือ "ต่อสาย" ไม่ใช่ "ออกแบบ"**

migration **0006** สร้างไว้หมดแล้วตั้งแต่ต้น ห้ามสร้างตารางซ้ำ:

| ตาราง | หน้าที่ | สถานะ |
|---|---|---|
| `skus` | อะไหล่ · `code` · `unit` · `stocking_policy` · `reorder_point` · `shelf_location` | ✅ มีแล้ว |
| `stock_moves` | **ledger แบบเพิ่มได้อย่างเดียว** type: `receipt`/`reserve`/`unreserve`/`issue`/`return`/`adjustment`/`count`/`transfer_*` · `idempotency_key` UNIQUE · `ref_type`/`ref_id`/`ref_line_id` · บังคับ `reason` เมื่อเป็น adjustment · มี trigger กันแก้ย้อนหลัง | ✅ มีแล้ว |
| `stock_balances` | `on_hand` · `reserved` · `avg_cost` · CHECK ห้ามติดลบทั้งคู่ | ✅ มีแล้ว |
| `stock_available` | view (`security_invoker = true`) | ✅ มีแล้ว |
| `purchase_suggestions` | ของขาดตอนอนุมัติ → ขึ้นรายการเสนอซื้อ | ✅ มีแล้ว |
| `stock_lots` · `stock_counts` · `stock_count_lines` | lot/serial · นับตามรอบ | ✅ มีแล้ว — **นอกขอบเขต Release 1 ห้ามแตะ** |

**ของที่ออกแบบไว้ดีมากตั้งแต่แรกและต้องใช้ให้คุ้ม:** `idempotency_key` UNIQUE บน `stock_moves`
→ ยิงซ้ำสองครั้งตัดสต๊อกครั้งเดียว · นี่คือสิ่งที่กันบั๊ก "ตัดของซ้ำ" ที่เจ็บที่สุดในระบบสต๊อก

## 1. ปัญหาเดียวที่ต้องแก้ก่อนเริ่ม — **ตอนนี้มีแคตตาล็อกสองชุด**

| | สร้างเมื่อ | คีย์ | ใช้ทำอะไร |
|---|---|---|---|
| `skus` | 0006 | `(shop_id, code)` | ของในสต๊อก |
| `catalog_items` | **0020 (P3.1 เพิ่งทำ)** | `(shop_id, category, name_key)` | ของที่ขาย/เสนอราคา |

**สองตารางนี้ไม่มีอะไรเชื่อมกันเลย** — อะไหล่หนึ่งตัวจะอยู่ทั้งสองที่ ไม่รู้ว่าเป็นตัวเดียวกัน

> ถ้าปล่อยไว้ **จะเกิดปัญหาเดียวกับที่เราเพิ่งแก้ไปเรื่องราคา** คือข้อมูลแตกเป็นสองชุด
> แล้ววันหนึ่งพนักงานถามว่า "ปีกนกล่างเหลือกี่ชิ้น" แล้วระบบตอบไม่ได้
> เพราะใบเสนอราคารู้จักมันในชื่อหนึ่ง สต๊อกรู้จักมันในอีกรหัสหนึ่ง

### migration 0023 — เชื่อมสองตาราง

```sql
ALTER TABLE catalog_items
  ADD COLUMN sku_id uuid,
  ADD CONSTRAINT fk_catalog_sku FOREIGN KEY (shop_id, sku_id)
    REFERENCES skus (shop_id, id) ON DELETE RESTRICT;
```

กติกา:
- `line_type = 'part'` → **ควร**มี `sku_id` · ไม่มี = ขายได้แต่ไม่ตัดสต๊อก (ขึ้นในรายการ "ยังไม่ผูกสต๊อก")
- `line_type = 'labor'` / `'fee'` → `sku_id` ต้องเป็น NULL เสมอ (ค่าแรงไม่มีสต๊อก) — บังคับด้วย CHECK
- หน้าจอแคตตาล็อกต้องผูก sku ได้ และสร้าง sku ใหม่จากหน้านั้นได้เลย
- `skus` ต้องมี FK แบบปลอดภัยต่อสาขา `(shop_id, id)` เหมือนที่ 0021 ทำกับ warranty_terms

## 2. "ยังไม่ตั้งยอด" ต่างจาก "ศูนย์" — **ไม่ต้องแก้ schema**

Ice ตัดสินไว้ว่าไม่นำเข้าจำนวนสต๊อกจากระบบเก่า พนักงานตั้งยอดเอง
และต้องแยก **"ยังไม่เคยนับ"** ออกจาก **"นับแล้วเหลือศูนย์"** ให้ได้

**คำตอบอยู่ในโครงที่มีอยู่แล้ว:**

| สภาพ | ความหมาย |
|---|---|
| **ไม่มีแถวใน `stock_balances`** | **ยังไม่ตั้งยอด** — ห้ามเตือนว่าของหมด ห้ามบล็อกการขาย |
| มีแถว `on_hand = 0` | นับแล้ว และหมดจริง — **เตือนได้** |

ห้ามสร้างแถวใน `stock_balances` ให้อัตโนมัติตอนสร้าง sku — แถวเกิดครั้งแรกเมื่อมี `stock_moves` แรกเท่านั้น

### การตั้งยอดตั้งต้น
- `stock_moves` type `count` · `reason` บังคับ · `idempotency_key` ผูกกับ (sku, user, วันที่)
- หน้าจอ: รายการอะไหล่ + ช่องใส่จำนวน **เรียงตามที่เคยมีของจริงก่อน** (319 ตัวจาก 512 ที่ระบบเก่ามียอด > 0)
  — ให้ของที่ใช้จริงขึ้นก่อน ไม่ใช่เรียง ก-ฮ แล้วพนักงานเลื่อนผ่านของที่ไม่มีวันมี
- ตั้งยอดได้ทุกเมื่อ ไม่ใช่แค่ครั้งแรก · ทุกครั้งเข้า audit

## 3. จองของตอนลูกค้าอนุมัติ — **จุดที่ต้องระวังที่สุด**

เป็นรายการที่ตัดออกจาก P3.1 (DECISION-Q1-Q2 §8.7) ตอนนี้ถึงเวลาทำ

### จองที่ไหน
ตอนกด **"ยืนยันผลลูกค้า"** (`confirm`) ใน transaction เดียวกัน — ไม่ใช่ตอน issue ไม่ใช่ตอนสร้างใบ

### จองอะไร — **บรรทัดย่อย ไม่ใช่บรรทัดแม่**
> ชุดโปรช่วงล่างมีบรรทัดแม่ 1 + บรรทัดย่อย 6
> **ของจริงที่ต้องหยิบจากชั้นคือบรรทัดย่อย** บรรทัดแม่เป็นแค่ราคา ไม่ใช่ของ
> ถ้าจองที่บรรทัดแม่ จะจองของผิดตัวและผิดจำนวนทุกครั้งที่ขายชุด ซึ่งคือ 40% ของบรรทัดทั้งหมด

กติกา:
1. จองเฉพาะบรรทัดที่ `approval_status = 'approved'` **และ** `line_type = 'part'` **และ** มี `sku_id`
2. บรรทัดย่อยที่ถูกปฏิเสธ (ลูกค้าตัดออกจากชุด) → **ไม่จอง**
3. บรรทัดแม่ของชุด → ไม่จองเอง จองผ่านบรรทัดย่อยเท่านั้น
4. `stock_moves` type `reserve` · `ref_type='document_line'` · `ref_id`/`ref_line_id` ชี้กลับได้
5. `idempotency_key` = `reserve:{document_line_id}` → **กดยืนยันซ้ำสองครั้ง จองครั้งเดียว**

### ของไม่พอ — **เตือน ไม่บล็อก**
ตามที่ Ice ตัดสินไว้นานแล้ว: อนุญาตให้อนุมัติ · เตือน · สร้าง `purchase_suggestions` (`origin='shortfall'`)
**ห้ามบล็อกการขายเพราะสต๊อกไม่พอ** อู่สั่งของมาเพิ่มได้

ของที่ `stocking_policy = 'buy_to_order'` → ไม่ต้องเตือนเลย ตั้งใจไม่สต๊อกอยู่แล้ว

### คืนของจองเมื่อไหร่
| เหตุการณ์ | ทำ |
|---|---|
| ถอยการยืนยัน (`confirm/undo`) | `unreserve` ทุกบรรทัดที่จองไป · key = `unreserve:{line_id}:{undo_seq}` |
| งานจบด้วย `rejected` / `carout` | `unreserve` ทั้งหมด ใน transaction เดียวกับการปิดงาน |
| ออก revision ใหม่ | `unreserve` ของใบเดิม แล้วจองใหม่ตามใบใหม่ |
| เบิกของจริง | `issue` **และ** `unreserve` ในก้อนเดียวกัน (ของย้ายจาก reserved → ออกจากคลัง) |

## 4. เบิกของ

- เบิกตอน**ของกองรออยู่หน้าห้องสต๊อก** ไม่ใช่ตอนช่างเริ่มทำ (ตามที่ Ice เล่าไว้ว่าพนักงานออฟฟิศเป็นคนกด)
- `stock_moves` type `issue` + `unreserve` คู่กัน · `idempotency_key` = `issue:{document_line_id}`
- เบิกได้เฉพาะบรรทัดที่อนุมัติแล้ว
- เบิกเกินที่จองไว้ → เตือนและต้องยืนยัน (เช่น ของเสียระหว่างติดตั้ง)
- **สแกน QR — อยู่ใน "ถ้าเหลือเวลา"** ทางที่การันตีคือค้นหาแล้วเลือก · ถ้าทำ ให้ `skus.code` เป็นค่าใน QR

## 5. ปรับยอดด้วยมือ

- `stock_moves` type `adjustment` · **`reason` บังคับอยู่แล้วด้วย CHECK ในฐานข้อมูล** (0006 ทำไว้แล้ว)
- สิทธิ์: พนักงานออฟฟิศขึ้นไป (Ice ยืนยันไว้ว่าออฟฟิศปรับยอดได้)
- audit ทุกครั้ง เก็บ ยอดเดิม → ยอดใหม่ → เหตุผล → ใคร
- ปรับให้ติดลบไม่ได้ (CHECK ใน `stock_balances` กันอยู่แล้ว — แต่ต้องมีด่าน domain ข้างหน้าตอบ 409 ตาม CLAUDE.md §4.y)

## 8. เกณฑ์ผ่าน

1. อนุมัติใบที่มีชุด 1 ชุด (ย่อย 6) → เกิด `reserve` **6 รายการ ไม่ใช่ 7** และไม่มีรายการของบรรทัดแม่
2. ลูกค้าตัดบรรทัดย่อยออก 1 → `reserve` **5 รายการ**
3. **กดยืนยันซ้ำสองครั้งติดกัน → `stock_moves` เพิ่มครั้งเดียว** (พิสูจน์ `idempotency_key`)
4. ถอยการยืนยัน → `unreserve` ครบทุกตัว · `reserved` กลับเป็นค่าเดิมเป๊ะ
5. ปิดงานด้วย `carout` ขณะมีของจองอยู่ → คืนครบ ใน transaction เดียว
6. ของไม่พอ → อนุมัติได้ + มีเตือน + เกิด `purchase_suggestions` 1 แถว
7. อะไหล่ที่ยังไม่ตั้งยอด → **ไม่ขึ้นในรายการของใกล้หมด** และขายได้ตามปกติ
8. ตั้งยอดเป็น 0 → **ขึ้นในรายการของใกล้หมด** (ต่างจากข้อ 7 ชัดเจน)
9. ปรับยอดโดยไม่กรอกเหตุผล → 409 ไม่ใช่ 500
10. advisor เรียกทุก endpoint → ไม่มีต้นทุนหลุดออกมาสักตัว
11. เทสสองร้าน: ร้าน A มองไม่เห็นสต๊อกร้าน B ทุก endpoint
12. ตรวจด้วยตาที่ 390 / 820 / 1180 / 1440

ตาม CLAUDE.md §14: คนเขียนห้ามรีวิวเอง · §4.x ลำดับล็อก `jobs` → `documents` → `document_lines` → สต๊อก
