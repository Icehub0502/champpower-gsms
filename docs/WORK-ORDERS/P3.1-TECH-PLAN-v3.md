## 3. ชุด/แพ็กเกจ [v3 — D10]

โครงสร้างเดิมจาก v2 §3.1–3.2 คงไว้ (`catalog_set_components` · `parent_line_id` ในเอกสารเดียวกัน · server กางชุด · บรรทัดย่อย `unit_price = 0` · ยอดนับเฉพาะบรรทัดแม่)

### 3.1 การตัดสินใจในชุด — กฎใหม่
| การกระทำ | ผล |
|---|---|
| อนุมัติบรรทัดแม่ | บรรทัดย่อยที่ยัง `pending` กลายเป็น `approved` · บรรทัดย่อยที่ปฏิเสธไว้แล้ว**คงปฏิเสธ** |
| ปฏิเสธบรรทัดแม่ (พร้อมเหตุผล) | บรรทัดย่อย**ทั้งหมด**ปฏิเสธตาม ด้วยเหตุผลเดียวกัน |
| ปฏิเสธบรรทัดย่อย (พร้อมเหตุผล) | **รับ** — ไม่ใช่ 409 แบบ v2 · บรรทัดแม่ไม่เปลี่ยน |
| ปฏิเสธบรรทัดย่อยครบทุกบรรทัด | บรรทัดแม่ปฏิเสธเองอัตโนมัติ · เหตุผลของแม่ = เหตุผลเดียวกันถ้าย่อยทุกบรรทัดใช้เหตุผลเดียวกัน ไม่งั้นใช้ `other` + โน้ต "ปฏิเสธครบทุกรายการในชุด" |
| อนุมัติบรรทัดย่อยที่เคยปฏิเสธ | ได้ ระหว่างที่ใบยังเป็น `issued` · ถ้าแม่ถูกปฏิเสธอัตโนมัติไว้ แม่กลับเป็น `pending` |

กฎทั้งหมดอยู่ในฟังก์ชันเดียวใน `packages/domain` (`applySetDecision`) ที่ API เรียกภายใน transaction เดียว · หน้าจอแสดงผลตามที่ server คืนมา ไม่คำนวณเอง

### 3.2 ยอดของชุดที่ถูกตัดบางชิ้น
- เงื่อนไข: บรรทัดแม่ `approved` และมีบรรทัดย่อย `declined` ≥ 1
- ก่อนกด "ยืนยันผลลูกค้า" **ต้องกรอกยอดใหม่ของชุด** (`approved_amount`) พร้อมเหตุผล — ไม่กรอก = ยืนยันไม่ได้ (409 พร้อมระบุชุดที่ยังขาดยอด)
- **ระบบไม่เสนอตัวเลข** ช่องกรอกว่างเปล่า แสดงข้างกันแค่ "ราคาชุดเดิม ฿X · ตัดออก: {รายการ}" — ไม่มีการคำนวณสัดส่วนหรือหักให้

### 3.3 `document_lines.approved_amount numeric(12,2) NULL` (migration 0021)
1. ว่าง = อนุมัติเต็มตามที่เสนอ (ใช้ `line_total`) · มีค่า = ยอดที่ตกลงจริง
2. **`approved_total` ของเอกสาร = Σ (`approved_amount` ถ้ามี ไม่งั้น `line_total`) ของบรรทัดที่ไม่มี parent และ `approved`** — แล้วหักส่วนลด clamp ≥ 0 · คำนวณในฟังก์ชันเดียวใน domain
3. ตั้งค่าได้**เฉพาะในจังหวะยืนยันผล** (endpoint confirm) · บังคับเหตุผล · audit เก็บ เสนอ → ตกลงจริง · trigger 0022 ยอมให้แก้คอลัมน์นี้เมื่อเอกสารเป็น `issued` เท่านั้น
4. **[Q2 — Ice ตัดสินแล้ว] กฎ 3 ชั้น** (ราคาชุดคือราคาเหมา ตัดชิ้นออกแล้วส่วนลดเหมาหายไปด้วย ยอดใหม่จึงสูงกว่าเดิมได้จริง):

   | ยอดใหม่ เทียบกับ `line_total` | ระบบทำ |
   |---|---|
   | ติดลบ | **บล็อกเสมอ** (CHECK ใน DB + zod) |
   | 0 | อนุญาต (แถมฟรี) · บังคับเหตุผล |
   | ต่ำกว่าที่เสนอ | อนุญาต · บังคับเหตุผล |
   | สูงกว่าที่เสนอ ไม่เกิน 2 เท่า | อนุญาต · บังคับเหตุผล · **หน้าจอแสดงส่วนต่างเป็นตัวเลขชัด ๆ** (เช่น "+฿1,200 จากราคาชุดเดิม") ไม่ใช่แค่ไอคอนเตือน |
   | **เกิน 2 เท่า** | **บล็อก** — "ยอดนี้เกิน 2 เท่าของราคาที่เสนอ น่าจะพิมพ์ผิด ถ้าตั้งใจจริงให้ออกใบเสนอราคาฉบับใหม่" |

   - เส้น 2 เท่า: ฟังก์ชันเดียวใน domain (`checkApprovedAmount`) ใช้ทั้ง API และหน้าจอ · ตรวจที่ API เสมอ (หน้าจอเป็นแค่การบอกล่วงหน้า)
   - ยอดเท่ากับที่เสนอพอดี = ไม่ต้องกรอก `approved_amount` (ปล่อยว่าง)
   - **เอกสารแสดง "เสนอ ฿X / ตกลง ฿Y" ที่บรรทัดนั้น** ให้ลูกค้าเห็นก่อนตกลง ไม่ใช่เห็นแค่ยอดสุดท้าย
5. API รับ `approved_amount` เฉพาะบรรทัดแม่ของชุดที่เข้าเงื่อนไข §3.2 · บรรทัดอื่น = 400
6. ถอยการยืนยัน (§8.2) ไม่ล้างค่า — กลับไปเป็น `issued` แก้ได้อีกครั้งในจังหวะยืนยันครั้งถัดไป
7. rev ใหม่คัดลอก `approved_amount` มาด้วย (D7)

### 3.4 ใบสั่งงาน / เอกสาร
- ใบสั่งงานช่าง: บรรทัดแม่ที่อนุมัติ + **เฉพาะบรรทัดย่อยที่อนุมัติ** · ไม่มีราคา · ช่างไม่เห็นงานที่ลูกค้าตัดออก

  - หน้าใบเสนอราคามีปุ่ม "เลือกรุ่นรถ" ให้พนักงานจับคู่ได้ทันทีจากรายการควบคุม (ค้นแบบเดียวกับตัวเลือกจังหวัด) หรือ**เพิ่มรุ่นใหม่ในรายการควบคุม**ได้จากหน้าเดียวกัน (WO-005 §5 ข้อ 3) · การจับคู่/เพิ่มรุ่นเข้า audit
  - หน้า "รุ่นที่ยังไม่จับคู่" (manager+): รายการรถ/ข้อความยี่ห้อ-รุ่นที่ยังไม่มี `vehicle_model_id` เรียงตามจำนวน ให้จับคู่ทีละกลุ่มได้ (เช่น `Chevloret` ทั้งหมด → Chevrolet …)
- ช่วงปีไม่เป็นคีย์ เก็บใน `vehicle_models.year_range` เพื่อแสดงผล (ตาม R2)
- `vehicle_models` ของสาขาตั้งต้นจาก `vehicle_models` ต้นแบบ 632 แถวผ่าน WO-004
- ตาราง `model_parts` (0002) ไม่ใช้ในรอบนี้

### 4.3 ลำดับการดึงราคา (ฟังก์ชันเดียวใน domain)
```
catalog_model_prices ของ vehicle_model_id ของรถคันนี้ (ถ้ารถจับคู่แล้ว)
  → catalog_items.base_price
    → ว่าง = พนักงานพิมพ์เอง
```
รายการที่ถูกรวม (`merged_into_id`) → ใช้รายการปลายทางเสมอ

### 4.5 [v3 — D12] กันรายการซ้ำ
1. **เตือนตอนเพิ่ม:** ก่อนบันทึกรายการใหม่ server ตรวจรายการในหมวดเดียวกันที่ชื่อ "คล้าย" → ถ้าเจอ หน้าจอถาม *"คล้ายกับ `X` ที่มีอยู่แล้ว ใช่อันเดียวกันไหม"* — เลือก "ใช้ของเดิม" หรือ "เพิ่มใหม่จริง ๆ"
   - "คล้าย" = `price_key()` เท่ากัน **หรือ** ระยะแก้ไข (edit distance) หลัง normalise ≤ 2 **หรือ** ชื่อหนึ่งเป็นส่วนหนึ่งของอีกชื่อ — ฟังก์ชันเดียวใน domain มีเทส (เช่น "ลูกหมากปีกนกล่าง L+R" กับ "ลูกหมากปีกนกล่าง L/R")
   - `GET /api/catalog/similar?category&name`
2. **หน้าจอรวมรายการซ้ำ** (manager+): เลือกรายการ A รวมเข้า B → A ได้ `merged_into_id = B` และ `is_active = false` · ราคาต่อรุ่นของ A ย้ายไป B เฉพาะรุ่นที่ B ยังไม่มีราคา (ที่ชนกันให้ manager เลือก) · audit
3. **บรรทัดเก่าที่อ้าง A ไม่ถูก UPDATE** — เพราะบรรทัดของเอกสารที่ออกเลขแล้วแก้ไม่ได้ (0022) · ทุกจุดที่อ่าน `catalog_item_id` ผ่านฟังก์ชันเดียว `resolveCatalogItem()` ที่ตาม `merged_into_id` ไปถึงรายการปลายทาง → รายงาน/การนับยอดขายเห็นเป็นรายการเดียวกัน ขณะที่เอกสารเดิมยังเป็นหลักฐานตามจริง
4. ห้ามรวมเป็นวง (A → B → A) — CHECK ในฟังก์ชัน + เทส

## 6. วงจรชีวิตใบเสนอราคา

วงจร draft → issued → signed และ trigger ตาม v2 §6 คงไว้ · เปลี่ยน/เพิ่มดังนี้

### 6.1 สิ่งที่แก้ได้ในแต่ละสถานะ [v3]
| สถานะ | แก้ได้ |
|---|---|
| draft | ทุกอย่าง |
| issued | การตัดสินใจรายบรรทัด (**รวมบรรทัดย่อย** — D10) · และในจังหวะยืนยันเท่านั้น: `approved_amount` ของชุด + `documents.discount` |
| signed | ไม่ได้เลย · ยกเว้นถอยการยืนยัน (→ issued) และ → superseded |
| superseded / void | ไม่ได้เลย |

### 6.2 [v3 — D10 + D11] "ยืนยันผลลูกค้า" = จุดปรับยอดจุดเดียว
`POST …/confirm` รับ:
```
{ adjustments?: { setLines?: [{ lineId, approvedAmount, reason }], discount?: { amount, reason } } }
```
- ตรวจครบ: ทุกบรรทัดแม่ตัดสินแล้ว · ชุดที่ถูกตัดบางชิ้นมี `approvedAmount` ครบ · เหตุผลไม่ว่าง
- ทั้งหมดใน transaction เดียว: บันทึกยอดปรับ → คำนวณ `approved_total` ด้วยฟังก์ชัน domain → issued → signed → สถานะงานตาม D4/D5 → เขียน `vehicle_offered_items` (`next_time`) → audit **รายการเดียว** `quotation_confirmed` ที่เก็บทุกการปรับ (เสนอ → ตกลง · ส่วนลดเดิม → ใหม่ · เหตุผล)
- หน้าจอยืนยันแสดงทุกชุดที่ต้องกรอกยอด + ช่องส่วนลด อยู่ใน dialog เดียว

### 6.3 การเปลี่ยนพฤติกรรมเดิม (เหมือน v2)
ถอยงาน "อนุมัติ → เสนอราคา" ได้ 409 เมื่อใบเป็น `signed` → ใช้การถอยการยืนยัน (§8.2) หรือออก rev ใหม่

### 6.4 [v3 — R3 แทนที่ด้วยคำตัดสิน Q1] งานจบแบบไม่ซ่อม

ใบเสนอราคาที่ลูกค้าปฏิเสธ**ไม่ใช่เอกสารที่ควรยกเลิก** — เป็นบันทึกว่าเสนอไปแล้วลูกค้าไม่เอา ซึ่งเป็นข้อมูลที่เจ้าของร้านต้องการมากที่สุด (30% ของใบจริงถูกปฏิเสธ) จึงแยก 3 กรณี

เมื่องานเข้า `rejected` (ไม่อนุมัติ) หรือ `carout` (เอารถลง) — **ใน transaction เดียวกับการเปลี่ยนสถานะงาน**:

| ใบเสนอราคาที่ยัง live | ทำอะไร |
|---|---|
| `signed` (ยืนยันผลแล้ว) | **ไม่แตะเลย** — เป็นบันทึกสมบูรณ์แล้ว (เช่น D5 ปฏิเสธหมดแล้วยืนยัน) |
| `issued` (มีเลข ตัดสินยังไม่ครบ) | **ปิดโดยระบบ:** `status = 'void'` · `void_reason = 'job_closed'` · `voided_by = NULL` (ระบบปิด ไม่ใช่คนกด) · `voided_at = now()` · audit ชนิด **`document_closed_by_job`** (คนละชนิดกับ `document_voided` ที่คนกด) · เนื้อหาและเลขที่ไม่เปลี่ยน เลขยังอยู่ในลำดับ |
| `draft` (ไม่มีเลข ไม่ใช่เอกสารทางการ) | **ไม่แตะเลย — คงเป็น draft** (Ice ตัดสิน 6 ต.ค.: "ปล่อยไว้ ไม่แตะต้อง") · ไม่ void · ไม่ลบ · ไม่เขียน audit `document_closed_by_job` · เหตุผล: `ck_number_when_issued` ห้าม void เอกสารที่ไม่มีเลข · ใบร่างไม่มีผลทางบัญชีและไม่อยู่ใน "รอลูกค้าตัดสินใจ" |

**สิทธิ์ owner-only ของการ void ด้วยมือไม่มีข้อยกเว้นเลย** เพราะการปิดโดยระบบไม่ใช่การกด void:
- `POST …/void` (void ด้วยมือ) ยังเป็นของ owner คนเดียว · advisor ยิงตรง → **403** เหมือนเดิม
- advisor ปิดงานตามปกติ → ใบถูกปิดโดยระบบ · audit `document_closed_by_job` ไม่ใช่ `document_voided`
- รายงาน/หน้าจอต้องแยก "ปิดเพราะงานจบ" ออกจาก "ยกเลิกเอกสาร" ด้วย `void_reason = 'job_closed'` (ฟังก์ชันเดียวใน domain)

**[Q1] บังคับเหตุผลก่อนปิดงานเป็น `rejected`:**
- ถ้างานมีใบ `issued` ที่ยังมีบรรทัดแม่ `pending` → การเปลี่ยนสถานะงานเป็น `rejected` **ต้องส่ง `declineReason` (enum `decline_reason` เดิม) + โน้ต (บังคับเมื่อเลือก "อื่น ๆ")** ไม่ส่ง = 400 พร้อม `fields.declineReason`
- ใน transaction เดียว: บรรทัดที่ `pending` ทั้งหมด → `declined` ด้วยเหตุผลนั้น (`decided_by` = ผู้กด) → ใบปิดโดยระบบตามตารางข้างบน → งาน `rejected`
- บรรทัดที่ตัดสินไปแล้วก่อนหน้า (อนุมัติ/ปฏิเสธ) **คงผลเดิม** ไม่ถูกเขียนทับ
- `chose_alternative` เลือกไม่ได้ในจังหวะนี้ (ไม่ใช่การปฏิเสธจริง — D13)
- `carout` **ไม่บังคับ** (เหตุผลมักไม่เกี่ยวกับราคา) — บรรทัด pending คงเป็น pending บนใบที่ถูกปิด
- หน้าจอ: ปุ่ม "ไม่อนุมัติ" บน /today และหน้าใบเสนอราคา เปิด dialog เลือกเหตุผลเมื่อมีบรรทัดยังไม่ตัดสิน (server บอกผ่าน `movesNeedingReason` / ฟิลด์ใหม่ที่บอกว่าต้องใช้เหตุผลปฏิเสธ)

ผลที่ได้: ไม่มีใบค้างใน "รอลูกค้าตัดสินใจ" หลังงานจบ · เหตุผลที่ลูกค้าไม่เอามีครบทุกเคสที่ปิดด้วย `rejected` · มีเทสคุม (§12)
