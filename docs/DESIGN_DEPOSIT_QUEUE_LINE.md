# ออกแบบแก้: นัดหมาย · มัดจำ · ปิดบิลผ่าน LINE

> เขียน 12 ก.ย. 2026 — จากปัญหาจริงที่เจอในระบบเดิม
> สามเรื่องนี้แยกกันไม่ได้ เพราะทั้งสามชนกันที่จุดเดียว: **ตอนปิดบิล**

## ส่วนที่ 1 — ทำไมคิวถึงซ้ำ

### อาการ

ลูกค้าโทรมานัด → ระบบสร้างใบเสนอราคาให้ → ลูกค้าโอนมัดจำ → ข้อมูลไปโผล่ในหน้ามัดจำ
วันเดียวกันลูกค้าเข้ามาจริง → พนักงานกด "สร้างคิวใหม่" → ได้คิวใหม่ **แต่ของเก่าเด้งกลับมาด้วย**

### สาเหตุจริง

ระบบเดิมมองว่า "การมาซ่อมรถหนึ่งครั้ง" คือของ **4 ชิ้นแยกกัน**:

```
นัดหมาย          ใบเสนอราคา         มัดจำ           คิว/งาน
   │                  │                │               │
   └── ไม่รู้จักกัน ──┴─ ไม่รู้จักกัน ─┴─ ไม่รู้จักกัน ─┘
```

ไม่มีอะไรในฐานข้อมูลบอกว่า 4 อันนี้คือ**เรื่องเดียวกัน** พอกด "สร้างคิวใหม่" ระบบก็ทำตามที่สั่งจริงๆ
คือ *สร้างของชิ้นที่ 5* แทนที่จะ *เลื่อนสถานะของเดิม* ของเก่าจึงยังลอยอยู่ และหน้าคิวก็ดึงมาแสดงทั้งคู่

**นี่ไม่ใช่บัคที่แก้ได้ด้วยการเขียนโค้ดให้ระวังขึ้น** ตราบใดที่ 4 อันนี้ยังไม่รู้จักกันในฐานข้อมูล
ทุกครั้งที่มีปุ่ม "สร้าง" ก็จะเกิดของซ้ำได้อีก แค่คนละที่

### วิธีแก้ — การมาถึงคือ "การเลื่อนสถานะ" ไม่ใช่ "การสร้าง"

```
booking ──(รถมาถึง)──▶ job
   │  status: booked → arrived        │
   │  job_id: NULL → <id ของ job>     │
   │                                  │
   └── quotation (draft, ยังไม่มีเลข) ┘
         เอกสารใบเดิม ไม่สร้างใหม่
```

**กติกาที่ฐานข้อมูลบังคับ:**

| # | กติกา | บังคับด้วย |
|---|---|---|
| 1 | หนึ่ง booking สร้าง job ได้ไม่เกิน 1 ใบ | `CREATE UNIQUE INDEX ... ON jobs (booking_id) WHERE booking_id IS NOT NULL` |
| 2 | job ที่ผูก booking แล้ว จะเปลี่ยนไปผูก booking อื่นไม่ได้ | trigger `trg_jobs_booking_immutable` บน `jobs` (0011 ลบ `bookings.job_id` ทิ้ง ลิงก์อยู่ข้างเดียวที่ `jobs.booking_id`) |
| 3 | หนึ่ง job มีใบเสนอราคาที่ยังไม่ถูกแทนที่ได้ 1 ใบ | partial unique index บน `documents (job_id)` where `kind='quotation' AND superseded_by IS NULL` |
| 4 | หน้าคิวอ่านจาก **view เดียว** ไม่ใช่เอาสองลิสต์มาต่อกันที่ frontend | view `queue_board` (0013 — แทน `queue_today` ของ 0011) — union แล้ว **ตัด booking ที่มี job แล้วออกด้วย `NOT EXISTS`** |

ข้อ 4 คือข้อที่ตรงกับอาการที่เจอที่สุด — ของเก่าเด้งกลับมาเพราะหน้าจอถามสองที่แล้วเอามาต่อกัน
พอมี view เดียว ของที่แปลงเป็นคิวแล้วจะหายจากลิสต์นัดหมายโดยอัตโนมัติ ไม่ต้องมีใครไปลบ

### ใบเสนอราคาตอนนัดหมาย — สร้างได้ แต่ยังไม่มีเลข

ต้องสร้างได้จริง เพราะเคสสั่งอะไหล่พิเศษต้องรู้ราคาก่อนถึงจะเก็บมัดจำได้
แต่ต้องเป็น **draft ที่ยังไม่ได้จองเลขที่เอกสาร**

- draft แก้ได้ ลบได้ ไม่กินเลข
- ลูกค้าไม่มา → draft ตายไปกับ booking ไม่มีเลขเอกสารหาย
- ลูกค้ามา → **draft ใบเดิมผูกเข้า job** แล้วค่อยจองเลขตอนออกให้ลูกค้าเซ็น

**เลขที่เอกสารจองตอน "ออกเอกสาร" ไม่ใช่ตอน "สร้างแถว"** — กติกานี้แก้ปัญหาเลขข้ามไปในตัว

## ส่วนที่ 2 — มัดจำ

### ความผิดพลาดหลักของระบบเดิม

**มัดจำถูกมองเป็น "ส่วนลด" หรือ "ฟิลด์บนใบเสนอราคา"**
ที่ถูกคือ **มัดจำคือ "เงินที่รับมาก่อนที่จะมีบิล"** — มันเป็น *รายการรับเงิน* ไม่ใช่ *ยอดบนเอกสาร*

พอมองผิด ปัญหาตามมาเป็นชุด:

| อาการ | เกิดเพราะ |
|---|---|
| มัดจำหายเมื่อใบเสนอราคาถูกแก้/สร้างใหม่ | มัดจำผูกกับเอกสาร แทนที่จะผูกกับลูกค้า |
| มัดจำออนไลน์ผ่านเพจลงไม่ได้ (ไม่มีรถ ไม่มีคิว) | มัดจำบังคับต้องมี job |
| ยอด VAT เพี้ยน | เอามัดจำไปลบออกจากยอดก่อนคิด VAT |
| สรุปยอดรายวันนับเงินซ้ำ/หาย | วันรับมัดจำกับวันปิดบิลคนละวัน แต่ระบบนับที่เดียว |

### แบบที่ถูก

```
มัดจำ = แถวใน payments ที่ยังไม่มีเอกสารปลายทาง
   ผูกกับ: customer (บังคับ) · booking (ถ้ามี) · job (เติมทีหลังได้)
   ไม่ผูกกับ: ใบเสนอราคา
```

**ตอนปิดบิล** มัดจำไม่ได้ไปลดยอดในเอกสาร แต่ไปโผล่เป็น **บรรทัดหักในส่วนการชำระ**:

```
ยอดรวมค่าอะไหล่                        8,000.00
ยอดรวมค่าแรง                           1,500.00
                                    ───────────
รวมทั้งสิ้น                            9,500.00     ← VAT (ถ้ามี) คิดจากบรรทัดนี้
  หักมัดจำ 3 ก.ย. (โอน)               -2,000.00
                                    ───────────
คงเหลือชำระ                            7,500.00
```

ยอดบนเอกสารคือ 9,500 เสมอ ไม่ว่าจะมัดจำมาเท่าไหร่ — **VAT คิดจากบิลเต็ม ไม่ใช่จากยอดคงเหลือ**

### สองรายงานที่ห้ามรวมกัน

นี่คือต้นเหตุที่สรุปยอดรายวันเพี้ยนเวลามีมัดจำ:

| รายงาน | นับอะไร | นับตามวันไหน |
|---|---|---|
| **เงินเข้าวันนี้** (ปิดกะ/นับลิ้นชัก) | ทุกแถวใน `payments` รวมมัดจำ | วันที่**รับเงิน** |
| **ยอดขายวันนี้** (รายได้) | เอกสารที่ออก | วันที่**ปิดบิล** |

มัดจำ 2,000 รับวันที่ 3 ปิดบิลวันที่ 8 → เงินเข้าวันที่ 3 คือ 2,000 · ยอดขายวันที่ 3 คือ 0 · ยอดขายวันที่ 8 คือ 9,500 · เงินเข้าวันที่ 8 คือ 7,500
**ถูกต้องทั้งคู่ และห้ามพยายามทำให้สองตัวเลขนี้เท่ากัน**

### สถานะของมัดจำ

| สถานะ | ความหมาย | ใครกด |
|---|---|---|
| `held` | รับแล้ว รอลูกค้ามา | ระบบ |
| `applied` | ใช้หักในบิลแล้ว | ระบบ ตอนปิดบิล |
| `refunded` | คืนลูกค้า | ผู้จัดการ |
| `forfeited` | ริบ | ผู้จัดการ |

เลยวันนัด → ระบบเตือนทันที ขึ้นในรายการที่ต้องตาม ให้เลือกเป็นเคสๆ ว่าคืนหรือริบ (ตามที่ตกลงไว้)
**ไม่มีการริบอัตโนมัติ** — เงินของลูกค้า ต้องมีคนตัดสินใจและมีชื่อกำกับ

### มัดจำออนไลน์ผ่านเพจ (ไม่มีรถ ไม่มีคิว)

รับได้ เพราะมัดจำผูกกับ **ลูกค้า** ไม่ใช่ job:

- ลูกค้าใหม่ → สร้างแถวลูกค้าจากชื่อ+เบอร์ที่ทักมา
- แนบสลิป (`slip_file_id`) + ช่องทาง + วันที่คาดว่าจะเข้า
- ยังไม่มี booking ก็ได้ — ขึ้นในรายการ "มัดจำที่ยังไม่มีนัด"
- วันที่ลูกค้าโผล่มา พนักงานเปิดคิว ระบบ**ค้นเจอมัดจำค้างของเบอร์นี้แล้วถามว่าใช่ใบนี้ไหม**

ข้อสุดท้ายสำคัญ — ถ้าไม่มีการค้นอัตโนมัติ มัดจำออนไลน์จะหายในทางปฏิบัติ เพราะไม่มีใครจำได้

## ส่วนที่ 3 — บอท LINE ปิดบิลอัตโนมัติ

### สิ่งที่ต้องการ

พิมพ์ในกลุ่ม LINE → บอทปิดบิลให้เลย → สรุปยอดรายวันขึ้นเอง
หน้าเว็บใช้เฉพาะตอนบอทล่ม

### ข้อขัดกันที่ต้องแก้

ระบบใหม่บังคับว่าใบเสร็จออกได้ต่อเมื่อรู้ว่า**ทำรายการไหนจริง** (บิลเก็บเฉพาะที่ทำ ไม่ใช่ทุกอย่างที่อนุมัติ)
แต่ข้อความ `คิว 12 โอน 4,500 ชำระเงินเรียบร้อย` ไม่ได้บอกว่าทำอะไรไปบ้าง

### ทางออก — ใช้ "ยอดเงิน" เป็นตัวตรวจสอบ

บอทเดิมทำถูกทางอยู่แล้ว: บอท 3 มีโหมดตรวจยอดก่อนปิด **ต่อยอดจากตรงนั้น**

```
ข้อความเข้ากลุ่ม
      │
      ▼
แกะ queue_no · ช่องทางชำระ · ยอดที่ได้รับ
      │
      ▼
ยอดที่ได้รับ + มัดจำที่ผูกกับคิวนี้  ==  ยอดรวมของรายการที่อนุมัติ ?
      │                                        │
     ใช่                                     ไม่ใช่
      │                                        │
      ▼                                        ▼
ปิดบิล — ถือว่าทำครบทุกบรรทัด        ไม่ปิด · ตอบในกลุ่มว่าต่างกันเท่าไหร่
ออกใบเสร็จ · ตัดสต๊อก                 · ให้ไปจัดการในระบบ
```

**เหตุผลที่ใช้ได้จริง:** งานส่วนใหญ่ทำครบตามที่อนุมัติ ยอดจึงตรง → ปิดอัตโนมัติ
งานที่ลูกค้าตัดรายการนาทีสุดท้าย ยอดจะไม่ตรงทันที → บอทไม่ปิด ซึ่งถูกแล้ว เพราะเคสนั้นต้องมีคนบอกว่าตัดอะไรออก

**ยอดเงินทำหน้าที่เป็น checksum** ไม่ใช่แค่ตัวเลข

### กติกาที่ต้องมี ไม่งั้นบอทจะสร้างปัญหาแทน

| # | กติกา | เหตุผล |
|---|---|---|
| 1 | **idempotency key = (shop, queue_no, วันที่, ยอด)** | พนักงานส่งข้อความซ้ำ / LINE ส่ง webhook ซ้ำ → ต้องไม่ปิดบิลสองรอบ |
| 2 | **ต้องบวกมัดจำเข้าไปในสมการเสมอ** | ไม่งั้นทุกงานที่มีมัดจำจะยอดไม่ตรงและปิดไม่ได้เลย |
| 3 | **บอทปิดได้เฉพาะคิวที่สถานะพร้อมปิด** | คิวที่ยังไม่ได้อนุมัติ/ยังไม่จบงาน ห้ามปิดจากแชท |
| 4 | **ทุกการปิดจากบอทบันทึกข้อความต้นฉบับไว้** | เป็นหลักฐานว่าใครสั่งปิด ด้วยข้อความอะไร เวลาไหน |
| 5 | **บอทตอบกลับทุกครั้ง — สำเร็จหรือไม่สำเร็จ** | เงียบ = พนักงานคิดว่าปิดแล้ว ทั้งที่ยังไม่ปิด อันตรายกว่าตอบว่าพัง |
| 6 | **หน้าเว็บทำได้ทุกอย่างที่บอททำได้** | บอทล่ม ร้านต้องไม่หยุด |
| 7 | **ปิดจากบอทกับปิดจากเว็บ ใช้ service ตัวเดียวกัน** | สองทางเข้า ตรรกะเดียว ไม่งั้นจะแตกต่างกันโดยไม่มีใครรู้ |

### งานแยกโค้ดที่ต้องทำ

บอท 3 ไฟล์ตัวเอง 8 KB แต่เรียกใช้ของในบอท 1 เกือบทั้งหมด:
`closeQuotationByQueue` · `verifySignature` · `getMessageTemplate` · `renderTemplate` · `parseLineQueueMessage.js` (53 KB) พร้อม `PAID_PHRASE_RE`

**ต้องดึงออกมาเป็น 3 ก้อนแยกกัน:**

1. `packages/line-parser` — แกะข้อความ ไม่มี I/O ไม่แตะฐานข้อมูล **เทสได้ด้วย unit test ล้วน**
2. `packages/domain/closeBill` — ตรรกะปิดบิล ใช้ร่วมกันระหว่างบอทกับเว็บ
3. `apps/api/routes/line` — แค่รับ webhook ตรวจลายเซ็น แล้วส่งต่อ

ก้อนที่ 1 คือของมีค่าที่สุดในระบบเก่า และเป็นก้อนเดียวที่**ต้องยกมาทั้งดุ้น**

### บอท 1 กับบอท 2 — คำถามที่ยังไม่ได้ตอบ

ถ้าตัดบอท 2 (พิมพ์รายการอะไหล่เข้าใบเสนอราคา) ทิ้ง แปลว่าพนักงานต้องคีย์รายการในเว็บ
พอคีย์ในเว็บแล้ว การกดปิดบิลในเว็บก็อีกคลิกเดียว — บอท 3 จะเหลือประโยชน์น้อยลง

**ต้องเลือกให้ชัดว่า "ที่ทำงานหลัก" ของพนักงานหน้าร้านคือ LINE หรือเว็บ**
ถ้าคือ LINE ต้องเก็บบอท 2 ไว้ด้วย ไม่งั้นข้อมูลจะอยู่คนละที่กับที่พนักงานพิมพ์
