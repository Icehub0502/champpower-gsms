# ทีมที่ดูแลโปรเจกต์นี้

> ทีม agent ที่รับผิดชอบ Champpower GSMS ทั้งโปรเจกต์
> เริ่มงานทุกครั้งที่ **`gsms-lead`** — ห้ามเรียก specialist ตรง ๆ สำหรับงานใหญ่

---

## วิธีเริ่มงาน

```
คุณ ──▶ gsms-lead ──▶ product-analyst ──▶ solution-architect
                            │
                            ▼
                    แตกงาน + เลือก specialist
                            │
                    ⏸ หยุดรออนุมัติจากคุณ
                            │
                            ▼
                    specialist ลงมือ ──▶ เกตรีวิว ──▶ ux-advocate
```

**`gsms-lead` จะไม่เริ่มเขียนโค้ดเองสำหรับอะไรที่แตะเงิน สต๊อก เอกสาร ภาษี สิทธิ์ หรือ migration** — มันจะเสนอแผนแล้วรอคุณอนุมัติเสมอ

## ฐานของโปรเจกต์ — สรุปเมื่อ 12 ก.ย. 2026

**ฐานคือดีไซน์ใหม่ 62 ตารางบน PostgreSQL ตามที่ออกแบบไว้**
**`stock-system` คือ *ต้นแบบ* ไม่ใช่ฐาน**

`stock-system` เป็นระบบที่อู่สมุทรปราการใช้จริงอยู่ตอนนี้ — 37 ตาราง · 33 หน้าจอ · 25 route
แต่เจ้าของระบบยืนยันว่า **ยังไม่สมบูรณ์ มีบัค และมีช่องโหว่ในการเปิดบิล** จึงไม่เอามาเป็นฐาน

หน้าที่ของมันในโปรเจกต์นี้คือ **สเปกที่มีชีวิต**:

- **อ่านเพื่อรู้กติกาจริงของอู่** — ก่อนออกแบบหน้าจอหรือ flow ไหน ต้องเปิดดูของเดิมก่อนว่าเขาทำยังไง
- **ยกโค้ด/ข้อมูลบางส่วนมาใช้** ตามตารางข้างล่าง
- **เป็นรายการบัคที่ห้ามเกิดซ้ำ** — ช่องโหว่ที่เจอในของเดิมต้องกันด้วยโครงสร้างฐานข้อมูล ไม่ใช่ด้วยการเขียนโค้ดให้ระวังขึ้น

**ข้อที่ยกเลิกจากแผนเดิม**

| เดิม | ความจริง |
|---|---|
| SYS-14 · ไม่ย้ายข้อมูลเลย | **แก้เป็น** — ย้ายเฉพาะ master data ทั้งสองสาขา ไม่ย้ายประวัติรายการ (ดูกติกาข้างล่าง) |
| FIX-02 · เงินเป็น VARCHAR | เป็นปัญหาของ `ChamppowerD` เท่านั้น — `stock-system` เป็น `DECIMAL` อยู่แล้ว |

## กติกาข้อมูล — เหมือนกันทั้งสองสาขา

| ย้ายมา | ไม่ย้าย |
|---|---|
| ลูกค้า · รถ · ทะเบียน | ประวัติงาน · ใบเสนอราคา · ใบเสร็จเก่า |
| อะไหล่ · ราคาขาย · price book | ledger สต๊อกเก่า (ยกมาเป็นยอดตั้งต้นเท่านั้น) |
| ยอดคงเหลือสต๊อกวันตัดระบบ | ประวัติการเคลื่อนไหวสต๊อก |
| งานที่ยังอยู่ในประกัน (ย้อน 12–18 เดือน) | ทุกอย่างที่เหลือ |

**เหตุผล:** ถ้าลูกค้าเก่ากลับมาแล้วพนักงานต้องพิมพ์ใหม่ทุกคน พนักงานจะเลิกใช้ระบบภายในสัปดาห์เดียว
แต่ประวัติรายการเก่าไม่ต้องมาอยู่ในระบบใหม่ — **เก็บระบบเดิมไว้อ่านอย่างเดียวอย่างน้อย 1 ปี**

- **สมุทรปราการ** — MySQL ย้ายง่าย เขียน SQL map เข้าตารางใหม่ได้ตรงๆ
- **ดอนเมือง** — Firebase (NoSQL) แปลงตรงๆ ไม่ได้ export JSON แล้วเขียน mapper แยก

### LINE — เหลือบอทเดียว

| บอท | หน้าที่เดิม | ระบบใหม่ |
|---|---|---|
| บอท 1 "คิว" (130 KB) | สร้างคิว/ใบเสนอราคาจากแชท | **ตัดทิ้ง** — หน้าคิวในระบบใหม่แทน |
| บอท 2 "รับรายการ" | พิมพ์รายการอะไหล่+ราคาเข้าใบเสนอราคา | **ตัดทิ้ง** — หน้าใบเสนอราคาแทน |
| บอท 3 "ปิดบิล" | ตรวจยอด + ปิดบิลจากข้อความแชท | **เก็บไว้** เพื่อให้สรุปยอดรายวันอัตโนมัติ |

⚠️ **บอท 3 ตัวไฟล์เองแค่ 8 KB แต่ตรรกะจริงไม่ได้อยู่ในนั้น** — มันเรียกใช้ของในบอท 1:
`closeQuotationByQueue` · `verifySignature` · `getMessageTemplate` · `renderTemplate` และ `parseLineQueueMessage.js` (53 KB) รวมถึง `PAID_PHRASE_RE`
**การ "เก็บแค่บอทปิดบิล" คืองานแยกโค้ด ไม่ใช่งานก๊อปไฟล์เดียว** ต้องดึงส่วนที่ใช้ร่วมออกมาเป็นโมดูลของตัวเอง

⚠️ **บอท 3 ห้ามปิดบิลเองในระบบใหม่** ระบบใหม่บังคับว่าใบเสร็จออกได้ต่อเมื่อติ๊กแล้วว่าบรรทัดไหนทำจริง และ `SUM(payments) = grand_total`
ข้อความแชทบอกไม่ได้ว่าทำรายการไหนบ้าง — **หน้าที่ใหม่ของบอท 3 คือบันทึก "รายการรับเงิน" เข้า `payments` เท่านั้น** ส่วนการปิดบิลเกิดในระบบ สรุปยอดรายวันยังอัตโนมัติเหมือนเดิม

## ความเสี่ยงข้อใหญ่ที่สุดของแผนนี้ — วันตัดระบบ

เมื่อฐานเป็นดีไซน์ใหม่ ไม่ใช่การต่อยอดของเดิม แปลว่า **อู่ต้องใช้ระบบเก่าที่มีบัคต่อไปจนกว่าระบบใหม่จะแทนได้ทั้งหมด** แล้วสลับทีเดียว

กติกาที่ทีมต้องยึด:

1. **ตัดระบบที่รอยต่อเดือน** ไม่ตัดกลางเดือน — สรุปยอดและภาษีจะคาบเกี่ยว
2. **ระบบเก่าไม่ถูกลบ** เปลี่ยนเป็นอ่านอย่างเดียว เก็บอย่างน้อย 1 ปี
3. **ต้องซ้อมนำเข้า master data บนสำเนาอย่างน้อย 2 รอบ** จับเวลาไว้ว่าอู่ต้องหยุดกี่นาที
4. **ต้องมีแผนถอย** — เงื่อนไขว่าเมื่อไหร่กลับไประบบเก่า และกลับยังไง ถ้าไม่มี ห้ามตัด
5. **ก่อนตัด ต้องเดินคู่ขนาน 1 สัปดาห์** — คีย์งานจริงเข้าทั้งสองระบบ เทียบยอดทุกวัน

## แผนปล่อยใช้ — จัดลำดับตามที่เจ้าของสั่ง (12 ก.ย. 2026)

> ลำดับความสำคัญ: **คิว/จอง → ออกบิล → สต๊อก (สำคัญที่สุด)** แล้วค่อย ฝั่งซื้อ → VAT → KPI
> ทุก release ต้องมีคนใช้จริงก่อนขึ้น release ถัดไป

### ทำไมสต๊อกต้องอยู่ใน release แรก

ระบบต้นแบบ **มีสต๊อกใช้งานอยู่แล้ว** — ledger · QR เบิกของ · นับสต๊อก · หน้าตัดสต๊อก
ถ้าตัดระบบโดยที่ของใหม่ยังไม่มีสต๊อก **นั่นคือการถอยหลัง ไม่ใช่การอัปเกรด** อู่จะเสียความสามารถที่มีอยู่
เพราะฉะนั้น **สต๊อกไม่ใช่ release ที่ 2 แต่เป็นเงื่อนไขของวันตัดระบบ**

### Release 0 — วางฐาน (ยังไม่มีใครใช้)

โฟลเดอร์นี้ · PostgreSQL 16 · migration 0001–0011 · seed 2 กลุ่ม 6 สาขา 7 role · `kysely-codegen` · API contract · CI
FIX-01 (API key) · FIX-06 · FIX-07 · FIX-10 (.env + ออก key ใหม่) ทำตั้งแต่ต้น ไม่ใช่ปะทีหลัง
รูปเก็บเป็นไฟล์บนดิสก์ตั้งแต่แรก — ไม่ทำซ้ำ `job_photos LONGTEXT` ของต้นแบบ

**ผ่านได้เมื่อ:** เทส isolation 2 กลุ่ม 6 สาขาผ่าน · query ข้ามกลุ่มได้ 0 แถว · CI เขียว

### Release 1 — คิว · จอง · บิล · สต๊อก แล้วตัดระบบที่สมุทรปราการ

release ที่ใหญ่ที่สุดของโปรเจกต์ ต้องทำให้ได้**อย่างน้อยเท่าต้นแบบ ลบบัคของต้นแบบออก**

**1 · คิวและการจอง**
- จองล่วงหน้า · walk-in · กันจองซ้อนที่ระดับฐานข้อมูล (`EXCLUDE USING gist`)
- **นัดหมาย → คิว เป็นการเลื่อนสถานะ ไม่ใช่การสร้าง** (`CLAUDE.md` §5.8) — บั๊กที่เจ็บที่สุดของต้นแบบ
- หน้าคิวอ่านจาก view เดียว

**2 · เอกสารและบิล**
- ใบเสนอราคา → **อนุมัติรายบรรทัด + เซ็น** → ใบแจ้งซ่อม → ปิดงาน → รับเงิน → ใบเสร็จ → สรุปยอดรายวัน
- เลขที่ผ่าน counter · เอกสารออกแล้วแก้ไม่ได้ · **เลขจองตอนออกเอกสาร ไม่ใช่ตอนสร้างแถว**
- **มัดจำเต็มโมดูล** — ผูกกับลูกค้า · มัดจำออนไลน์ผ่านเพจ · เตือนเมื่อเลยนัด · คืน/ริบ
- แยก "เงินเข้าตามวันรับ" กับ "ยอดขายตามวันปิดบิล"

**3 · สต๊อก ★**
- ledger · **reserve ตอนอนุมัติ / issue ตอนเบิกจริง** สองจังหวะ
- ต้นทุนเฉลี่ยเคลื่อนที่ ตรึงลงบนแถวตอน issue — **ไม่มีใครกรอกต้นทุน**
- รับเข้าแบบง่าย (ยังไม่ต้องมีใบกำกับซื้อ/เจ้าหนี้) · ตัดมือ + เกณฑ์วงเงิน · ซื้อด่วน/`buy_to_order`
- นับสต๊อกรอบ · QR เบิกของ (ยกจากต้นแบบ) · กระทบยอด

**4 · LINE**
- บอทปิดบิลเวอร์ชันใหม่ ใช้ยอดเงินเป็น checksum + รหัสเอกสารในข้อความ (`CLAUDE.md` §5.9)
- แยก `packages/line-parser` ออกจากบอท 1 พร้อม fixture ร่วม

**5 · ย้ายข้อมูล + ตัดระบบ**
- นำเข้า master data ของสมุทรปราการ · **ยอดสต๊อกตั้งต้นจากการนับจริงวันตัดระบบ**
- เดินคู่ขนาน 1 สัปดาห์ · ตัดที่รอยต่อเดือน · แผนถอยพร้อม

**ผ่านได้เมื่อ:** เดินคู่ขนานแล้วยอดตรงกันทุกวัน 1 สัปดาห์ · ตัดระบบแล้วทำงานจริง 2 สัปดาห์โดยไม่กลับไปใช้ของเดิม · นับสต๊อกจริงตรงกับระบบภายใน ±2%

### Release 2 — ดอนเมืองขึ้นระบบ

- นำเข้า master data จาก Firebase (export JSON → mapper แยกตัว)
- หน้ารวมกลุ่มสำหรับเจ้าของ
- ทีมแบบดอนเมือง (หัวหน้าทีม + ลูกทีม) คู่กับแบบสมุทรปราการ (ไม่มีทีมตายตัว)
- โอนอะไหล่ระหว่างสาขา

**ผ่านได้เมื่อ:** สองสาขาอยู่ระบบเดียวกัน · เจ้าของเปิดหน้ารวมกลุ่มได้ · ดอนเมืองเปิดบิลใบแรกได้โดยไม่ต้องพิมพ์ข้อมูลลูกค้าใหม่

### Release 3 — ฝั่งซื้อ + ห้อง VAT

- `suppliers` เต็มรูป · ใบกำกับซื้อ · เจ้าหนี้รายเดือน · รู้ว่าอะไหล่แต่ละชิ้นมาจากร้านไหน
- ห้อง VAT — 3 โหมด · VAT เฉพาะค่าของ · ภาษีซื้อดึงจากใบกำกับซื้อ ไม่กรอกซ้ำ

**ผ่านได้เมื่อ:** ออกใบกำกับส่งสรรพากรได้ครบ 1 รอบเดือน · ยอดค้างต่อร้านอะไหล่ตรงกับผลรวมบิลที่ยังไม่จ่าย

### Release 4 — KPI + รายงานเจ้าของ

- ประเมินพนักงานรายไตรมาส
- รายงานเจ้าของ — ต่อยอดจาก `DeclinedSummaryPage` และ `CustomerChannelPage` ของต้นแบบ

## ติดตั้งทีมนี้ในโฟลเดอร์ใหม่

เครื่องมือรีโมตเขียนลง `.claude/` ไม่ได้ ไฟล์ agent จึงอยู่ที่ `docs/agents/`

```
โฟลเดอร์ใหม่/
├─ CLAUDE.md              ← คัดลอกมา
├─ docs/
│  ├─ SYSTEM_PLAN.md      ← คัดลอกมา
│  ├─ TEAM.md             ← ไฟล์นี้
│  └─ agents/*.md         ← คัดลอกมา
└─ .claude/
   └─ agents/*.md         ← คัดลอกจาก docs/agents/
```

รัน `install-agents.bat` ที่ root ของโฟลเดอร์ใหม่ (ดับเบิลคลิก) จะก๊อป `docs\agents\*.md` เข้า `.claude\agents\` ให้เอง
